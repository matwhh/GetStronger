# AGENTS.md — контракт для того, хто продовжує роботу над Get Stronger

Цей файл читають ПЕРШИМ: і людина, і будь-яка нейронка (Claude, GPT,
Cursor, Copilot — байдуже). Тут немає опису фіч — тут правила, які не
видно з коду, і які найдорожче ламати.

Формат навмисно такий: спершу заборони, потім обовʼязкове, потім карта,
потім рецепти. Якщо в тебе п'ять хвилин — читай розділи 1 і 2.

---

## 0. Що це за проєкт за 60 секунд

Get Stronger — особистий інструмент для тренувань і харчування. **Статичний
сайт без збірки**: 23 HTML-сторінки, 64 файли в `js/`, один
`css/style.css`, service worker. Ні webpack, ні Vite, ні npm-залежностей
на фронтенді. Модулі — глобали `window.*`, підключені через
`<script defer>` у розмітці кожної сторінки.

Дані: `localStorage` завжди, Supabase — коли користувач увійшов. Без
акаунта працює все, крім сезонного рейтингу.

Мова коду й коментарів — **українська**. Коментар пояснює ЧОМУ, а не ЩО:
«що» видно з коду.

| Куди | Що там |
|---|---|
| `README.md` | огляд продукту, структура, як запустити |
| `AGENTS.md` (цей файл) | правила, карта, рецепти, стан справ |
| `docs/MAP.md` | карта файл-за-файлом: що чим є і від чого залежить |
| `docs/RECIPES.md` | покрокові рецепти типових змін |
| `docs/ENGINEERING.md` | інженерний журнал: чому рішення саме такі (3400 рядків, читати за потреби) |

## 1. ЗАБОРОНЕНО

Порушення будь-чого з цього списку — це не «спірне рішення», а зламаний
продукт або втрачені дані користувача.

### 1.1. База даних

- **Не скидати, не чистити, не дропати бойову базу.** Жодних `TRUNCATE`,
  `DROP`, `DELETE FROM` без `WHERE` по таблицях користувачів. Там живі
  акаунти, історія тренувань і рейтинг, яких немає більше ніде.
- **Зміни схеми — тільки міграцією** (`apply_migration` з осмисленою
  назвою) І тим самим текстом файлом у `db/`. Виконати SQL руками в
  редакторі й не покласти файл — значить створити обʼєкт, якого немає в
  історії; це вже було (DB-010, знадобився `db/fixate-out-of-band.sql`).
- **Будь-яка перевірка, що ЩОСЬ ПИШЕ, — тільки всередині
  `BEGIN … ROLLBACK`**, а результат повертається через
  `RAISE EXCEPTION`. Так зроблені всі `db/*-tests.sql`.
- **Не послаблювати RLS.** Не давати клієнтові доступ до `elo_week_plan`.
  Не повертати економіку, керовану клієнтським `action_key`.
- **Ніяких чорних списків «заборонених ключів»** — барʼєр має бути
  структурним (RLS, `SECURITY DEFINER`, `CHECK`), а не переліком.

### 1.2. Довіра до клієнта

- **Ніколи не вірити фронтенду** щодо `isAdmin`, `approved`, `rating`,
  `userId`. Це підказки для інтерфейсу. Рішення ухвалює база.
- Сервер — єдине джерело правди про ELO. Клієнт може порахувати
  прогноз, але записує подію тільки `elo_submit`.

### 1.3. Секрети

- **Не використовувати жодних ключів і токенів, які хтось вставив у
  чат.** Не вводити паролі, токени, API-ключі й коди підтвердження в
  жодні поля. Не створювати нових токенів від імені власника.
- Ніяких секретів у коді, логах, звітах, знахідках і комітах.
- `supabase.anonKey` і `sentry.dsn` у `js/config.js` **публічні за
  задумом** — дані боронить RLS, а не таємність ключа. Це не витік.

### 1.4. Продакшн

- **Не створювати акаунти в бойовому Supabase.** Авторизацію перевіряти
  імперсонацією ролей у SQL.
- **Не ганяти навантажувальні тести, високочастотні запити й паралельні
  атаки** по бойовому Supabase.
- Ці перевірки ходять у бойовий бекенд — **запускати тільки з прямого
  дозволу власника**: `verifyregister`, `verifyregfail`,
  `verifyregresume`, `verifyrecover`, `verifyproduction`, `verifyauthz`.
- **Не запускати `tools/fix-push.command`** — він викидає `ci.yml` з
  коміта.

### 1.5. Код

- **Не додавати залежностей на фронтенді.** Жодного npm-пакета в
  браузер. Потрібна бібліотека — вона вендориться файлом у `js/` з
  шапкою-коментарем про походження й ліцензію (як `js/liquid-glass.js`).
- **Не додавати бандлер, TypeScript, JSX, фреймворк.** Це не
  консерватизм: без збірки сайт відкривається подвійним кліком по
  `index.html`, і саме тому його можна лагодити з телефона.
- **Не використовувати `toISOString()` для ключа дня.** Дати ЛОКАЛЬНІ:
  `getFullYear/getMonth/getDate`. Запис о 23:40 в Києві інакше ляже в
  завтра.
- **Не ставити inline `<script>`** — CSP `script-src 'self'` його
  заблокує. Inline `<style>` можна (`'unsafe-inline'` дозволений).
- **Не прибирати функціональність, не пояснивши чому.**

### 1.6. Що робити СТОП і питати власника

- зміни в панелях Supabase / Vercel / GitHub;
- платні плани;
- нова залежність будь-де;
- видалення або міграція даних користувачів;
- зміна правил, які видно користувачеві (як рахується рейтинг, коли
  закінчується сезон, скільки коштує дія);
- знахідка, яку неможливо закрити всередині репозиторію.

У проєкту чотири візуальні стандарти. Новий екран бере готове, а не
малює свій варіант. Повний опис — `docs/ENGINEERING.md`, розділ
«Стандарти візуалізації» (§14).

| Стандарт | Файл | Правило одним рядком |
|---|---|---|
| Графік | `js/journal.js` (`chartScale`, `chartRows`) | графік — це ЛІНІЯ з крапками; стовпчиків немає ніде |

### 2.2. Драбина перевірок

Знизу вгору. Кожна сходинка дешевша за наступну — не лізь угору, поки
нижня червона.

```bash
node --check js/файл.js                     # синтаксис, миттєво
npm test                                    # 766 юніт-тестів, ~6 с
TZ=Europe/Kyiv npm test                     # той самий набір в іншому поясі
node tools/ci-hygiene.mjs                   # гігієна репозиторію, ~1 с
node tools/verify<назва>.mjs                # одна браузерна перевірка, 10–60 с
bash tools/ci-browser.sh core               # 10 наборів, ~6 хв
bash tools/ci-browser.sh full               # core + 31, ~40 хв
```

**Правило, яке тут головне: нова перевірка мусить ПАДАТИ без
виправлення.** Написав тест — зламай виправлення, переконайся, що тест
червоний, поверни. Тест, який ніколи не був червоним, не стереже нічого.
Це не формальність: у цьому репозиторії вже було двоє таких — перевірка
дивилась на клас елемента, а ламалась ширина шару під ним.

## 4. Словник

Без нього половина коду читається неправильно.

| Термін | Що означає в Get Stronger |
|---|---|
| **Сезон** | період рейтингу, ~квартал. Починається в понеділок, закінчується в неділю. Правило діє з `RULE_FROM = 2026-09-01`, заднім числом не застосовується |
| **Тиждень** | завжди Пн→Нд. Зсув `(getDay() + 6) % 7`. Клієнт і сервер мусять рахувати однаково, інакше штрафи розійдуться |
| **Тиждень N** на «Сьогодні» | рахується від ПЕРШОГО ВИКОНАНОГО тренування, а не від старту сезону |
| **ELO** | рейтинг за регулярність. Рахує сервер, клієнт лише показує |
| **Слот** | день тижня в плані (1..7), не конкретна дата |
| **Ключ дня** | рядок `'YYYY-MM-DD'` у ЛОКАЛЬНОМУ поясі. Порівняння дат — це порівняння рядків |
| **Трекер** | модуль щоденного вводу (сон, вода, кроки…), `js/tracker-core.js` |
| **Онбординг** | не прапорець, а СТАН ДАНИХ: крок щоразу виводиться з полів профілю |
| **Ядро** (`*-core`) | модуль без DOM, під юніт-тестами |
| **`ib.*`** | префікс ключів у localStorage |
| **Гейт** | сторож: віковий (17+) і онбординговий, `js/agegate.js` |

## 5. Інваріанти, які легко зламати мовчки

Кожен із них уже ламався.

1. **Дати локальні, не UTC.** `toISOString()` для ключа дня заборонений.
2. **Тиждень з понеділка** — і в клієнті, і в сервері, і в календарі.
3. **Журнали append-only.** Виняток один: повторний запис у ТОЙ САМИЙ
   день замінює сьогоднішній. За рівної ваги рекорд лишається за ПЕРШОЮ
   датою.
4. **Ліміти живуть у ядрі й експортуються** (`LIMITS`, `MAX_WEIGHT`,
   `REP_CAP`…). Екран показує людині те саме число, яким перевіряє.
   Другий список у розмітці розійдеться мовчки.
5. **Стать фільтрує програми тільки через `programAllowedFor`** —
   фільтр у розмітці лишає чужий план доступним через збережений
   `activePlan`.
6. **`PERSONAL_KEYS` — один перелік на весь `store.js`.** Три списки вже
   розходились (SYN-006).
7. **Порожня відповідь хмари ≠ «в хмарі порожньо»** — інакше вхід стирає
   локальні дані.
8. **`backdrop-filter` не бачить нічого крізь предка, у якого він теж
   є.** Предок із `filter`, `opacity<1`, `mask`, `mix-blend-mode`,
   `isolation` чи `contain:paint` створює backdrop root і мовчки вбиває
   скло всередині.
9. **`lostpointercapture` спливає.** Обробник на контейнері ловить події
   дітей і ламає жест — треба `if (ev.target !== bar) return;`.
10. **`SCHEMA_VERSION` росте лише при зміні ФОРМИ даних**, не при
    додаванні поля. Версія 5 зайнята назавжди.
11. **Порожні ключі Supabase — робочий стан**, а не помилка: сайт іде в
    локальний режим.

## 6. Публікація

```
робота в репозиторії
   ↓  копіюємо змінені файли
тека релізу на Mac:  ~/Desktop/Get Stronger/Get Stronger
   ↓  подвійний клік по «Опублікувати.command» у корені теки
npm test + ci-hygiene → коміт → git push origin main
   ↓
Vercel збирає сам (збірки немає — статика)
```

Ключ до GitHub лежить у звʼязці ключів Mac. Хмарний контейнер до нього
доступу не має і мати не повинен — тому пуш робить машина.

**Тести — ворота.** Червоні тести чи гігієна = нічого не відправлено.

**Автопублікації більше немає.** Тут був launchd-агент
`com.forge.autopublish`, який раз на хвилину запускав
`tools/auto-publish.sh`. Він тихо помер: macOS перестав давати
`/bin/bash` читати теку на Робочому столі —

```
/bin/bash: .../Get Stronger/tools/auto-publish.sh: Operation not permitted
```

— і дві доби зміни нікуди не їхали, а ніхто цього не бачив. Автомат,
який мовчки не працює, гірший за ручну кнопку: кнопка або спрацювала на
очах, або ні. Вирізано разом із усіма `Автопублікація-*.command`.

Заразом прибрано «Полагодити-пуш.command»: він викидав `ci.yml` з
коміта, тобто «лагодив» пуш ціною вимкнення CI. Кнопку, яку не можна
натискати, краще не тримати поруч із кнопкою, яку натискати треба.
