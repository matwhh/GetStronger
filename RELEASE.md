# Випуск Forge

Коротко: Forge — статичний сайт без збірки. «Зібрати» його не потрібно —
достатньо покласти файли на будь-який статичний хостинг. Нижче — що
зробити ПЕРЕД цим і що свідомо лишається на потім.

---

## 1. Перед викладенням

### 1.1. Впиши домен

`js/config.js` → `siteUrl`. Без нього не буде `canonical` і `og:url`.

```js
siteUrl: 'https://forge.example.com'
```

### 1.2. Прошити метатеги в розмітку

```bash
node tools/build-meta.js
```

Скрипт вписує `canonical`, `og:url` і створює `sitemap.xml` та рядок
`Sitemap:` у `robots.txt`.

**Навіщо це окремим кроком:** `js/app.js` уміє додавати ті самі теги, але
вже після виконання JavaScript. Для Google цього досить, для краулерів
превʼю в месенджерах — ні: Telegram, Slack, WhatsApp і Signal JS не
виконують узагалі, і посилання відкривалось би в чаті без картки.

Скрипт ідемпотентний: повторний запуск оновлює теги, а не додає другі.

### 1.3. Акаунти (необовʼязково)

Порожні `supabase.url` / `anonKey` — це РОБОЧИЙ стан: Forge працює
локально, дані лежать у `localStorage` цього браузера. Синхронізація між
пристроями зʼявляється лише коли ключі заповнені (інструкція — у шапці
`js/config.js`, схема — `db/schema.sql`).

`anon`-ключ публічний за задумом: доступ обмежують політики RLS. У коді
немає жодного секрету, який не можна показувати.

### 1.4. Перевірка

```bash
npm test                      # 226 модульних тестів
TZ=Europe/Kyiv npm test       # обовʼязково у двох поясах, див. нижче
```

Далі — браузерні прогони з `tools/README-verify.md`. Дев'ять скриптів,
усі повертають код виходу, тож ставляться в CI як є. Найважливіший перед
релізом — `verifyroundtrip.mjs`: він тисне справжні кнопки «Експортувати
JSON» → «Стерти локальні дані» → «Імпортувати JSON» і звіряє профіль поле
за полем, включно з тим, що Forge Rating після відновлення дає ТЕ САМЕ
число.

**Про часові пояси.** Частина логіки рахує календарні дні. Помилки
переходу на зимовий час у UTC не видно взагалі — саме так у минулому
проїхав нескінченний цикл, що вішав вкладку. Ганяй тести щонайменше в
UTC і в цільовому поясі.

## 2. Вимоги до хостингу

| Що | Навіщо |
|---|---|
| Статична роздача файлів | Іншого й не потрібно — немає ні збірки, ні бекенду |
| **gzip або brotli** | Найважча сторінка: 564 КБ сирих → 155 КБ gzip. Без стиснення це втричі більше трафіку |
| HTTPS | Обовʼязково для «Додати на екран Home» і для `navigator.clipboard` |
| Кешування з валідацією | `Cache-Control: no-cache` на `.html`, довгий кеш на іконки. Без версіонування імен файлів агресивний кеш на `.js`/`.css` віддасть стару версію після оновлення |

Forge відкривається і як `file://` (подвійним кліком по `index.html`) —
це навмисно й перевіряється тестами.

## 3. Свідомо НЕ зроблено

Це не забуті пункти, а рішення. Кожне з наслідками.

### 3.1. Немає service worker → офлайн працює НЕ повністю

**Що працює зараз без мережі:** усе, що вже відкрито. Дані пишуться в
`localStorage`, зміни лягають у чергу, після повернення мережі
досилаються. Індикатор у шапці показує, що чекає на відправку.

**Що НЕ працює:** перехід на сторінку, яку браузер ще не поклав у свій
HTTP-кеш. Без service worker він покаже власну сторінку «немає мережі».
У встановленому вигляді (з `manifest.webmanifest`, `display: standalone`)
це виглядає як зламаний застосунок.

**Що потрібно, коли до цього дійдуть руки:**

1. `sw.js` зі стратегією *cache-first для оболонки, network-first для
   даних*. Оболонка тут — 16 сторінок, `css/style.css`, `js/*.js`,
   іконки. Це ~1,9 МБ сирих файлів.
2. Реєстрація в `js/app.js` під `if ('serviceWorker' in navigator)`.
3. **Версіонування кешу.** Без нього оновлення сайту не доїде до тих, хто
   вже його відкривав: service worker віддаватиме стару копію вічно. Ім'я
   кешу має мінятись із кожним випуском, а старі — видалятись в `activate`.
4. Повідомлення «є нова версія, перезавантажити» — інакше людина сидітиме
   на старій збірці й не знатиме про це.

Пункти 3 і 4 — причина, чому цього немає зараз: поганий service worker
гірший за його відсутність, бо ламає доставку оновлень мовчки.

### 3.2. Немає мініфікації

Код навмисно з розлогими коментарями: вони пояснюють, ЧОМУ саме так, і
кілька разів рятували від повторення старих помилок. Після gzip коментарі
коштують мало (155 КБ на найважчій сторінці). Мініфікація зʼявиться
разом зі збіркою — якщо вона колись знадобиться.

### 3.3. Шрифти з Google Fonts

`Archivo Black`, `Inter`, `JetBrains Mono` тягнуться з
`fonts.googleapis.com`. Наслідки: сторонній запит на кожне завантаження і
залежність від чужої доступності. Підвантаження асинхронне
(`media="print"` + `onload`), тож рендер це не блокує, а `<noscript>`
лишає запасний варіант. Локальне розміщення шрифтів прибрало б і запит,
і питання приватності — окремий крок.

## 4. Що перевірити руками після викладення

- [ ] Кинути посилання в Telegram — має зʼявитись картка з `og-image.png`
- [ ] Відкрити на iPhone, «Поділитись» → «На екран Home» — на ярлику має
      бути знак Forge, а не скріншот сторінки
- [ ] Заповнити вагу з **комою** (`82,5`) на iOS — має зберегтись
- [ ] Вимкнути мережу, змінити дані, перезавантажити — дані на місці,
      у шапці зʼявилась позначка «Не синхронізовано»
- [ ] «Експортувати JSON» → «Стерти локальні дані» → «Імпортувати JSON» —
      профіль, історія, трекери й Rating повернулись
- [ ] Надрукувати «Мій план» — має вийти аркуш без інтерфейсу

## 5. Записані ідеї на майбутнє

Знайдені під час аудиту, **свідомо не реалізовані**: кожна — нова
функція або переписування, а не готовність до релізу.

| Ідея | Чому не зараз | Що вона дасть |
|---|---|---|
| Service worker | Правильний SW — це версіонування кешу й доставка оновлень; поганий SW гірший за жоден (див. 3.1) | Повний офлайн, вхід із ярлика без мережі |
| Мініфікація і збірка | Зараз сайт відкривається подвійним кліком по `index.html`; збірка це ламає | −40% ваги JS/CSS понад gzip |
| Самостійний хостинг шрифтів | Треба покласти `.woff2` і переписати `@font-face` (див. 3.3) | Мінус зовнішній запит, працює без інтернету |
| Спільні помічники дат | `todayKey`/`addDays`/`keyOf` живуть у трьох ядрах окремо — навмисно, заради незалежності модулів | −60 рядків, але поява спільної залежності між ядрами |
| Винесення `window.X` в `import` | Модулі шукають одне одного через глобалі — це єдина прив'язка ядер до браузера | Ядра можна взяти в React Native / Node як є |
| Віртуалізація довгих списків | Найважча сторінка — 552 вузли; поріг, за яким це потрібно, ще не досягнутий | Запас на профілі з 5+ роками історії |

## 6. Готовність до мобільного застосунку

Аудит §6 — **аналіз, не робота**. Стан на момент релізу:

- **Бізнес-логіка відділена.** 4225 рядків із 18281 (23%) — це
  `js/*-core.js` і `js/*-data.js`: нуль звернень до `document`,
  `location` чи слухачів подій. Вони переносяться в React Native або
  Node без правок, окрім заміни `window.X` на `import`.
- **Сховище за одним інтерфейсом.** Усе йде через `Store`
  (`getProfile`/`saveProfile`/`onChange`); ні сторінки, ні ядра не
  чіпають `localStorage` напряму. Заміна на SQLite чи AsyncStorage —
  це один файл.
- **Модель даних одна й описана.** `blankProfile()` у `js/store.js` —
  єдине джерело форми, `SCHEMA_VERSION` + `migrate()` уже вміють
  переносити старі профілі. Той самий JSON віддає експорт.
- **Автентифікація й синхронізація вже не браузерні.** Supabase
  говорить по HTTP; черга офлайн-патчів (`ib.pending`) — звичайний
  масив, не залежний від Web API.
- **Точка входу для Apple Health / Google Fit існує.**
  `TrackerCore.ingest()` приймає `{value, source, date}` — записи вже
  зберігаються з полем джерела, тож імпорт із годинника не потребує
  зміни формату.

Що доведеться писати заново в застосунку: увесь UI (сторінки
`js/*.js` — 14 тис. рядків), друк плану і графіки на SVG.
