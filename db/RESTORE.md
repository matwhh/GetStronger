# Відновлення бази Get Stronger з резервної копії

Supabase на Free-плані не робить бекапів узагалі. Єдина копія даних усіх
користувачів — це файл `backup-forge-РРРР-ММ-ДД.json` на Mac, у
`~/Desktop/Get Stronger/backups/`. Цей документ описує, як із нього відновитись, і
чесно перелічує, чого він не покриває.

Стан на 2026-09-07: відновлення пройдено на справжньому дампі продакшену
(3 користувачі, 3 identities, 2 профілі, 3 події ELO) — 27 перевірок,
0 провалів.

## Що з чого складається

| Файл | Роль |
|---|---|
| `db/backup-export.sql` | SELECT, який віддає всю базу одним JSON. Запускається через SQL Editor або MCP під service_role. |
| `tools/restore-backup.mjs` | JSON → SQL відновлення. Нічого не видаляє, все в одній транзакції, з самоперевіркою. |
| `db/restore-skeleton.sql` | Мінімальна структура (таблиці, PK, FK, послідовності) для прогону відновлення в порожній базі. Не заміна `db/schema.sql`. |
| `tools/verify-backup-roundtrip.mjs` | Повний цикл файл → база → файл. Ганяється в CI на кожен пуш. |
| Задача «Get Stronger: щоденна резервна копія бази» | Знімає копію щодня о 16:00 UTC (19:00 за Києвом) і віддає файл **у чат**. На диск сама не кладе — чому, у розділі «Привʼязка задачі до компʼютера» нижче. Сповіщення (push + email) увімкнені. |

Копія самого запиту лежить і поруч із бекапами — `~/Desktop/Get Stronger/backups/backup-export.sql`,
щоб зняти дамп можна було, не відкриваючи репозиторій. Змінюєш `db/backup-export.sql` —
онови ту копію і текст запланованої задачі: запит зашитий і в неї теж.

**Привʼязка задачі до компʼютера.** Щоб задача могла класти файл на Mac, її треба
підтвердити на самому Mac при створенні. Без підтвердження вона виконується
тільки в хмарі: копію зніме і віддасть у чат, але на диск не покладе — і скаже
про це першим реченням. Привʼязку не можна додати заднім числом: задачу
доведеться створити наново. Саме на цьому провалилася попередня версія
(`folders_state = FOLDERS_STATE_NONE` плюс вимкнені сповіщення = тиха відсутність
бекапів).

**Стан на 2026-09-10.** Попередня задача зникла зовсім: у списку запланованих
задач не було жодної, а найсвіжіша копія на диску була від 1 вересня — девʼять
днів без бекапа. Задачу створено наново (`trig_01PUgPUqKKgH4iXjWEctZQQB`,
щодня о 16:00 UTC = 19:00 за Києвом, push і email увімкнені). Привʼязатись до
Mac вона знову НЕ змогла — `folders_state = FOLDERS_STATE_NONE`, бо створювалась
не з підтвердженням на самому Mac. Тому тепер головний шлях у її тексті —
віддати файл у чат через `SendUserFile`, а запис у `~/Desktop/Get Stronger/backups/`
описаний як необовʼязковий крок «якщо доступ до Mac є». Копія в чаті лежить поза
Mac, тож як бекап вона навіть надійніша; ціна — файл треба зберегти руками.

Щоб копія знову лягала на диск сама, задачу треба **перестворити з Mac**, у
десктопному застосунку, підтвердивши доступ до теки. Відредагувати наявну не
вийде: привʼязка не додається заднім числом.

## Зняти копію вручну

Supabase → SQL Editor → вміст `db/backup-export.sql` → Run → зберегти результат
як `~/Desktop/Get Stronger/backups/backup-forge-РРРР-ММ-ДД.json`.

Файл має бути ~35 КБ і більше. Кілька сотень байтів означає, що SELECT віддав
порожні масиви — це не копія.

## Перевірити копію (без бази, 2 секунди)

```sh
node tools/restore-backup.mjs ~/Desktop/Get Stronger/backups/backup-forge-2026-09-07.json --out /tmp/restore.sql
```

Скрипт впаде, якщо файл обрізаний (`counts` не збігається з довжиною масивів),
якщо немає масиву таблиці, якщо в бекапі нуль користувачів або якщо рядки одної
таблиці мають різні набори колонок.

## Перевірити, що з копії справді відновлюється (повний цикл)

```sh
node tools/verify-backup-roundtrip.mjs ~/Desktop/Get Stronger/backups/backup-forge-2026-09-07.json
```

Потрібен локальний Postgres (`initdb`, `pg_ctl` — пакет `postgresql`).
Скрипт піднімає тимчасовий кластер у `tmp`, розгортає `db/restore-skeleton.sql`,
заливає бекап, повторно знімає експорт і звіряє його з вихідним файлом рядок у
рядок, потім зносить кластер. Нічого поза `tmp` не чіпає, до мережі не ходить.

Код виходу: `0` — усе пройшло, `1` — щось впало, `3` — Postgres у системі
немає, тому перевірено не все.

## Відновлення в бойову базу

**Спершу зупинись і прочитай.** Скрипт відновлення нічого не видаляє: усі
вставки — `on conflict do nothing`. Тобто він доливає в базу те, чого в ній
бракує, і не чіпає наявних рядків. Якщо задача протилежна («повернути базу до
стану на дату»), цей скрипт її не вирішує — і не повинен: автоматичне затирання
живих даних файлом з робочого столу — це наступна аварія, а не вихід із цієї.

1. Прожени `verify-backup-roundtrip.mjs` на файлі. Не відновлюйся з файла, який
   не пройшов перевірку.
2. Згенеруй SQL: `node tools/restore-backup.mjs <файл> --out restore.sql`.
3. Прочитай початок `restore.sql` — там дата зняття копії. Переконайся, що це
   той файл.
4. Supabase → SQL Editor → вміст `restore.sql` → Run. Усе в одній транзакції:
   якщо в кінці самоперевірка знайде, що рядків менше, ніж у `counts`, —
   виняток і відкат цілком.
5. Після відновлення перевір послідовності:
   `select last_value from pg_sequences where schemaname = 'public';` —
   мають збігатися з `sequences` у файлі.

Якщо база втрачена повністю (новий проєкт Supabase), перед кроком 4 треба
розгорнути справжню схему: `db/schema.sql`, далі міграції в порядку
`list_migrations`. `db/restore-skeleton.sql` для цього не годиться — у ньому
немає ні RLS, ні політик, ні функцій.

## Чого це відновлення НЕ покриває

Це не «дрібний шрифт», а перелік того, що доведеться робити руками.

- **Паролі.** `encrypted_password` і всі токени навмисно не експортуються:
  файл лежить на робочому столі, і хеші паролів усіх користувачів у ньому —
  гірше, ніж їхня відсутність. Після відновлення кожен проходить
  «Забули пароль?». Саме тому у форматі 2 зʼявилися `auth.identities`,
  `raw_app_meta_data.provider`, `aud`, `role`, `instance_id` — без них GoTrue не
  знайде email-провайдера і навіть скидання пароля не спрацює.
- **Чи справді GoTrue пустить відновленого користувача.** Локальний Postgres
  цього не доводить: там немає GoTrue. Перевіряється лише на справжньому
  Supabase (гілка або новий проєкт) і поки що не перевірено.
- **Сесії.** Після відновлення всі недійсні — це правильно.
- **Схема, політики RLS, функції, cron.** Вони в `db/*.sql` і в міграціях, а не
  в бекапі даних.
- **Файли Storage.** Проєкт ним не користується. Зʼявиться — доведеться
  розширювати експорт.
- **Ротація копій.** Старі файли не видаляються. ~35 КБ на добу — приблизно
  13 МБ на рік; коли набридне, чисти теку руками.

## Якщо копії немає за вчора

Задача «Get Stronger: щоденна резервна копія» перевіряє це сама і пише про це в
сповіщенні. Причини за спаданням імовірності: Mac був вимкнений о годині
запуску; задача втратила привʼязку до компʼютера; Supabase недоступний. Зняти
копію вручну (розділ вище) — і подивитись у список задач, чи вона взагалі
запускалась.
