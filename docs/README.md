# docs/ — документація Get Stronger

Сім файлів і тека звітів. Кожен відповідає на своє питання, і навмисно не
переказує сусіда: два описи одного й того самого розходяться на першій же
правці.

| Файл | Питання, на яке відповідає | Коли читати |
|---|---|---|
| [`CONTINUE.md`](CONTINUE.md) | **«Я тут уперше (або через півроку). З чого почати?»** — модель проєкту, робочий цикл, пастки, готовий промт | найперше |
| [`MAP.md`](MAP.md) | «Де це міняти?» | коли знаєш, ЩО робиш, але не знаєш ДЕ |
| [`RECIPES.md`](RECIPES.md) | «Як додати сторінку / трекер / продукт / поле?» | перед типовою зміною |
| [`GLASS.md`](GLASS.md) | «Як зроблений цей ефект скла?» | коли чіпаєш оформлення |
| [`ENGINEERING.md`](ENGINEERING.md) | «Чому воно саме так?» | коли рішення здається дивним — там причина |
| [`EMAIL.md`](EMAIL.md) | «Що з листами Supabase?» | коли правиш реєстрацію чи відновлення |
| [`audit/`](audit/) | «Що вже знайшли й виправили?» | перед великою переробкою |

Що змінилось останнім — теж не тут, а в `git log --oneline -15`: тіло
кожного коміту пояснює причину. Документ «останні зміни» протух би за
тиждень, тому його немає навмисно.

Правила проєкту — не тут, а в [`../AGENTS.md`](../AGENTS.md). Це
свідомо: правила читаються першими й мусять лежати в корені, де їх видно
і людині, і інструменту.

---

## Порядок, у якому це має сенс читати

```
AGENTS.md            що можна, чого не можна, як перевіряти
   ↓
docs/CONTINUE.md     як запустити, як влаштований робочий цикл
   ↓
docs/MAP.md          що де лежить
   ↓
docs/RECIPES.md      як зробити конкретну типову зміну
   ↓
   (далі — за потреби)
docs/GLASS.md · docs/ENGINEERING.md · docs/EMAIL.md · docs/audit/
```

`ENGINEERING.md` — 3400 рядків. Його не читають підряд: у ньому шукають
розділ про те, що саме зараз чіпаєш, щоб не переробити вдруге те, що вже
пробували й відкинули.

---

## Що куди дописувати

| Зробив | Пиши в |
|---|---|
| новий модуль, сторінку, ключ у профілі | `MAP.md` |
| новий тип зміни, який доведеться повторювати | `RECIPES.md` |
| рішення, яке через рік виглядатиме дивним | `ENGINEERING.md` — з причиною |
| новий візуальний ефект або поверхню | `GLASS.md` |
| змінив шаблон листа | `EMAIL.md` |
| знайшов і виправив проблему | коміт + `ENGINEERING.md`, якщо причина неочевидна |

Документ без причини не потрібен. `ENGINEERING.md` цінний саме тим, що в
ньому написано **чому**, а не **що** — «що» видно з коду.
