# Браузерні перевірки

Не частина `npm test`: вони піднімають справжній Chromium і ходять по
сторінках через `file://`. Тримаються окремо, щоб `npm test` лишався
швидким і не вимагав браузера.

Потрібен Playwright:

```bash
npm i playwright
```

## Набори, які ганяє CI

Перелік — не тут, а в `tools/ci-browser.sh` (змінні `CORE` і `FULL`): один
файл, з якого і CI, і людина беруть той самий список. Дублювати його тут
означало б розійтись — саме це й сталось (TST-014: тут було 17 скриптів
із 41).

```bash
bash tools/ci-browser.sh core   # 14 наборів, кожен пуш, ~8 хв
bash tools/ci-browser.sh full   # + 33, раз на добу, ~50 хв
```

**Поза CI навмисно** (пояснення — у шапці `ci-browser.sh`):
`verifyregister`, `verifyregfail`, `verifyregresume`, `verifyrecover` —
створюють користувачів у бойовому Supabase; `verifyproduction` — стукає в
бойовий домен; `verifyauthz` — читає бойовий бекенд anon-ключем, доводячи,
що незалогінений не бачить нічого (ганяти руками після змін у RLS).

```bash
node tools/verify7.mjs           # 16 сторінок × 2 ширини: overflow, JS-помилки

node tools/verifya11y.mjs        # focus trap, Escape, aria, мобільне меню
                                 # + рейтинг, сезони й нагороди: заголовки,
                                 #   імена контролів, tabindex, skip-link, inert
node tools/verifyflows.mjs       # наскрізні сценарії + друк
node tools/verifyhardening.mjs   # пошкоджене сховище, швидкі кліки, offline, крайні числа
node tools/verifyonboard.mjs     # шлях нового користувача: онбординг → тиждень
node tools/verifyonboarding.mjs  # ворота онбордингу: кроки, обходи, імпорт копії
node tools/verifyresponsive.mjs  # 320/375/430/768/1024/1280/1920: overflow, дрібні цілі
node tools/verifyroundtrip.mjs   # §14: Export → Clear → Import, звірка поле за полем
node tools/verifyplanfields.mjs  # перехід між полями ваги не згортає день і не краде фокус
node tools/verifythemes.mjs      # 18 тем: контраст, поверхні, вибір, імпорт
node tools/verifyloop.mjs        # щоденний цикл: дія → стан оновився; мобільна панель
node tools/verifyworkout.mjs     # тренування як окремий екран + опційний настрій сесії
node tools/verifyagegate.mjs     # 17+: гейт, обхід URL/історією/localStorage/імпортом, токен у хеші
node tools/verifyreps.mjs        # діапазони повторень: 4 стажі × 4 програми × великі/малі групи
node tools/verifyheatmap.mjs     # теплокарта: рівні з журналу, підказка, легенда, перемикач дня
node tools/verifyseg.mjs         # сегментований перемикач: доріжка по вмісту, виділення їздить і не бреше
node tools/verifytilt.mjs        # скляні картки вибору: нахил, блик за курсором, фокус, контраст скла
node tools/verifyperf.mjs        # вага сторінок, час завантаження, вузли — зі стелями
node tools/verifysw.mjs          # service worker: оболонка, офлайн, аварійний вимикач
node tools/verifyhelp.mjs        # контекстна довідка: кнопка на кожній сторінці, різний вміст, модальність
node tools/verifylink.mjs        # вхід за посиланням із листа, чужий токен, beacon
node tools/verifyawards.mjs      # вітрина нагород: рідкість кольором, слово на звороті, фільтри
node tools/verifyseasons.mjs     # стрічка подій (згортається й памʼятає), плитки-входи, seasons.html

node tools/verify-schema-perms.mjs  # права й політики: справжні запити клієнта по копії схеми
```

Усі повертають ненульовий код при провалі — їх можна ставити в CI як є.
`verifyperf.mjs` донедавна був винятком: він лише друкував таблицю і
завжди виходив з нулем, а `ci-browser.sh` рахував його пройденим. Тепер
у нього три стелі (вага, час, вузли) — TST-012.

Усі перевірки, крім `verifyagegate.mjs`, `verifyonboarding.mjs` і `verifyonboard.mjs`, створюють
контекст через `tools/adult.mjs` — він садить `profile.birthDate` ще до
першого переходу. Без цього віковий сторож чесно відвертав би їх на
`welcome.html`, і падали б вони не через баг, а через правильну поведінку.
Ті двоє починають із чистого браузера навмисно: одна перевіряє сам гейт,
друга — шлях новачка від першого екрана.

Шлях до браузера рахує `tools/pw.mjs` — переносно, з кількох звичних місць
(`PLAYWRIGHT_BROWSERS_PATH`, `/opt/pw-browsers`, домашня тека). Прибитих
цвяхами шляхів у перевірках більше немає.

`npm test` варто ганяти щонайменше у двох часових поясах: частина логіки
рахує календарні дні, і помилки переходу на зимовий час видно лише там.

```bash
TZ=UTC npm test && TZ=Europe/Kyiv npm test
```

## ELO (етап 6)

- `simelo.mjs` — детермінована симуляція сезону (92 дні, mulberry32):
  5 профілів × 5 сідів + Flawless; перевіряє 6 цілей балансу з
  `db/elo-config.json`. Якщо міняєш баланс — цей скрипт мусить лишатись 6/6.
- Юніт-тести ELO: `tests/elo-core.test.js` (сезони, рівні, дельти,
  толеранс-драбини, Grace, кепи) — ганяються звичайним `npm test`.
- **Паритет JS↔SQL стережеться машиною** (TST-004). Дельти живуть у двох
  реалізаціях: `js/elo-core.js` показує число людині, а
  `public.elo_action_delta` записує його в базу. Розбіжність не падає й не
  логується — на екрані одне, в акаунті інше.
  - `tests/elo-parity.fixtures.json` — 20 входів із межами (нуль, повний
    обсяг, перебір, середина смуги, grace). Генерує
    `node tools/gen-elo-parity.mjs`.
  - `tests/elo-parity.test.js` — бік JS, ганяється в `npm test`.
  - `tools/verify-elo-week.mjs` — бік SQL: ті самі входи крізь
    `elo_action_delta` у тимчасовому локальному Postgres.
  - Правиш формулу — міняй ОБИДВА боки, перегенеруй фікстури й поклади їх
    у той самий коміт: тоді в `git diff` видно, як саме змінились
    нарахування.
  - Чинне визначення `elo_action_delta` — `db/elo-proportional.sql`, а не
    `db/elo-engine.sql`: пропорційна модель тренувань замінила східчасту.
    Фактичний текст усіх функцій — у `db/live-schema.sql`.

## SQL-перевірки сервера

92 перевірки авторитетного шару: атаки підробленим payload, бюджети,
реконсиляція, RLS, адмінські RPC. Це єдині тести того шару, де помилка
коштує найдорожче, — і до вересня 2026 вони ганялись лише руками в SQL
Editor, без жодного сліду останнього прогону (TST-017).

Тепер їх ганяє машина:

```bash
node tools/verify-sql-suites.mjs
```

Знімок бойової схеми (`db/live-schema.sql`) розгортається в тимчасовий
локальний Postgres, туди ж заливається `db/elo-config.json`, і кожен файл
виконується як є. Кожен скрипт НАВМИСНО завершується `raise exception` —
так він відкочує все, що насіяв, і водночас віддає підсумок.

| Файл | Що перевіряє | Перевірок |
|---|---|---|
| `db/elo-tests.sql` | Дельти дій, драбини якості, кепи дня й тижня | 20 |
| `db/elo-integrity-tests.sql` | Серверна ідентичність події, бюджети, реконсиляція, нагороди | 29 |
| `db/multiuser-tests.sql` | RLS і адмінські RPC під імперсонацією | 21 |
| `db/sim-week.sql` | Тиждень одним прогоном, 10 користувачів | 22 |

**Часозалежні фікстури.** Двічі ці скрипти падали не через сервер, а
через день тижня: у понеділок «вчора» і «сьогодні» належать різним
ISO-тижням, а в суботу вичерпаний тижневий бюджет робив реконсиляцію
неможливою (TST-015). Обидва місця тепер фіксують передумову явно. Якщо
щось падає лише певного дня — спершу перевіряй фікстуру.

Поруч у CI ганяються ще дві перевірки того ж шару:
`tools/verify-elo-week.mjs` (оцінка тижня, гонка двох викликів, паритет
JS↔SQL) і `tools/verify-schema-perms.mjs` (права й політики: справжні
запити клієнта по копії схеми).
